# Notes: talking to a Blackhole

What we have learned about the chip, where each fact comes from, and what is still unknown. ROADMAP.md has the plan.
Sources: **ISA** = tt-isa-documentation/BlackholeA0, **sim** = ttsim `src/`, **kmd** = tt-kmd, **umd** = tt-umd.
Facts the code uses live in `ferrite/bh.py`.

## Address map

### PCIe function

Vendor 0x1E52, device 0xB140 (sim `pcie.cpp`, kmd). Three 64-bit prefetchable BARs (ISA `PCIExpressTile/README.md`):

| BAR | Size | Contents |
|---|---|---|
| BAR0 | 512 MiB | `0x0000_0000-0x193F_FFFF`: 202 TLB windows of 2 MiB (TLBs 0-201). TLBs 0-31 can do strided multicast; TLB 201 is reserved for the kernel driver. |
| | | `0x1FC0_0000`: TLB config, `u32[3]` per TLB for TLBs 0-209, then `u32 strided[32]` at `0x1FC0_09D8` |
| | | `0x1FD0_4000`, `0x1FD1_4000`: the PCIe tile's NoC0 and NoC1 NIU registers |
| | | `0x1FE0_0000-0x1FFF_FFFF`: ARC on PCIe 1 only; reserved on PCIe 0, which is the one a p150 uses |
| BAR2 | 1 MiB | PCIe controller (DBI): eDMA read channel 0 at `0x100-0x1A8`, iATU at `0x1000` (outbound region r at `0x1000 + 0x200*r`, inbound interleaved between). Not in ISA; offsets from kmd `blackhole.c`, umd `blackhole_dma_transfer.cpp`, sim. |
| BAR4 | 32 GiB | 8 TLB windows of 4 GiB (TLBs 202-209) |

### NoC

17 x 12 grid. Raw NoC0 coordinates (ISA `Diagrams/Src/NoC.lua`, sim `tile.cpp`): DRAM at x=0 (banks 0-3) and x=9 (banks 4-7), ARC (8,0), PCIe 0 (2,0) and PCIe 1 (11,0), Ethernet on y=1, Tensix at x=1..7,10..16, y=2..11. NoC1 numbers the same grid from the other corner: (16-x, 11-y).

Firmware turns on **coordinate translation** at boot (`NIU_CFG_0` bit 14) and programs every tile's translation tables, so harvested Tensix columns move to the highest x and software never sees which physical columns are dead (ISA `NoC/Coordinates.md`). ferrite uses translated coordinates everywhere:

| Translated (x, y) | What |
|---|---|
| x 1..7, 10..14, y 2..11 | Tensix, 120 on a p150 (x 15, 16 are its 2 harvested columns: firmware 19.5+ harvests 2 on every p150, umd `CHANGELOG`, `cluster_descriptor.cpp`) |
| x 17..18, y 12..23 | DRAM: bank b at (17 + b//4, 12 + 3*(b%4) + port), port 0..2, all three ports reach the same 4 GiB |
| (19, 24) | the PCIe tile connected to the host |
| x 20..31, y 25 | Ethernet |
| y 0 and 1 | not translated in x: ARC is (8, 0) |

A NoC address is (x, y, 64-bit address inside that tile).

### Inside a Tensix tile

As the tile's own cores see it; the last column says whether the NoC reaches the same address (ISA `TensixTile/BabyRISCV/README.md`):

| Address | What | Over NoC |
|---|---|---|
| `0x0000_0000-0x0017_FFFF` | L1, 1.5 MiB. Code runs only from here. | yes |
| `0xFFB0_0000` | the core's own data RAM: 8 KiB for BRISC and NCRISC, 4 KiB for each TRISC. Stack goes here. | no (yes via slow aliases at `0xFFB1_4000`...) |
| `0xFFB1_2000-0xFFB1_2FFF` | tile control and debug registers, including soft reset and reset PCs | yes |
| `0xFFB1_3138-0xFFB1_314B` | PC snapshot of each core | yes |
| `0xFFB2_0000`, `0xFFB3_0000` | NoC0 and NoC1 NIU registers (the tile issues NoC requests here) | yes |
| `0xFFE0_0000`... | Tensix coprocessor: GPRs, instruction push, PC buffers, mailboxes, config | no |

MMIO registers take exactly one 4-byte access, from either side.

### DRAM

Eight 4 GiB banks; the address inside a DRAM tile is the byte offset in its bank, starting at 0 (umd soc descriptor, kmd `test/tlbs.cpp`; sim models 4080 MiB per bank). ISA does not document the DRAM tile's address layout. On silicon, GDDR training must be done before first use: telemetry tag 22 has 2 bits per bank (trained, error); umd waits up to 300 s and retrains with ARC message `0xB6`.

### Host memory, from the device

The device reaches host memory by sending NoC requests to the PCIe tile at (19, 24). Its address space (ISA `PCIExpressTile/README.md`):

| NoC address | Goes to |
|---|---|
| below `0x0400_0000_0000_0000` (2^58) | the host, as a bus address, through the host IOMMU |
| bits 58/59 set | same, with relaxed ordering / no-snoop |
| `0x1000_0000_0000_0000` (bit 60) | through the outbound iATU (16 regions, programmed in BAR2) to the host |
| `0xF800_0000_0000_0000` | PCIe controller DBI |

So a host buffer at bus address B is NoC address (19, 24, B), with no iATU setup: firmware sets up the windows, and kmd's DMA-mask comment says the same (an IOVA below 2^58 is used directly as a NoC address, kmd `enumerate.c`). kmd and umd still route pinned memory through the bit-60 iATU window, which is only needed to make scattered memory look contiguous. test_dma checks the direct path with a TLB pointed at the PCIe tile.

## TLB setup

A TLB window turns a range of BAR0 (or BAR4) into a range of one tile's NoC address space. Each TLB has a 96-bit config at `BAR0 + 0x1FC0_0000 + 12*i`, written as three 32-bit uncached writes. 2 MiB TLBs (ISA `PCIExpressTile/HostToDeviceTLBs.md`, matches sim and umd):

| Bits | Field |
|---|---|
| 0-42 | NoC address >> 21 |
| 43-48, 49-54 | x_end, y_end (the target, or the far corner of a multicast rectangle) |
| 55-60, 61-66 | x_start, y_start (multicast only) |
| 67-68 | noc: NoC0 or NoC1 |
| 69 | multicast |
| 70-71 | ordering: 0 relaxed, 1 strict AXI, 2 posted writes, 3 counted writes |
| 72 | linked (never safe to set) |
| 73, 75, 76-77 | static VC enable, buddy, VC class (kmd names 74 stream_header and 75-77 static_vc; same bits) |

4 GiB TLBs: bits 0-31 are address >> 32, then x_end at 32, y_end 38, x_start 44, y_start 50, noc 56-57, mcast 58, ordering 59-60, linked 61, static VC 62.

Write the three dwords with 32-bit stores (odd TLBs are not 8-byte aligned), and the address must be window aligned (kmd, umd). umd turns on static VC for windows that only write or only read, and leaves it off for a window that does both: a read+write window on a static VC "crashes the host" (umd `architecture_tlbs.cpp`).

ferrite moves one shared 2 MiB window (TLB 0, strict ordering) whenever an access crosses into another 2 MiB block, and gives the doorbell a TLB of its own (`Chip.map`). Unicast uses dynamic VC. Multicast (`Chip.write(..., start=...)`) sets x_start/y_start, mcast, and static VC class 2, as umd does. Slow on purpose: simple first. Faster later: more windows of their own, posted ordering for bulk writes, BAR4 windows for DRAM.

## Reset sequence

Per Tensix tile, `RISCV_DEBUG_REG_SOFT_RESET_0` at `0xFFB1_21B0`, reachable over the NoC (ISA `TensixTile/SoftReset.md`). A set bit holds a core in reset:

| Bit | Core |
|---|---|
| 11 | BRISC |
| 12, 13, 14 | TRISC0, TRISC1, TRISC2 |
| 18 | NCRISC |

Other bits reset parts of the Tensix coprocessor. There is no atomic set/clear; it is read-modify-write. Power-on value is `0x47800`, all five cores held (sim; ISA does not say). umd releases with `0x80047000`: bit 31 is "staggered start", which spreads core start-up across the chip (power, not function; sim ignores it).

To run code on a core: write `0x47800` (hold everything), write the program into L1, write `0x47000` (release BRISC only), poll L1 for its result with a timeout, write `0x47800` again. `Chip.halt` holds a rectangle; `Runtime` boots it and releases BRISC and the TRISCs.

Leaving reset: the instruction cache is invalidated, GPRs are zeroed, the PC is set (below), and the core's data RAM zeroes itself over up to 2048 cycles unless `RISCV_DEBUG_REG_DISABLE_RESET` (`0xFFB1_2224`) says not to. So: load code while the core is held, and do not preload data RAM over the NoC without setting that bit.

## What the cores run out of reset

Nothing of ours: there is no boot ROM in a Tensix tile. A released core fetches from L1 at its reset PC (ISA `SoftReset.md`):

| Core | Reset PC |
|---|---|
| BRISC | `0x0` (fixed) |
| TRISC0/1/2 | `0x6000`/`0xA000`/`0xE000`, or `RISCV_DEBUG_REG_TRISCn_RESET_PC` (`0xFFB1_2228/222C/2230`) if bit n of `0xFFB1_2234` is set |
| NCRISC | `0x12000`, or `0xFFB1_2238` if bit 0 of `0xFFB1_223C` is set |

The baby cores are rv32im with Zicsr, Zaamo (no lr/sc), Zba, Zbb, and a partial F (no fdiv/fsqrt). No C extension: its encoding space holds `.ttinsn`. ferrite compiles with plain `clang --target=riscv32-unknown-elf -march=rv32im` and links a flat binary at 0 with lld. Gotchas (ISA `BabyRISCV/`):

- `mhartid` reads 0 on every core per ISA; ttsim does not implement it and kills the process. Tell cores apart by entry point.
- `fence.i` does not flush the instruction cache (ttsim rejects it). New code needs a reset release, or a write to `RISCV_IC_INVALIDATE` in Tensix config from a core.
- The L0 data cache (4 x 16 B) is not coherent with NoC or host writes: poll L1 with a `fence` or an atomic in the loop.
- Stores to the same region (e.g. L1) are processed in order, so "write the result, then write the done flag" is safe. Across regions a `fence` is not enough: store, load it back, use the value, then signal.
- Unsupported instructions are undefined behavior, not traps.

Elsewhere on the chip, firmware is already running when we arrive: ARC runs the board management firmware and set up NoC translation and the PCIe windows; Ethernet core E0 runs Tenstorrent's Ethernet firmware.

## What tt-kmd does that a userspace driver must do instead

What kmd does for a Blackhole at probe, open, reset and remove (kmd `enumerate.c`, `blackhole.c`, `chardev.c`, `memory.c`, `pcie.c`), and where ferrite stands:

| kmd | ferrite |
|---|---|
| `pci_enable_device`, 58-bit DMA mask, bus mastering | `Card`: unbind kmd, write sysfs `enable`, set memory + bus master in `PCI_COMMAND` |
| Max Read Request Size 4096 in PCIe Device Control | not done (throughput only) |
| Maps BAR0 TLB config + NIU, BAR2, BAR4; reserves TLB 201 for its own NoC accesses; hands other TLBs out per fd | `Card` mmaps sysfs `resource0/2/4`; with kmd gone every TLB is ours; ferrite uses TLB 0, and TLB 1 for the doorbell |
| Waits for ARC: `0x80030408` bit 0 (500 ms); umd waits for `& 7 == 5` (300 s after a reset) | `Chip.__init__` waits for `& 7 == 5`, 2 s (tested on sim) |
| ARC messages `0xA0` (ASIC_STATE0, then reads `0x80030410` bit 1 for a power-cable fault), `0xC1` (watchdog, 10 s), `0xC7` (firmware log buffer) | not done; `Chip.arc_msg` can send them |
| Power policy: with no fd open, ARC message `0x21` with all flags 0 (minimum AICLK, GDDR PHY down, **Tensix clock-gated**); opening an fd sends `0x7FFE0F21` (everything on); remove sends `0xA3` | `Chip.__init__` sends `0x21` with all 15 flags valid and set (`0x7FFF0F21`: max AI clock, GDDR PHY awake, Tensix and L2CPU on) through `Chip.arc_msg` (tested on sim). Never powers down again. `0x52` (AICLK go busy), which umd also sends, is not sent |
| Pins host memory: IOVA from the IOMMU, or physically contiguous pages without one; programs an outbound iATU region so the device sees it at `0x1000_0000_0000_0000 + offset` | `Card.alloc`: a locked 2 MiB hugepage, bus address from `/proc/self/pagemap` (IOMMU off or passthrough). The device uses the bus address directly: kmd's own comment says an IOVA below 2^58 is a valid NoC address, so no iATU. With an IOMMU on, VFIO type1 `VFIO_IOMMU_MAP_DMA` would supply the IOVA; not written |
| One MSI, only for the firmware log | none needed |
| Reset: set `PCI_COMMAND` bit 6 as a marker, config writes `0x934 = 1` then `0x930 = 0x11` (or ARC `0x56` arg 3), wait >= 2 s, wait for the device to reappear and firmware to clear bit 6, restore config space and MPS (via DBI at NoC `(x,0)` `0xF800_0000_0000_0078`), wait for ARC again | not done; all of it is reachable from userspace through sysfs `config` |
| Telemetry table: `*0x80030434` (tags) and `*0x80030430` (values), each tag word is `id \| index << 16` | `Chip.telemetry`. `Chip.__init__` takes the Tensix column count from tag 34 (enabled columns; good ones come first in translated x) and waits up to 60 s for tag 22 to show every bank in tag 36 trained |
| "NoC cleanup": puts cores back in reset when a process dies | not done: a dead process leaves its firmware polling, which is harmless; the next `Runtime` resets the cores it uses |

ARC messages (kmd `msgqueue.c`, umd `blackhole_arc_message_queue.cpp`): `*0x8003042C` (SCRATCH_RAM[11]) points at a control block whose word 0 is the base of 4 queues and word 1 is `entries | queues << 8`. Queue i (0 = kmd, 3 = applications) is a 32-byte header (`+0` request wptr, `+4` response rptr, `+0x10` request rptr, `+0x14` response wptr; pointers wrap at 2N) followed by N request slots and N response slots of 32 bytes (`u32 header, u32 payload[7]`). Write the slot, bump the request wptr, poke the ARC (kmd: write 0 to `0x800B0000`; umd: write `0x10000` to `0x80030100`), poll the response wptr for up to 1 s. Status is the low byte of the response header, below 240 means OK. ferrite uses queue 3 and umd's poke (ARC_MISC_CNTL IRQ0); ttsim models both pokes and answers kmd's and umd's messages, but kills the process on an unknown code, and returns all-zero responses (so `0x57` "get harvesting" is not usable there; telemetry is).

## The launch loop and the command queue

`ferrite/runtime.py`. Built and tested on ttsim.

**Cores.** `Runtime(chip, start, end)` takes a rectangle of Tensix in translated coordinates. Its last core runs the **dispatcher**; the rest are **workers**. A rectangle of good columns in translated space covers exactly those cores: harvested and non-Tensix columns in between opt out of multicast.

**L1 layout** (ours). Workers: firmware at `0x0`, starting with one jump per core (BRISC at `0x0`, its reset PC; TRISC i at `0x4 + 4i`, set as its reset PC), mailbox at `0x1000` (`[go, kernel, arguments, workers] [done, the dispatcher's x|y, scratch, index]`), the TRISCs' `[go, done 0, done 1, done 2]` at `0x1020`, `SYNC` at `0x1040` (64 bytes for the kernel's cores to talk through; its first 8 words, the counters, zeroed before each launch, the rest written before they are read), `FLAGS` at `0x1080` (32 words for a kernel's workers to signal each other over the NoC, each written by one of them and zeroed by its own worker at the end), two argument buffers at `0x1100` (launches alternate), the loaded kernels from `0x2000` (500 KiB; each a header of four entry offsets, then a program per core), a tile of zeros at `0x7F000` (4 KiB, an fp32 tile; written once at boot, read by kernels that add to zero or reduce: the compiler's slot 0, whose bf16 slot 0 is its second half), kernel data from `0x80000` (`L1_DATA`). Dispatcher: firmware at `0x0`, config at `0x1000` (`[doorbell, ring lo, hi, ring size, status lo, hi, workers' rectangle, workers]`), outbox at `0x1400`, the count of the workers' reports at `0x80000`, command staging from `0x80040` (above the kernels, since loading one writes the dispatcher's tile too).

**Boot** (host, once): multicast reset and worker firmware over the rectangle, a unicast mailbox per worker with its index and the dispatcher's coordinates, the dispatcher firmware and config over the top of the dispatcher's tile (its TRISC jumps park them), a TLB of its own aimed at the doorbell, the TRISC reset PCs and their override bits, then multicast release of every BRISC and TRISC.

**Loaded kernels** (`Runtime.load`). A kernel goes into every worker's L1 once, by one multicast write over the rectangle, and stays: launches name its address. Images run wherever they land: clang's medany model reaches code and data PC-relative, with linker relaxation and jump tables off, and the header holds entry offsets. When the 500 KiB are full, the next load waits for the queue and evicts them all (`evict`). A kernel's zeroed statics are zeroed again at each launch (`KENTRY` clears `.bss` before `kmain`), since nothing reloads it. Its TLB orders writes strictly, so a kernel has landed before the doorbell that launches it (to confirm on silicon). Before this, every launch copied the whole image (up to 15 KB) to every worker: a GPT-2 token was then about 600 launches of 15 kernels.

**A launch** (host): build one command (a 16-byte header `[length, kernel address, argument bytes, workers]`, then the arguments, the same for every worker, 64-byte aligned), copy it into the ring in host memory, and write the new write pointer to the dispatcher's doorbell. That doorbell is the launch's only PCIe access (`test_queue` counts). Commands never straddle the ring's end: a header of length 0 marks the tail unused. Pointers are free-running 32-bit byte counts, so the ring size is a power of two. Before writing, the host waits (with a timeout) for the space the dispatcher has freed.

**The dispatcher** (BRISC firmware, about 1.1 KB): poll the doorbell; read the command's header and then its body from host memory with NoC reads to the PCIe tile (19, 24); multicast the arguments to every worker and wait for every acknowledgement; multicast the launch number, the addresses of the kernel and the arguments, and how many workers it is for into every mailbox (the go: always the same 16 bytes from its outbox, so request initiator 1 holds that multicast from the start, the outbox is written as soon as the command is in, and the go itself is one store); poll the count of reports until every worker has added to it, only that while the next launch is staged; write `[read pointer, launches done]` into host memory. One launch runs at a time, but the next command is read and its arguments written (into the other buffer) while the last one runs, so it goes as soon as the last worker reports; the host hears of a finished launch after that go. What a launch costs: "Launch cost" (5630 cycles on 119 workers when arguments, go and done went worker by worker, polled every 1000 cycles).

**Multicast from a core** (the dispatcher's `multicast`): a write with `NOC_CMD_BRCST_PACKET`, path reserve and a static VC of class 2 (ttsim insists on all three), the rectangle in `NOC_RET_ADDR_HI` as `end | start << 12`, and `NOC_CMD_BRCST_SRC_INCLUDE` off, since the dispatcher sits in the rectangle it multicasts to and its L1 holds other things at the mailbox's address. Each recipient acknowledges, so `NIU_MST_REQS_OUTSTANDING_ID` goes up once and down once per recipient (ISA `NoC/Counters.md`): the dispatcher counts `NIU_MST_WR_ACK_RECEIVED` up to the number of workers instead, then clears the outstanding counters (`0xFFFF` at `NIU + 0x60`; ttsim takes nothing else), which is safe because nothing else is in flight then.

**A worker** (firmware for all four cores, about 680 bytes). BRISC, once at boot: preset request initiators 1 and 2 for `noc_get` and `noc_put` (`noc_setup`). Then: poll `go` with a `fence` in the loop; sit the launch out if its index is not below the launch's worker count; turn the arguments' first word, a number of units, into its own share `[first unit, how many]` (even, in order); zero `SYNC`'s 8 counters; invalidate the instruction caches of BRISC and the TRISCs (Tensix config 185, bits 0-3), then `fence`, read config back, `fence`, so the invalidate has landed before anyone jumps; write the TRISCs' go; call its program; `noc_wait` for the kernel's own transfers; wait for the three TRISCs' done; note the launch as done in its own mailbox (the host reads it if a launch hangs) and add 1 to the dispatcher's count with a NoC atomic increment (`NOC_AT_LEN_BE` = `1 << 12 | 31 << 2`, a 32-bit add of `NOC_AT_DATA`; posted, so no counter moves at either end). A TRISC: poll its go, call its program (if the kernel has one for it), wait until its Tensix thread has run everything it pushed (`tensix_idle`, the Manual TTSync load), write its done.

**Launch cost.** The arguments and the go are one multicast each and the reports one counter, whatever the number of workers. A launch names how many units of work it has (`Runtime.launch(kernel, args, units)`), and goes to no more workers than that: a GPT-2 attention head's kernels have one or two tiles of work. Arguments and go worker by worker cost 45 cycles a worker: multicast took a GPT-2 token from 627k simulated cycles to 371k (a one-tile-row matmul, 768 x 3072, a token's MLP, from 24 to 76 "TFLOPS"). Then the done slots: all 119 workers were done 240 cycles into a launch, and the dispatcher read their slots, one L1 load each, until cycle 870; with one count to read, a token went to 282k (312k after split K). A trace of one worker and the dispatcher through queued one-tile launches (317 cycles each, 352 with a tile on every worker) then showed every core of a worker idle most of a launch, waiting on a chain: the dispatcher's go (about 50 cycles after the last report), the firmware zeroing all 16 words of SYNC, TRISC0's setup pushed as stores, the tile, the report. The dispatcher now spins on the count alone when the next launch is staged and fires a go it set up in advance, the firmware zeroes only SYNC's counters, and setup words other than what a replay records are `.ttinsn`: 220 cycles a launch, 245 with a tile on every worker; a GPT-2 token went from 122.7k cycles to 117.1k, ferrite's training step from 421k to 377k, tinygrad's from 2.05M to 1.98M.

**Profiles** (`Runtime.profile`, `test_profile`). The dispatcher reads its tile's wall clock (`RISCV_DEBUG_REG_WALL_CLOCK_L`, one count a cycle, ISA `DebugTimestamper.md`; ttsim's own clock) when it fires a launch's go and when it sees the launch's last report, and writes the pair into a ring of 1024 entries in host memory before the launch's status: every launch's time on the chip's own clock, with no polling in it. `Runtime.launch` takes a name (Tensor names a kernel by its ops, operands first: a softmax is "max2 sub exp sum2 recip mul"), and `profile(since)` adds up the launches after one by name. A GPT-2 token on ttsim: plain matmuls 46k cycles in 37 launches, the MLP's up-projection with gelu 20k in 12, the attention projection with its bias 20k in 12, layer norms 8k in 25, residual sums 7k in 25, attention 6k in 12, the embeddings 3k: 111k of the 117k the host sees, the rest between launches. `test/gpt2.py` prints this for its last token, the first profile to take on the card (ROADMAP, stage 2).

**Waiting** (`Runtime.wait`) polls the status words in host memory, never the chip. `Tensor` does not wait for its launches: they run in order, so each kernel sees the results of those before it, and only reading a result back (`tobytes`, `tolist`) waits. A timeout counts from the last launch that finished (`until`): a long queue is not a hang, a launch that never finishes is. On timeout it reads the dispatcher's current launch and each of its workers' mailboxes, and names the workers that have not finished.

**DRAM** (`Runtime.dram_alloc`, `dram_free`). A tensor takes the same address range in all 8 banks (tile i in bank i % 8). First fit over a sorted list of holes, 64-byte aligned; a freed block merges with the holes beside it. A `Tensor` frees its DRAM in `__del__`, which CPython runs as soon as the last reference goes, so intermediates and old results go back right away (a reference cycle would hold them until the garbage collector runs: `realize`'s walk is a plain function, not a closure, for that reason). A freed block goes back only once every launch queued before the free is done (`reclaim`), since those may still read or write it; an allocation that finds no room waits for the queue first. ttsim models 4080 MiB a bank.

**Device API**, prepended to every program (`DEVICE`): `noc_me()` (own translated coordinates, `NOC_ID_LOGICAL`), `noc_read`, `noc_write`, `noc_get`, `noc_put`, `noc_wait`, `l1_settle`. All requests go through NIU 0, transaction ID 0: `noc_read` and `noc_write` through request initiator 0, writing all nine of its registers; `noc_get` (a read into this L1) and `noc_put` (a write from it), each of at most one packet, through initiators 1 and 2, which the firmware sets up once at boot (`noc_setup`: the read or write command, this tile's coordinates on its side), so each writes only the four registers that change and the go. An initiator keeps its registers between requests (ttsim keeps four sets, `offset / 0x800`); tt-metal's "stateful" NoC calls do the same. A tile's read went from about 36 RISC-V instructions to 17, which a matmul's critical path felt ("Cutting the critical path"). They are acknowledged (`RESP_MARKED`), so `NIU_MST_REQS_OUTSTANDING_ID(0)` counts them, on a dynamic VC. Rules (ISA `NoC/MemoryMap.md`, `NoC/Counters.md`, enforced by ttsim):

- At most 16 KiB per request (`noc_read`/`noc_write` split; ttsim does not model hardware splitting).
- Source and destination agree in their low 4 bits for L1, low 6 bits when DRAM is involved.
- Reads must be acknowledged. Inline writes to L1 are broken on Blackhole; we never use inline writes.
- Wait for `NOC_CMD_CTRL` bit 0 to clear before touching an initiator; read `NOC_CMD_CTRL` back before reading counters.
- Before the NIU reads data a core just stored: `fence`, load from L1, `fence` (`l1_settle`). After data lands: `fence` before reading it (the L0 data cache). Every `fence` is also a compiler barrier (`"memory"` clobber), or the compiler can cache L1 across it.

**Not built yet:**

1. **Commands other than "launch":** host-to-DRAM copies, events, waiting on another queue.
2. **NCRISC**, a second data mover, stays in reset. It could take the sends home off BRISC, or fetch for a second NoC.
3. **Hang reports from silicon.** The host should also read each stuck core's PC snapshot (`0xFFB1_3138`...); ttsim does not model those registers.
4. **Ordering of the host's ring writes before the doorbell** relies on x86 ordering cached stores before an uncached MMIO write. Fine on x86, and needs a barrier anywhere else.

## The Tensix coprocessor, and the first compiler

`ferrite/compiler.py` (the kernels; `ferrite/tensor.py` builds the trees of ops they compute), encodings and register numbers in `ferrite/bh.py`. Tested on ttsim by `test/test_sim.py`, from `test_tile_math` on; each paragraph below names its tests.

**Who drives it.** Three Tensix threads, each an in-order instruction FIFO; any thread can issue to any unit (unpackers, FPU, packer, ...), the threads only differ in their per-thread state (ADCs, RWCs, GPRs, ThreadConfig). TRISC t pushes to thread t, through that thread's MOP expander; BRISC can push to all three (`0xFFE4_0000 + 0x10000 t`, skipping the MOP expander), but a BRISC push and a TRISC push in the same cycle drop the TRISC's, so only one of them may feed a thread. ferrite: each TRISC feeds its own thread and BRISC only moves data (ISA `BabyRISCV/PushTensixInstruction.md`).

**Instruction words.** `opcode << 24 | fields` (ISA `Diagrams/Src/Bits32.lua`; ttsim `data/bh/tensix_isa.json` agrees and names the fields). A TRISC pushes one by storing it to `0xFFE4_0000`, or by executing it: `.ttinsn` is the word rotated left by 2, written straight into the code (opcodes are below `0xC0`, so the low bits are never `0b11` and it cannot be read as RISC-V). Either way a full FIFO stalls the TRISC. The generated programs are mostly `.ttinsn` words (`compiler.tt`, as `.word`s, since clang has no `.ttinsn`); runs that differ per Dst half or frame are branches between two copies. What a `REPLAY` records goes through stores instead: a TRISC fuses up to four `.ttinsn`s in a row, and fused ones must not be what it records. The rest of setup is `.ttinsn`, one instruction a word where a store takes three (the word built in a register, then stored).

**Configuration.** Three kinds, all needed:

- *Backend config*: 32-bit words at `0xFFEF_0000`, two banks (thread chooses with `CFG_STATE_ID`), a RISC-V store hits bank 0. The ISA docs name the fields but defer every index, shift and width to tt-metal's `cfg_defines.h`; ours come from ttsim's `tensix_regs.json` and must be checked on silicon.
- *Thread config*: 16-bit registers per thread, written only by `SETC16` from that thread, so they are set in-band at the start of the kernel. Reset values are undocumented, so every one we depend on is written.
- *ADCs and RWCs*: per-thread address counters (`SETADC*`) for unpackers and packer, and register-window counters (`SETRWC`) for the FPU.

TRISC0 writes the backend config, then `fence`, reads back a config word, `fence`, and only then pushes; it initialises the semaphores, waits for its thread to run all that (`tensix_idle`), and sets `READY` in `SYNC`. TRISC1 and TRISC2 push their own thread config and setup (address modes, replay recordings, the packer's counters: nothing that reads the backend config or a semaphore) and then wait for `READY` before anything else: the semaphores' power-on values are not documented. All of it is straight-line code generated per kernel (`.ttinsn`, and stores for what a replay records: `_pushes`), not loops over tables in L1: with the overlap, a one-tile kernel went from 790 cycles to 490, and a GPT-2 token from 170k to 150k.

**Tile layout** (ours; the ISA has no notion of a tile). A 32x32 tile is four 16x16 faces in row-major order (top-left, top-right, bottom-left, bottom-right), each face row-major: element (r, c) is at `(r//16*2 + c//16)*256 + r%16*16 + c%16`. An unpacker copies the 1024 datums linearly into Src rows, so face f is Src rows 16f..16f+15, which is what `MVMUL` wants; Dst and the packer keep the same order. Elementwise ops do not care. Tensors are tiles in row-major tile order, tile i in DRAM bank i % 8 at `base + i//8 * 2048`.

**Precision.** Dst is kept in fp32 (`Fp32_enabled`); the packer rounds it to bf16 (`(bits + 0x8000) >> 16`, the only fp32-Dst-to-bf16 mode ttsim allows is `Read_32b_data` with In = bf16). With 4 fidelity phases a bf16 x bf16 product is exact before that rounding (bit-exact on 8192 random pairs). `ELWADD`/`ELWSUB` align the two 11-bit mantissas with round-half-up first, so about 0.4% of random sums differ from the fp32 sum by a last-place bf16 step. fp32 tensors would lose 13 mantissa bits in SrcA/SrcB (TF32), so they are unpacked into Dst and computed on the SFPU ("fp32 tensors").

**Where the docs and ttsim disagree.** `UNPACR` bit 7 is `MultiContextMode` in the ISA and `ovrd_thread_id` in ttsim; both say it must be 1. Bit 0 is "write 0" in the ISA, `last` (must be 1) in ttsim; we follow ttsim. The Blackhole README says "4x packer", the PACR page says one packer with four Dst read ports. `SETDVALID` is unsupported on Blackhole (use `UNPACR_NOP`).

**The pipeline** (`fused_kernel`). Each thread has one job, so unpack, math and pack work on different tiles at the same time. L1 holds an array of tile slots; the unpackers' Z counter (Z stride: one tile) and the packer's channel-1 Y counter (that Y stride: one tile) pick the slot, so moving between slots never touches config:

| Thread | Job | Per tile (or matmul step) |
|---|---|---|
| 0 | unpack, and report | `SETADC` each unpacker's Z to its slot, `UNPACR` into SrcA and SrcB; after a frame or a matmul step, wait for the unpackers and `SEMPOST` SEM_UNPACKED |
| 1 | math | per result: set the address modes for its kind (elementwise or matmul; one kernel can mix them), `SEMWAIT` for a free Dst half, aim at it (`SETC16 MATH_Offset` = 0 or 64), zero it if the op accumulates (`ZEROACC` four 16-row blocks); the FPU program (one per matmul step); at the end: wait for the FPU, `SEMPOST` SEM_DST |
| 2 | pack | `SEMWAIT` SEM_DST, aim the packer at the Dst half (ADC ch0 Y) and the L1 slot (ADC ch1 Y), 16 `PACR`, wait for the packer, `SEMGET` SEM_DST, `SEMPOST` SEM_L1 (an intermediate) or SEM_PACKED (an output) |

Handoffs:

- **Unpack to math**: SrcA and SrcB have two banks each, and the hardware does the rest (`UNPACR` waits for a bank the FPU has released, the FPU for one the unpacker has filled).
- **Math to pack**: SEM_DST counts results in Dst waiting to be packed (max 2, one per half). Math waits while both halves are full, pack while none is.
- **Pack to unpack** (fused chains): an intermediate is packed into L1 and unpacked by a later op. Pack posts SEM_L1 for each; before an op that reads an intermediate, unpack takes one for every op packed since it last looked. Packs happen in op order, so that covers whichever earlier op it reads (a plain count would not: the op might read an older intermediate than the one just posted).
- **Between BRISC and the TRISCs**: words in `SYNC`, each written by one core and read with a `fence` first (the L0 data cache never sees another core's writes). BRISC cannot read semaphores, so TRISC0 and TRISC2 relay theirs: they read SEM_UNPACKED or SEM_PACKED (TRISCs see the semaphores at `0xFFE8_0020 + 4i`), take one with a store of 1, and bump a count in `SYNC`.

| word | written by | means |
|---|---|---|
| `FETCHED` | BRISC | fetches done (a frame, or a matmul step's pair); TRISC0 waits for the next before unpacking it |
| `UNPACKED` | TRISC0 | SEM_UNPACKED posts relayed; BRISC refills a slot once the tiles in it two uses ago are unpacked |
| `READY` | TRISC0 | config and semaphores set up |
| `PACKED`, `RING` | TRISC2 | results packed, and where each is (slot) and goes (tile), four entries |
| `SENT` | BRISC | results sent home; TRISC2 packs into an output slot only after its last result there is sent |

**Four programs, one schedule.** A kernel is a program per core, all four running the same loops over units, passes and tiles, each doing its own part of every tile:

- BRISC: wait until the frame's slots are free (`UNPACKED`), fetch the tile's inputs, bump `FETCHED`; for a matmul, the same per step through the stream slots. While it waits, it sends home whatever `PACKED` says is ready, in order, and bumps `SENT`. At the end, until all its results are sent.
- TRISC0: wait for `FETCHED` (relaying SEM_UNPACKED meanwhile), then the unpacks, `drain` before an op that reads an intermediate, and the report.
- TRISC1: the math, alternating Dst halves (it tracks `h` itself).
- TRISC2: the packs, tracking `h` the same way; for the result, first claim its output slot (`output`), then relay SEM_PACKED until every result is counted.

A result goes home as soon as it is packed, and the only waits between the cores are on data: a slot to be refilled, a tile to be unpacked, a result to be sent. No core waits for one that is waiting for it: every wait loop on BRISC also sends, and every one on TRISC0 or TRISC2 also relays.

**No push order to get right.** When BRISC fed all three threads through one stream of stores, a full FIFO stalled BRISC, so it could never queue work a thread would block on before pushing what unblocks it. With a TRISC per thread, a stalled TRISC holds up only its own thread, whose work waits on the others anyway.

**Replay buffers and address modes keep the pushes small.** Each TRISC pushes one instruction a cycle (four if they come in a row), so words per tile are its code and time per tile. Each thread has a 32-entry replay buffer (`REPLAY` with `load` records the next N instructions; without it, plays them back; it sits after the MOP expander, so it worked from BRISC too). Each kernel's setup records the runs that repeat: one 16-`MVMUL` fidelity phase and one 9-word `ELWMUL` phase in the math thread, 15 `PACR`s in the pack thread. The last instruction of a sequence that also has to release the Src banks is pushed by itself with `clear_dvalid`. Elementwise ops use address modes 0-1 and matmul 4-7, all set once at setup, so a kernel can mix them with no per-op rewrites. Blackhole's `addr_mode` field is 3 bits (bits 16:14 in ttsim's `tensix_isa.json`; the ISA pages are Wormhole's, with 2 bits plus an `ADDR_MOD_SET_Base` that Blackhole dropped). This needs confirming on silicon.

| words pushed, all three threads | before | now |
|---|---|---|
| add or sub tile | 48 | 26 |
| mul tile | 80 | 27 |
| matmul step | 71 | 12 |
| matmul output tile, on top of its steps | 39 | 17 |

What is left is per-tile control (slots, Dst half, semaphores). `test_replay_keeps_pushes_small` holds most of these numbers. A matmul test multiplies by a diagonal of full-mantissa values, so every output is one product that is exact only if all four fidelity phases ran; it catches a replay one instruction short.

**Replay budget.** The math thread's 32 entries are shared out per kernel: SFPU bodies first (32 replays a tile, longest first), then the matmul and mul phases (4). A run that does not fit is pushed by a loop on TRISC1 (`compiler.Loop`), still correct, just more pushes: the fp32-grade transcendentals (37 to 54 words) always go that way; reciprocal (12), sqrt (25), relu, the binary ops and the folds are replayed.

**ttsim's FIFOs.** ttsim executes one instruction per pipe per clock. A TRISC's `.ttinsn` stalls while its thread's FIFO holds more than 52 entries, like silicon's stall on a full FIFO; stores to `0xFFE4_0000` have no such check there (only what a replay records goes that way), and a 512-entry overflow kills the process. (When BRISC pushed everything, it had to pause after each `REPLAY` for this reason.)

**Only slots below 256 can be unpacked.** An unpacker's input address takes only the low 8 bits of its Z counter (ISA `ADCs.md`; ttsim agrees, its Z is 13 bits wide but the unpacker sees 8), so frames, row values and A's rows all sit below slot 256 (`UNPACKABLE`). A matmul whose row does not fit streams A through slots 3-4 instead. Two long matmuls in one kernel once wrapped past it and read the wrong tiles; it took a checker running every kernel of a GPT-2 forward against numpy to find.

**Matmul, one pair of tiles** (`compiler.matmul`). `MVMUL` does `Dst[8x16] += SrcB[8x16] @ SrcA[16x16]`: SrcB rows from its row counter (a multiple of 8), SrcA rows from its counter (a multiple of 16 in ttsim), Dst rows from the instruction's `dst` field plus the Dst counter. So the left tile goes to SrcB (unpacker 1) and the right tile to SrcA (unpacker 0). Output face (i, j) = sum over k of left face (i, k) @ right face (k, j): 8 face products of 2 `MVMUL`s each, 16 per fidelity phase, 4 phases (SrcA gives 5 mantissa bits a phase, SrcB 7). The `dst` field carries the output rows; the Src counters walk in the order i, k, h (half), j, which needs only four address modes (slots 4-7): SrcA +16 rows (next j), SrcA -16 / SrcB +8 (next h), SrcA +16 / SrcB +8 (next k or i), and the same plus fidelity +1 at the end of a phase. Counters wrap at 64, so that last step lands back on row 0. The last `MVMUL` of the last phase gives both banks back to the unpackers.

**Matmul, whole tensors.** A matmul is an op in a fused kernel (alone, it is a one-op kernel). Each worker owns some output tiles; each is K steps through the pipeline: the left (i, k) and right (k, j) tiles, 64 `MVMUL`s into the same Dst half, which accumulates over k in fp32; then one pack. Error on random bf16 inputs is under 2^-8 of sum |a*b| (1.4e-3 measured on 64x96 @ 96x128).

**A's row stays in L1.** Each matmul in a kernel has a row of slots for A's tiles (K of them, after the row values). A worker's result tiles run along rows, so while they stay in row i only B's tiles are fetched; A's row comes in with the steps of the first tile in a new row (`fresh`, after everything so far is unpacked, which matters only when K is one tile: otherwise the wait for B's slot two steps back already covers it, and ttsim never shows the difference). Unpacker 1 walks the row by itself: the matmul sets its Z to the row's first slot once, and each step's `UNPACR` adds 1 (`AddrMode` bits 0-1, Ch0ZInc). That halves DRAM reads for a matmul with one row of tiles, which is every matmul of GPT-2 decoding a short prompt: each weight tile is read once a token.

**Blocks.** With one matmul and no row passes, a unit is a block of up to 4 x 4 result tiles, done column by column: the block's rows of A and its current column of B stay in L1, unpacker 1 walking A's row (its start worked out at run time and pushed with a store, since it depends on the row) and unpacker 0 walking B's column. Each A and B tile is read once a block rather than once a result tile. Part-blocks at the edges leave out the tiles past the matrix (`test_matmul_blocks` puts a canary after the result). The benchmark's DRAM reads went from 14.9 to 6.9 times its inputs; what was left took sharing tiles between workers (below).

**Tiles shared between workers** (`Runtime.grid`, `test_matmul_multicast`). Blocks were already as good as blocks get: the benchmark's 96 workers each computed 16 result tiles from 4 rows of A and 4 columns of B, the fewest reads for 16 tiles, so DRAM reads could only fall by workers sharing what they read. The workers are a grid of whole NoC rows (9 rows of 12 of ttsim's 120 cores; the dispatcher's row is short and sits out), and a matmul of more than one row of tiles, unbatched, alone in its kernel but for elementwise ops after it, gives worker (gy, gx) one block of the result cut to the grid (blocks of rows/9 by columns/12 tiles, rounded up, so as many workers are busy as the result allows). Each worker of a grid row reads its share of the block row's rows of A from DRAM and multicasts it along the row; each worker of a grid column reads its share of each of the column's columns of B in turn and multicasts it down the column, into one of three buffers. After every recipient has acknowledged a share comes its sender's flag (`FLAGS`, a word for each worker of a grid row, then of a grid column), multicast the same way and counting the shares that worker has sent, and each worker zeroes its own flags at the end of the kernel (it has seen every flag of the launch by then, and none is written before the next go; a new Runtime zeroes them too); a worker waits for every flag of a column before computing it. Three buffers need no message to say one is free: a worker posts its share of column c only once its own unpacker is done with column c - 2, and a worker writing column c has seen every share of column c - 1, so every other worker is done with column c - 3, whose buffer c reuses. (A leader per row and column reading everything was the first version: "Cutting the critical path".) A multicast leaves the NIU's outstanding count wrong (up once, down once a recipient), so BRISC waits for everything else first and clears the count after, as the dispatcher does. The unpackers walk the same slots as before; when three buffers do not fit below slot 256 with the rows of A, the matmul keeps blocks. The benchmark: DRAM reads 6.9 to 1.0 times its inputs, 17k cycles to 9k (steps whose tiles are already in L1 no longer wait on a fetch); 128x768 @ 768x768, which 4 x 4 blocks put on 6 workers, 17k to 2.3k on 48. tinygrad's transformer step went from 2.86M cycles to 2.58M, ferrite's training step from 845k to 766k (both measured polling every 1000 cycles: "How ttsim counts"). One-row matmuls (a token's) share only A, their one row ("A token's row, shared", below). With the reads shared out and cheaper (below), the benchmark is 1.7k cycles, 128x768 @ 768x768 1.0k, 64x768 @ 768x3072 1.5k.

**Split K.** A unit is at least a result tile, so a matmul with few of them leaves workers idle however long K is: a token's MLP down-projection, (5 x 3072) @ (3072 x 768), is 24 result tiles of 96 steps each, on 24 of 119 workers. When an unbatched matmul's result tiles times s still fit on the workers and each part keeps at least 4 K tiles, `@` cuts K into s parts (2, 4 or 8; `split` of A's columns and B's rows, views, no copy), multiplies them as a batch, and sums the parts lazily, so the sum fuses with what comes after (the bias, the residual). The down-projection becomes 96 units of 24 steps, 8000 cycles to 3000, and a token 371k cycles to 312k. Each part is rounded to bf16 before the sum, one more rounding than Dst's fp32 sum over all of K; GPT-2 still picks numpy's token 8 times out of 8. On silicon it also spreads the weights' DRAM reads over four times the cores.

**Matmul precision.** A product of bf16s is exact after four fidelity phases and Dst sums in fp32, but the FPU adds each group of 8 products after aligning them to the largest at 12 bits (ttsim's model, `mvmul`), so a matmul is good to about 2^-12 of its larger terms, whatever Dst holds. Rounded to bf16 (2^-8) that never showed; written as fp32 it does: 1.6e-4 relative on 64 x 96 @ 96 x 70. An fp32 matmul goes as bf16x3 (each operand hi + lo, both bf16; hi@hi + hi@lo + lo@hi summed in fp32), which reaches that limit rather than bf16's 4e-3 rounding of the operands. More would take the SFPU, or splitting the dot products so they do not share an exponent.

**Fewer fidelity phases** (`matmul(fidelity=)`, `tensor.FIDELITY`, `test_matmul_fidelity`). A phase multiplies 7 of A's 8 significand bits (SrcB: its top 7, or its last) by 5 of B's (SrcA: its top 5, or its last 3) (ISA `SrcASrcB.md`, `SrcAFidelityBits`); ferrite runs them in order 0-3 (top by top, top by B's last, A's last by top, last by last), and `SETRWC` puts every step back at phase 0, so a matmul can stop after any of them. Three leave out under 2^-11 of a product, two drop A's last bit (a truncation, toward zero, of up to 2^-7), one keeps 5 bits of B. Rounded to bf16, on random 128 x 768 @ 768 x 256: three phases are four's to the bit in error (worst 1.0e-3 of the sum of |products|, mean 1.0e-4); two give a worst 1.45e-3, mean 1.9e-4; one 6e-3 and, with all products positive, a 1.9% bias. GPT-2 at two and three phases keeps its logits within the 1.5 of numpy's it has at four (picking ' to' for ' not' at every count, a tie at -95.0 in bf16 either way); SmolLM at two picks numpy's 6 tokens out of 6 with logits within 0.54 (0.61 at four). Four stays the default (exact products, as `test_matmul_exact` wants); fp32's bf16x3 matmuls always take four. On ttsim fewer phases cost the same (it runs queued `MVMUL`s at no cost); on silicon each phase is one `MVMUL` a 16 x 16 block, so two phases should double a matmul's math rate, which waits for the card to measure.

**Weights in BFP8** (`cast("bfp8")`, `test_bfp8`). A token reads every weight once, so on silicon decode waits on DRAM, and a bfp8 tile is 1088 bytes where bf16's is 2048: 64 exponent bytes, one for each run of 16 values (a face's row), then 1024 bytes of a sign and 7 bits of magnitude, a value being `magnitude * 2^(exponent - 133)`. What ttsim does (`tensix.cpp`), and so ferrite:

- The cast is the packer's: `Pack_out_format` BFP8 (6), `Exp_section_size` (config word 68, bits 16-31, in 16-byte units) 4. From an fp32 `Pack_in_format` it cuts each value to bf16 and rounds it once, half up, to its run's largest exponent; from a bfp8 one it first rounds to 6 bits, then again (221 values of 6,144 off from rounding once, on a test matrix). So a cast to bfp8 packs from fp32, the packer reading Dst 64 bytes a row, and matches a numpy model to the bit.
- The unpacker makes each value the bf16 it is (7 bits fit in bf16's 8) on its way into SrcA, and MVMUL multiplies it like any other. Its out format must say bfp8 too. It finds slot z's exponents at `base + 64 z` and its values after an exponent section as long as the tile descriptor's Z dimension makes it (64 bytes a slot), at `+ 1024 z`, so bfp8 tiles cannot sit in the 2 KiB slots: a matmul's bfp8 B gets a region of its own past slot 255 (`B8`), exponents first, BRISC reading each tile there in two pieces (`get8`), two slots to stream through or a block's whole column. Thread 0 switches unpacker 0 to that region and format for the matmul's steps and back after (`bfp8_b`: format, out format, Z dimension and base, each written a byte at a time with `RMWCIB` between `STALLWAIT`s, as `haloize` switches the transpose), so what follows the matmul in the kernel unpacks bf16 as before: a bias add, gelu, another matmul.
- A matmul by a bfp8 B is bit for bit the bf16 matmul by the same values, whichever way B comes in (streamed beside A, with A's row kept, a block's column kept, K split); not yet by multicast. With their matrices in bfp8 (the blocks' and the output layer, numpy given the same values; `test/gpt2.py ... bfp8`), GPT-2 picks numpy's token 8 times of 8, logits within 1.22, and SmolLM 6 of 6 within 0.75, each writing the same text as with bf16 weights.
- A GPT-2 token reads 131 MB of weights where bf16 reads 247 MB. On ttsim it takes the same 126 launches and 134k cycles to bf16's 111k: a bfp8 matmul costs about 30% more cycles (1x768 @ 768x2304: 2.06k to 1.59k), about 20 a step, BRISC's second read (fused with nothing at first, the bias adds made it 150 launches and 139k). That is RISC-V work, which is all ttsim counts; on silicon a worker's share of DRAM bandwidth takes about 250 ns for a tile, and the two reads issue in a few.
- Left for the card: whether silicon finds bfp8 slots where ttsim does, and what decode gains.

**Reads in flight** (`DEPTH`). A matmul step's tiles came in one at a time: BRISC read B's tile (and A's, if new), waited for the NoC to go quiet (`noc_wait`), told thread 0, and only then read the next, so each worker had one read in flight. On silicon a DRAM read is long next to the step it feeds (a worker's share of the card's bandwidth moves a 2 KiB tile in about 500 ns, and latency comes on top), so decode would wait on latency rather than bandwidth. Now step k's reads carry NoC transaction ID k % 4 + 1 (the packet tag's bits 10-13; ISA `NoC/Counters.md`) and B streams through 4 slots (A, when it streams, through 4 more). BRISC issues a step's reads as soon as its slot is free and counts the step in `ISSUED`; thread 0's TRISC, which waits for the step anyway, then waits for that ID's `NIU_MST_REQS_OUTSTANDING_ID` to reach 0, which the NIU decrements as each read's data lands in L1 (every core of the tile may read the NoC's registers). So up to 4 steps' reads are in flight a worker. The ordering this relies on (ISA `MemoryOrdering.md`): BRISC reads initiator 1's `CMD` back and fences before it bumps `ISSUED`, so the NIU has counted the reads first, and thread 0 reads the counter only after seeing `ISSUED` (its loop's branch orders the two loads). A frame's reads keep ID 0 (`noc_wait`). The first version had BRISC wait on the IDs and tell thread 0 of each step, about 30 more RISC-V instructions a step on BRISC, the critical path (a GPT-2 token 111k cycles to 147k); with thread 0 waiting, a token is 114k (bfp8 weights 134k to 136k) and the benchmark, whose shares are already read together, is unchanged. On ttsim reads land at once, so the depth itself changes nothing there.

**A token's row, shared** (`bcast`, `test_matmul_multicast`). A matmul of one row of tiles (a token, or a few) gave each worker result tiles of its own, and each read A's whole row for them: as many tiles as its share of B, so a token read its activations from DRAM as often as its weights (`ferrite.bench 1 768 3072`: 2.0 times the inputs). Now, given the grid, each worker takes a block of the result's columns, and the first grid row reads A's tiles in shares and multicasts them to every worker, flagging each share as the multicast matmul does (FLAGS); B, whose tiles no two workers share, streams through the DEPTH slots as before, behind one wait for A. A batch (K split in parts, for few result tiles) gives each matrix whole grid rows of its own, its blocks padded out to them, and its first row shares its part of A. The decode benchmark reads 1.0 times its inputs; a GPT-2 token's DRAM reads went from 222.8k tiles to 139.0k (its weights are 120.6k), and on ttsim from 114k cycles to 72k (bfp8 weights 136k to 115k): with A in L1 before the first step and B's reads ahead of the unpacker, the Tensix pipes rarely wait, and ttsim counts only the clocks they do.

**Fusion** (`fused_kernel`, `Tensor` is lazy). `+`, `-`, `*` and `@` build a tree; `realize` (or `tolist`) compiles the whole tree into one kernel, so `(a @ b) * d - c` or `(a @ b) + (e @ f)` is one launch. A matmul's own operands are realized first: each of its output tiles needs a whole row and column of them. Equal subtrees become one op. Slot 0 is the runtime's zero tile, slots 1-4 stream matmul tiles; per output tile, a frame of slots holds the elementwise inputs, then one slot per op in post order; the last is the result. BRISC fetches the inputs into the frame; then, op by op, an elementwise op is unpacked from its operands' slots, computed into the next Dst half and packed into its own slot, or a matmul runs its K steps (each: BRISC waits until the stream slots from two steps back are unpacked and fetches B(k, j), and A(i, k) unless A's row is in L1 already; unpack; MVMULs) and is packed. Intermediates live in L1 only, and only the result goes to DRAM. Two frames alternate, so tile n + 1 is fetched while tile n computes, and results go home while both happen. Every intermediate is rounded to bf16 on its way to L1, exactly as it would be on its way to DRAM, so a fused chain is bit for bit the same as one launch per op (`test_fusion` checks). A single op is just a one-op chain. Limits: matmuls only over realized tensors (no fused prologue), and at most 15 ops (below).

**Too big for one kernel.** A kernel holds at most 15 ops (SEM_L1 is 4 bits); a sum of 12 heads alone is 23. `realize` counts the ops a kernel would get and, while there are too many, goes down the operand with the most and realizes the first part that fits, on its own.

**The SFPU: tinygrad's elementwise primitives** (`compiler.SFPU`). A 32-lane fp32 vector unit that works on Dst, issued from the math thread right after the FPU, over the same Dst half. Facts (ISA `VectorUnit.md`, `SFPLOAD.md` and the per-instruction pages; ttsim `tensix.cpp`):

- LRegs 0-7 are writable; 8 = 0.8373, 9 = 0.0, 10 = 1.0, 11 = -1.0 are constants. Writing 12-15 configures load macros instead of computing, so never use them as a destination.
- An `SFPLOAD`/`SFPSTORE` moves 4 Dst rows x 8 columns (even columns at address 4r, odd at 4r + 2). So 32 of them cover a tile, and the address is the instruction's immediate plus the Dst counter plus the math thread's `MATH_Offset`. With fp32 Dst use mod0 3; the 16-bit modes address raw rows.
- We load with address mode 2 (no step) and store with 3 (Dst counter + 2), so one body repeated 32 times walks the tile, and it is recorded in the replay buffer.
- `SFPMAD` is a fused multiply-add with one rounding; denormals flush to zero in and out. Blackhole stalls for the 2-cycle MAD latency by itself (Wormhole needed `SFPNOP`s), with listed exceptions none of our programs hit.
- `SFPSWAP` mod 1 leaves the min in vd and the max in vc. `SFPARECIP` (Blackhole only) is a reciprocal estimate within 0.6%: inf for 0 and denormals, 0 above 2^126. There is no exp instruction in ttsim (`SFPARECIP` mode 2 is rejected).
- Condition codes are shared by all threads: `SFPENCC` mod 10 imm 3 turns lane flags on with all lanes set, mod 0 sets them all again, mod 10 imm 2 turns them off. `SFPIADD` with an immediate narrows the enabled lanes (mod 1: where the sum is negative, mod 9: where it is not), `SFPSETCC` mod 0 sets them where a value's sign is set, and while flags are on every instruction writes only enabled lanes, `SFPLOADI` included, so a constant loaded then is a conditional assignment.
- `SFPGT` mod 8 (Blackhole only) writes all ones where vd > vc as ordered floats (sign and magnitude, so -0 < 0) and 0 elsewhere, a mask for `SFPAND`, `SFPOR`, `SFPNOT`. `SFPEXEXP` mod 1 gives the biased exponent as an integer, `SFPSETEXP` mod 1 replaces the exponent with an immediate, `SFPCAST` mod 0 turns a sign-and-magnitude integer into a float. `SFPMAD` rounds to nearest even (ttsim's model, Blackhole), so adding and taking away 1.5 2^23 rounds to an integer, and x * 1 + 0 turns -0 into 0.

The programs are tinygrad's elementwise primitives: exp2, log2, sin, sqrt and reciprocal; max, cmplt and cmpne; where. Everything else in `Tensor` is built from them, as in tinygrad (`minimum` is `-max(-x, -y)`, `rsqrt` is `sqrt().reciprocal()`, `==` is `1 - (x != y)`), except that exp, log and cos are programs of their own. Their constants (log2(e), ln 2, a quarter turn) stay in fp32 inside the program; as numbers they would be bf16 tensors, and exp(10) as `exp2(10 * log2(e))` with log2(e) rounded to 8 bits is 2% off.

Each transcendental reduces x to a small range by exact steps, then a polynomial (fit offline toward minimax, coefficients as fp32 literals) does the rest, so fp32 tensors get fp32's accuracy: within a step or two of numpy's float32 (2^-23 is 1.2e-7), checked in `test_fp32`. Over the whole fp32 range:

| program | error | at |
|---|---|---|
| exp2, exp | 8e-8 relative | x in [-126, 128], [-87, 88.5] |
| log2, log | 9e-8, 1.6e-7 relative | x from 1e-35 to 1e35, and near 1 |
| sin, cos | 1.0e-7, 1.6e-7 absolute | \|x\| up to 200; 3e-10 and 3e-8 within 1e-3 of a zero |

- **exp2, exp**: n = round(t), t = x or x log2(e) (adding and taking away 1.5 2^23 rounds to an integer and leaves it in the sum's low bits, where an integer subtract reads it), r = (x - n) ln 2, or for e^x x - n ln 2 in two parts (Cody-Waite: n times 0.693359375, 9 bits, is exact), e^r by 7 coefficients on [-ln2/2, ln2/2], then times 2^floor(n/2) and 2^ceil(n/2), each built from its exponent bits. Two multiplies, not adding n to the exponent: they overflow to inf and flush to 0 exactly where the result does (2^127.5 is finite though n is 128). x is first held to |t| <= 150. The old way, `(e^(x/4096))^4096` by a Taylor series and 12 squarings, was 4e-4: each squaring doubles fp32's rounding.
- **log2, log**: x = 2^e m, m in [1, 2) (`SFPEXEXP`, `SFPCAST`, `SFPSETEXP`), halved where above sqrt 2 with e one more (`SFPGT` sets the lanes), so u = m - 1 is in [-0.29, 0.41] and `log2(x) = e + u q(u)`, q of 9 coefficients, relative, so log2 near 1 keeps its digits (just below 1 there is no cancellation of e = -1 against log2(m) near 1). Times ln 2 for log. Edges by lane flags: inf and NaN give themselves, negatives NaN, zero -inf.
- **sin, cos**: k = round(x / pi + phase), phase 1/2 for cos, r = x - k pi in two parts (3.140625, 8 bits, then the rest; what is left of x is within a factor of 2 of it, so exact), plus pi/2 in two for cos: r is in [-pi/2, pi/2], `sin(r) = r p(r^2)` by 5 coefficients, and k's low bit, shifted to the sign and `SFPXOR`ed in, gives (-1)^k. A first try reduced in turns (f = x / (2 pi) - n, folded into [-1/4, 1/4] by 1/2 - f) and lost digits at the fold: f near 1/2 carries 0.5's rounding, 3e-8, into a small result, 3e-7 after times 2 pi. An fp32 model of the program, matching the device to 6e-8, showed the loss was the algorithm's. From |x| = 2^24 on, an fp32 x is a whole number and the rounding trick fails: 0 there; inf and NaN give NaN.
- **sqrt**: x + 0 (so -0 is 0), the bit trick `0x5F3759DF - bits(x) / 2` for 1/sqrt(x) (within 3.5%), two Newton steps `y *= 1.5 - x/2 * y^2`, times x. Edges: 0 (where the Newton steps would overflow), inf and NaN give themselves, negatives NaN.
- **reciprocal**: the `SFPARECIP` estimate and two Newton steps `y += y(1 - xy)`, only in lanes where x is a normal number. 0 and inf would make `0 * inf = NaN`, so those lanes keep the estimate (inf and 0). A NaN comes out 0, so `rsqrt` of a negative number is 0, not NaN.
- **relu**: `max(x, 0)` with one `SFPSWAP` against 0.
- **max, cmplt, cmpne** take two operands, which the SFPU only sees in Dst: the unpacker and FPU put x + 0 in the op's Dst half and y + 0 128 rows on (the reductions' scratch place), and the program loads both and stores over x. `SFPSWAP` gives the max; a comparison is an `SFPGT` mask (both orders, ORed, for cmpne) ANDed with 1.0's bits, after x + 0 has made -0 into 0.
- **where** has a third operand and Dst has no room for one (fp32 Dst is 512 rows, and the halves, the scratch and the accumulators fill them), so `c.where(x, y)` is `keep(c, x) + drop(c, y)`: two binary programs that AND x, or y, with the mask `|c| > 0` (or its complement), and an add. Each pick is exact and the add has a zero on one side, so `where` is exact, and an inf in the side not picked does not turn into a NaN as `c * x` would. A masked softmax can use -inf (`test_elementwise`).

Packing to bf16 turns NaN into inf, so a NaN reads back as inf. `test_sfpu` and `test_elementwise` feed ±inf, ±0, a denormal and ±1e30 to every program, and compare comparisons and picks with numpy exactly.

**Where a unary op runs.** In place, on the Dst result of the op below it, if nothing else reads that result (`relu(a @ b + c)` is one op with two SFPU programs after it). Otherwise its operand goes through `x + 0` (slot 0 is the runtime's zero tile) into Dst first. In place it sees the fp32 result, not one rounded to bf16, so it can be more accurate than op by op: `exp(x + y)` fused is `exp` of the fp32 sum.

**gelu** is GPT-2's tanh form, built from what is there: `0.5 x (1 + tanh(z))` is `x / (1 + e^(-2z))`, so `x * (1 + exp(x (-k c x^2 - k))).reciprocal()` with `k = 2 sqrt(2/pi)`, `c = 0.044715`. One kernel; within 2% of numpy after the bf16 rounding of each step.

**Reductions** (`sum(axis)`, `max(axis)`, numpy's with the axis kept as 1; `reduce_step`, `ACROSS`, `MASK`, `COMBINE`). Axis 0 folds the batch into one matrix, axis 1 the rows into one row, axis 2 each row into one column. Each tile along the axis is unpacked beside the zero tile and added to zero into Dst. (BRISC used to zero that tile at the start of every such kernel: 512 stores, 1200 cycles, more than a one-tile reduction's whole work. Now the runtime keeps one in every worker, and a GPT-2 token went from 282k cycles to 195k.) The first goes into an accumulator (Dst rows 256-319, or 320-383 for a second reduction in the same pass). Each later one goes 128 rows further on, where an SFPU pass folds it in: load both, `SFPSWAP` for max or a multiply-add by 1.0 for sum, store; 32 passes of 4 words, replayed. The line's last tile is masked first if it is cut short (`MASK`: `mask_columns` for axis 2, `mask_rows` for axis 1; the batch has no padding).

At the end of the line, the accumulator is folded inside the tile (`ACROSS`), so the result fills its tile and broadcasts as it is:

- **Along each row** (`across_rows`): row r sits in Dst rows `(r // 16) * 32 + r % 16` (columns 0-15) and 16 rows on (16-31), so four `SFPLOAD`s (even and odd columns, both faces) hold 4 rows, a row per 8-lane group. After folding those four, `SFPSHFT2` mod 3 rotates each group by one lane; rotating by 1, 2 and 4 and folding each time leaves the row's result in all 8 lanes, which goes back to all four places. 8 groups of 21 words, pushed directly since the addresses differ.
- **Down each column** (`across_cols`): column c is one lane of the loads at the even or odd addresses of its two faces, a row of it in each 8-lane group, so 8 loads fold to one register holding four partial results, one per group. `SFPSHFT2` cannot cross groups; `SFPTRANSP` (ISA `SFPTRANSP.md`, ttsim `tensix.cpp`) treats LRegs 0-3 as a 4 x 4 of lane groups and transposes it, so three copies and one `SFPTRANSP` put each group across a register of its own, and folding the four leaves the column's result in every lane, which goes back to all 8 places. 4 runs of 30 words.
- **Through the batch**: nothing; the tiles were folded as they came.

Each accumulator has a semaphore (1 while free): the first step of a line takes it, and the pack gives it back, so the next line cannot overwrite an accumulator still being packed. Sums are fp32 throughout, rounded once. `test_reductions`, `test_reduce_axes` (exact maxes of all-negative values with the last tile cut short, so the masks are tested), and `test_fuzz`, which draws the axis at random.

**Lines in passes, one launch** (`fused_kernel`). If an expression reduces, a work unit is a whole line of tiles along the axis (a row of tiles, a column of them, or one tile position through the batch) and each worker owns lines; otherwise a unit is one tile (or, with one matmul, a block of them: "Blocks" above). A line is done in passes, each a sweep along it. A reduction's result is readable only in the pass after the one that swept its operand, and each pass recomputes the values it needs rather than keep whole lines of them in L1. Inputs come from DRAM once: one read in more than one pass keeps its line of tiles in L1 from the first (while the line fits below slot 256), and one a tile long along the axis (a constant, a row's scale) gets a slot of its own, fetched once a line; BRISC refills a kept slot for the next line once the line before's last read of it is unpacked. The unpackers find a kept tile by its place along the line, so its slot is worked out at run time: a `SETADC` stored with the slot added, as for a matmul's row of A. A kernel reduces along one axis: `_tree` takes the first reduction's, and a reduction along another axis is computed first, on its own, as is an op that is 1 along an axis the kernel keeps (it would repeat there).

So `realize` works some of it out first, on its own: a long matmul (K over 256), and an elementwise value that a reduction reads and something else reads too (a layer norm's input). The second matters when there are few rows: GPT-2's residual stream is a lazy sum of 14 terms by the time a layer norm reads it, which with the norm is more than one kernel holds; split by the 15-op rule into 3 or 4 kernels of one row unit each, all of it ran on one worker, three passes over. Realized first, the sum runs a tile per worker, and the norm is one kernel: a layer is the 11 launches it should be, and a token went from 195k cycles to 170k.

softmax `e * e.sum(2).reciprocal()` with `e = (x - x.max(2)).exp()` is three passes in one launch:

1. Sweep x into the row max.
2. Compute e tile by tile and sweep it into the row sum; the reciprocal runs in place on the accumulator.
3. Recompute e and multiply by the reciprocal.

Values one tile long along the axis (reduction results, ops on them like `x.sum(2) * (1/n)`, inputs of 1 there) are computed once per line, in the first tile of the pass that needs them, into slots of their own after the two frames.

Book-keeping happens at run time, in each program, because what a tile does depends on whether it is a pass's first or last:

- Which Dst half each op gets (TRISC1 and TRISC2, each counting the same way).
- How many `SEM_L1` posts an unpack must take before reading an intermediate (TRISC0 takes all packed so far: `drain`).
- Which frame or stream slot is free again (BRISC, counting thread 0's reports the way TRISC0 pushes them).

**Softmax and layer norm** (`Tensor.softmax`, `layernorm`; `test_softmax_and_layernorm`) are built from these:

- softmax: `e = (x - x.max(axis)).exp(); e * e.sum(axis).reciprocal()`
- layer norm: `d = x - x.mean(axis); d * ((d * d).mean(axis) + eps).rsqrt() * gamma + beta`, with `mean` a sum times `1/n`

Each is one launch; they match float64 to about 2% (softmax) and 0.05 + 2% (layer norm), the bf16 rounding of each intermediate. With inputs kept (above), a 64 x 768 softmax reads x once rather than three times, and a layer norm once rather than six (three passes, and its three constants, 1/n twice and eps, fetched for every tile): 288 reads to 54, 2.6k cycles to 0.6k (0.42k since, with cheaper NoC requests and launches). Each half alone took it to 1.9k or 1.15k: on ttsim every fetch costs BRISC instructions on the critical path ("How ttsim counts").

**Any shape** (`Tensor`, `fused_kernel(shapes=...)` takes each input's (batch, rows, columns)). A tensor is padded to whole tiles, and the padding has one rule: zeros, except that a dimension of 1 fills its tile with copies (a row vector's tile holds the row in all 32 rows, a column's in all 32 columns, a scalar's everywhere). Uploads follow it, and so does every kernel's result:

- **Results go home tidy.** In a tile at the result's last row or column, the math thread zeroes the padding in Dst before the pack (`mask_columns` with 0, `mask_rows`: SFPU stores into the lanes past the edge, picked as below). Inside a kernel the padding is whatever the ops made of it (`exp(0)` is 1); in DRAM it is zero, so a matmul can sum over a padded K: zero columns of A meet zero rows of B. (Multiplying by a 0/1 mask instead would not do: an inf in the padding times 0 is NaN.) A dimension of 1 stays filled by itself: an op on filled tiles gives filled tiles, a row reduction writes all 32 columns, and a matmul with a filled B gives a filled result. This first ran on BRISC, a store per padding datum before the send: 5000 cycles a tile, 129k for a 16-row layer norm. On the SFPU it is a few dozen instructions.
- **Reductions mask their last tile.** Padding would count in a sum, and with all values negative a padding 0 would win a max. After the last tile of a line lands in Dst, an SFPU pass (`mask_columns`, or `mask_rows` down the columns) stores the identity (0, or -inf for max) into the columns past the edge. Which columns an `SFPSTORE` lane holds is fixed (lane l of a store at an even or odd address: column 2 (l % 8) or one more, plus 16 in the right faces), and `LReg[15]` holds 2l in every lane (ISA `LReg.md`; ttsim agrees), so `LReg[15] & 14` compared with the first padded column (`SFPIADD` with an immediate, flags on) enables exactly the padded lanes, and the store only writes enabled lanes. 32 stores at most, only in a row's last tile.
- **Broadcasting is numpy's**: shapes match, or one side has 1 where the other does not; a number is a 1 x 1 tensor. It is tile reuse, not a hardware broadcast: the fetch for output tile (i, j) takes the 1-wide input's tile (i, 0), (0, j) or (0, 0), and the filling makes that tile right everywhere. A computed operand one tile wide stays in the expression and is worked out once per row; one with a single row (repeated down) is realized first in its own kernel. `sum(2)` and `max(2)` give a column (rows x 1), `sum(1)` and `max(1)` a row; along an axis that is already 1 they are the tensor itself (32 copies would add up). `(R, 1) @ (1, C)` is broadcasting, not a matmul (a filled K would add up 32 times).

Bug found on the way: a row reduction whose operand is one tile wide inside a wider kernel was swept like a wide one, adding the same tile once per column tile. It is now reduced in the pass's first tile; `test_any_shape` covers it (and caught the old code).

**A batch dimension** (`Tensor(..., batch=)`, `shape` is (batch, rows, cols)). A batch is its matrices one after another in DRAM; a batch of 1 repeats across a bigger one (broadcasting, as numpy's leading dimension). Kernels take each input as address and tile strides for batch and row plus an offset, and units run through the batch. Elementwise ops, row reductions and matmul (matrix by matrix, or by one matrix for all) all work on batches. Views: `x[b]` is one matrix, and `x.split(n, axis)` cuts a matrix into a batch of n in place, which is how attention's heads become a batch: `test_batch`, and GPT-2's attention is two batched kernels (scores with softmax, then times the values, merged back side by side) instead of a loop over twelve heads.

**Results into views** (`realize(into)`, `merge`). A fused kernel takes its result's address and strides the way it takes each input's, so it can write into a view of another tensor: `x.merge()`, the inverse of `split`, realizes a batch into the column blocks of one matrix, and the realized batch becomes a view of it. Attention's heads come back side by side this way, with no copy.

**Views** (`x[b]`, `x[rows, cols]` or `x[batch, rows, cols]` with step-1 slices on tile boundaries, `split`). A view shares its owner's DRAM: tile (b, i, j) of the view is tile `b * bstride + i * stride + j + offset` of the owner's, and every kernel takes each input as (address, batch stride, row stride, offset), so views go straight into kernels with no copy. The view keeps its owner alive, and only the owner frees. A view ends on a tile boundary or at the tensor's end, so its padding follows the rule too; any other slice is a move (below). GPT-2's q, k and v are views of one qkv result, split into heads by `split`.

**Transpose** (`x.T`, `transpose_kernel`). Result tile (i, j) is input tile (j, i) transposed. BRISC fetches the tile face by face with the two off-diagonal faces swapped (four 512-byte NoC reads), and unpacker 0 transposes each 16x16 face on its way into SrcA (`Haloize_mode`, backend config word 72 bit 8; ISA `UNPACR_Regular.md` swaps the row's low 4 bits with the column; unpacker 1 ignores it). Then `x + 0` through the FPU, which is exact. `.T` is lazy: a matmul whose B is a transpose reads it that way itself, fetching each tile flipped and turning `Haloize_mode` on for unpacker 0 around its K loop, which unpacks only B (`haloize`: a `STALLWAIT` that holds the config unit until unpacker 0 has finished, `RMWCIB1` on byte 1 of word 72, a `STALLWAIT` that holds the next unpack until the config unit has). Anything else realizes it with the transpose kernel, whose config has the bit on throughout (bf16: an fp32 or int32 transpose is a move). Reading transposed costs four quarter-tile reads a tile, so a weight read every token is transposed once instead (`wte.T`: read transposed, the logits took 39k cycles rather than 17.6k). GPT-2's attention reads its keys transposed, with no transpose kernel: a token went from 138 launches and 143k cycles to 126 and 140k. Breaking `haloize` fails `test_batch`.

**Movement at any granularity** (`reshape`, `permute`, `expand`, `pad`, slices at any offset and step, numpy's; `Tensor._move`, `Tensor._map`, `move_kernel`). Each is one map from the result's elements to the source's: element (b, r, c) of the result is element `offset + b sb + r sr + c sc` of the source counted in row-major order, inside per-axis bounds `lo <= . < hi`, and 0 outside. A permute permutes the strides, an expand sets a stride to 0, a slice moves the offset and multiplies the strides by the steps (negative ones too), a pad moves the offset back and sets the bounds, and a reshape reads the source in order. Swapping rows and columns of bf16 stays the Tensix transpose above, and slices of whole tiles stay views.

The kernel is BRISC alone, since a NoC read cannot put 2 bytes just anywhere. It loads and stores 2 bytes at a time in L1, which ttsim allows and silicon should (rv32im has them; bring-up step 4), and fetches source tiles whole into a cache in L1 as it needs them (127 slots, by tile number mod a prime so that power-of-two strides spread out). A result tile that is a source tile as it is (a pad, slice or cat on tile boundaries) comes by one NoC read, 250 ttsim cycles; one that is a source tile transposed (`.T` of fp32 or int32) is copied face by face, the off-diagonal faces swapped, 2.5k. Any other starts as a NoC copy of the runtime's zero tile, so padding and everything outside the bounds cost nothing, and takes the datums inside the bounds in lines along its rows or down its columns, whichever lie in the source as runs (along a source row or down a source column), the longer if both: tinygrad's attention heads, (1, 384, 128) to (64, 128, 6), run 6 along a row and 32 down a column, 6k cycles a tile one way and 2.6k the other. A run is copied up to a face's edge by stepped pointers; a line that is not one steps through the source by its stride, split once into matrices, rows and columns, so no datum takes a division. A dimension of 1 fills its tile as the padding rule wants, so a moved tensor goes straight into any kernel: a column is made once and copied across, and a row is made once and doubled down the tile by NoC copies inside L1, as `gather` does (a single-row move went from 49k cycles to 3k, which a Llama decode step, all single rows, needed: "A Llama-family model"). It began at 40 cycles a datum, each found by two divisions and checked against the bounds with the arguments read from L1: removing the divisions saved 10%, and skipping what is outside the bounds and keeping arguments in registers took a mostly-padding permute on one worker from 2.3M cycles to 470k. Whole tiles, transposed tiles and runs then took the adapters' moves from 30-80k cycles each on every worker to 2-30k (an fp32 transpose of (384, 128) 51k to 3.4k, a pad on tile boundaries 50k to 1.5k, the heads 36k to 8.8k), tinygrad's transformer step from 6.1M cycles to 2.9M, and ferrite's own training step from 1.27M to 845k. A chain of moves is one launch: a permute, expand, pad or slice (`_map`) says for each axis of its result which axis of the source it reads, from where and by what step, so on a move not yet made it composes with that move's map, and the bounds pulled back through it bound the new move (a pad's zeros are the source's edges, pulled back). A reshape does not compose (unravelling an index is not affine), so it starts a move of its own. Convolution was the first user to need it ("A small CNN"). `test_movement`: fixed cases and random chains against numpy, bit for bit.

**fp32 tensors** (`dtype="fp32"`, `cast`, `float()`, `bfloat16()`; `test_fp32`). 4 KiB tiles, the same layout. SrcA and SrcB hold 19 bits, so fp32 cannot go through the FPU. In an fp32 kernel the math thread unpacks each operand straight into its own Dst half (`fill`: unpacker 0 in its second config context, which has unpacking to Dst on and which the math thread selects with its `UNPACK_MISC` thread config; the 32-bit Dst row is channel 1's Y at 64 bytes a row; that thread's `SRCA_SET` must be off), waits for the unpacker (`FILLED`), and the SFPU does every op, add, sub and mul included, each rounded once, so a fused fp32 tree is numpy's float32 exactly. Because the math thread owns its Dst half, filling it needs no new handshake: it waits for a free half, fills it and computes, in order. It also takes over the unpack thread's other duties in such a kernel (waiting for BRISC's fetches, draining SEM_L1, reporting frames); the unpack thread only relays the reports to BRISC.

- **One dtype a kernel.** bf16 cannot be unpacked into Dst (ttsim does not model it) and fp32 cannot go into SrcA whole, so a kernel computes in one dtype: its inputs and slots are of it (slots one tile of it apart, since the unpackers' Z stride counts datums: `slot_base`). A binop of bf16 with fp32 casts the bf16 side first, as tinygrad does, and a number takes its tensor's dtype, so fp32 constants are exact (a mean of 768 values is exact in fp32, 0.2% off in bf16).
- **Casts, and matmuls written as fp32**, are kernels of one op that pack in another format, into two 4 KiB buffers at `OUTS` (the packer's base and slot stride are config). The packer's Dst row stride is in bytes of its source format, 64 for fp32 and 32 for bf16; with 32 it reads half rows and ttsim stops on a misaligned read port. Its modes: `Read_32b_data` with `Dstacc` = `Pack_in_format` = `Pack_out_format` = fp32 (0x100) or bf16 (0x155).
- **Movement and gather** move 4 bytes a value; an fp32 transpose is a move, since the unpacker transposes only on its way into SrcA. A matmul's fp32 operand that is a transpose is split into its bf16 parts first, and those transpose as bf16 does (read transposed as B, the tile transpose as A), so a matmul's backward, all A^T and B^T, moves nothing ("Training").
- **Not fp32-grade**: matmul ("Matmul precision", above).

**int32 tensors** (`dtype="int32"`; `test_int32`). Two's complement in DRAM and L1, and in Dst and the LRegs too: the unpacker (format 8, into Dst only), `SFPLOAD`, `SFPSTORE` in its INT32 mode and the packer (mode 0x188) move the bits as they are. `SFPSTORE`'s FP32 mode flushes denormals, which are the small positive integers, so everything that stores integers or picks bits (the int programs, `keep`, `drop`, `relu`) stores in the INT32 mode (`RAW`; the ISA says as much). An int32 kernel is an fp32 kernel's shape (the math thread fills Dst) with integer programs: add and sub by `SFPIADD`, wrapping as int32 does; max and comparisons through sign-magnitude (`SFPCAST` mode 3, its own inverse), the order `SFPGT` and `SFPSWAP` use, a comparison giving 1, not 1.0; `keep`, `drop` and `relu` as they are, since they only look at the sign or at zero. `SFPMUL24` multiplies 23 bits, so multiplies, reductions and float functions go through fp32, exact below 2^24, and a matmul is the FPU's, for floats only.

- **Casts** are SFPU programs inside the one-op cast kernel: an integer to sign-magnitude, then `SFPCAST` to float (to nearest); a float to an integer toward zero by shifting its mantissa, hidden bit in (`SFPEXMAN`), by its exponent - 23 (`SFPSHFT` takes a signed amount from a register), 0 where the exponent is negative, negated where the sign is set. `SFPSTOCHRND` would round, but only into 16 bits.
- **Mixing**: a float number with int32 makes fp32 (an int number stays int32), int32 with a float tensor meets in fp32, and `where` turns a condition of another dtype into 0 or 1 of the picked values' dtype first. Negation is `0 - x` for int32, exact, where `x * -1` would go through fp32.
- **gather** reads its indices from an int32 tensor of one row on the chip: BRISC fetches the indices' tile for each result tile. A Python list is uploaded as one first, so indices computed on the chip (an argmax, one day) need no trip to the host.

**Upload and download** go a tile at a time through the `array` module (floats to fp32 bytes, then bf16 bits with one list comprehension), about 10x faster than a struct call per value, which matters at GPT-2's 768 x 3072.

**Autograd** (`requires_grad_`, `backward`, `gradient`; `ferrite/tensor.py`; `test_autograd`). tinygrad's way: a rule per op (`_backward`), applied from the result back in reverse order of making, each rule a few of the same lazy ops, so the backward pass is ordinary tensors, fused into kernels as the forward is. A tensor made from one that requires a gradient remembers how (`_ctx`: the op, its operands, its arguments), and keeps that past realizing, which throws `op` and `srcs` away; without `requires_grad` nothing is kept, so inference (GPT-2) holds no graph. What the forward fused stays lazy, so the backward recomputes it rather than store it.

- **Rules** are tinygrad's: add, sub and mul by the chain rule; max splits a tie in half; a comparison and where's condition get none; `keep` and `drop` pass g through the same pick; exp, exp2, log, log2, sin, cos, sqrt and reciprocal from their result or input; a cast casts back; a sum broadcasts back and a max goes to its maxima, shared; a matmul is `g @ B^T` and `A^T @ g`.
- **Broadcasting**: an operand that was broadcast gets g summed over those axes (`_unbroadcast`). A gradient that is itself broadcast (a sum's) stays that way through elementwise rules and is made whole (`expand`) only where every element is needed: matmul, movement, and the leaves.
- **Movement and views record what they mean**, not the copy's map: reshape, permute, expand, pad, slice, index, split, merge, transpose, each undone by its inverse (a slice by a pad, a merge by a split, an expand by a sum). A slice with a step other than 1 or -1 has no backward yet. gather's backward is a one-hot matmul, `onehot(ids)^T @ g`, so repeated rows add.
- **An op, not its implementation**: an fp32 matmul is bf16x3, and differentiating through its parts gave gradients rounded to bf16 (each part's operand is bf16): 3e-3 off. It is recorded as one matmul, whose backward is two more fp32 matmuls.
- `test_autograd` checks every op's backward against numpy's central differences in float64, through a loss `sum(f(x) * w)` with random w, in fp32 with odd shapes and broadcasting: within 2e-4 (fp32 and the SFPU programs), 2^-11 for matmuls (the FPU's sums). Then a bf16 leaf (its gradient comes back through the cast), a tensor read twice, and `.grad` adding over two passes.

**MNIST** (`test_mnist_mlp`): 784 -> 128 -> 10 with relu and biases on a batch of 16, two launches, against numpy in float64: logits within 2%, and the same predicted classes wherever the top two are not a near tie. It found a bug as old as matmul fusion: the kernel took its row width from every input, including a matmul's A, whose columns are K. With K wider than the result (784 against 128) the units were cut wrong and whole result tiles were never computed. The tests had only multiplied with K at most the result's width. Now the width comes from what elementwise ops and reductions sweep.

**A GPT-2 layer** (`test_gpt2_layer`). GPT-2 small's block: 768 wide, 12 heads of 64, MLP 3072, on 16 and 40 tokens, with weights drawn the way GPT-2 initialises them. `gpt2.layer` is written once and runs on both ferrite `Tensor`s and numpy arrays (the reference, float64, same bf16 weights). Layer norms are one launch each; q, k and v are 64-column views of one qkv result; the heads are a batch (`split`): queries and values split by columns, the keys split the same way and read transposed by the matmul (`q @ k.T`), then one kernel for every head's scores, mask and softmax, one for attention times values, whose kernel writes each head into its 64 columns of one 768-wide result (`merge`, above), then `attn.c_proj` and its bias, added to the residual last, so the large value is rounded once. (Before `merge`, each head went through its own 64 rows of `attn.c_proj` and the 12 results were summed: the same numbers, but 12 roundings and a sum too big for one kernel.) Inside a kernel that sweeps rows in passes, a long matmul (K over 256) runs first on its own, or each pass would recompute it. A token was 148 launches and 0.8M simulated cycles (before multicast launches and split K: now 126 and 117k). The residual reaches 3000 in one channel, where bf16 steps by 16, so the logits drift about 1 from numpy's over 12 blocks: a pick within that of numpy's best is a tie bf16 cannot break (`test_gpt2_model`). Every intermediate is bf16, so the block's change to x matches to within 2% of its size (0.03 against 1.7; the test allows 3%). Breaking the row mask, the tidy padding, the transpose's face swap or the views' offsets each fails it.

**GPT-2 small, the real thing** (`test/gpt2.py`, `test_gpt2_model` when `GPT2=` names the weights). Hugging Face's `openai-community/gpt2` `model.safetensors` (float32, read with numpy and rounded to bf16), tiktoken's `gpt2` tokenizer. `forward` is written once for Tensors and numpy arrays: token and position embeddings, 12 blocks, the last layer norm, and the output layer, which is the token embedding again. The numpy version, in fp32, matches Hugging Face's own GPT-2 to 1e-4 in the logits, so it is the model and not just a copy of our mistakes. On ttsim, greedy from "The meaning of life is", ferrite writes " not the same as the meaning of death", the same 8 tokens as numpy and as Hugging Face, each step's 50257 logits within about 1.5 (they span about 100). What it took:

- `Tensor.frombytes` / `tobytes`: a dtype's values in row-major order, moved into tile order 16 values at a time with no per-value Python work. All 124M weights are on the chip in 5 s.
- `Tensor.gather(ids)`, the embedding lookup: a BRISC-only kernel that reads the indices from an int32 tensor and copies each row's two 32-byte runs out of the table's tiles. A NoC read from DRAM keeps its low 6 address bits, so a run comes in as the 64-byte block holding it and is copied into place. The tile starts as a NoC copy of the runtime's zero tile; a single row (the last position's, for the logits) comes in once and fills its tile by NoC copies within L1, doubling: 940 cycles instead of 5370 for 64 fetches.
- The output layer multiplies by `wte.T`, transposed on the chip once (37,700 tiles, 1.4 s on ttsim).
- Logits only for the last position: `gather([n - 1])` of the final layer norm, a filled one-row tile.
- No KV cache: up to 32 tokens are one tile row anyway, so a step costs the same either way. 27 s a token on ttsim, about 120,000 matmul steps (one per weight tile); the output layer is 7 s of that. On silicon the same work is a few milliseconds.
- `Runtime.wait` gives a launch 60 s to finish (`until`): on the simulator the biggest kernels take seconds.

**A Llama-family model** (`test/llama.py`, `test_llama_layer`, `test_kv_cache`, `test_llama_model` when `LLAMA=` names the folder). SmolLM-135M from Hugging Face (`HuggingFaceTB/SmolLM-135M`, Llama's architecture: 30 blocks 576 wide, 9 query heads sharing 3 key and value heads of 64, a SwiGLU MLP of 1536, RMSNorm, RoPE with theta 10000, tied embeddings), its weights stored in fp32 and rounded to bf16 at load, linear weights transposed on the host (so `x @ w`, no transposing on the chip). The model is written once for ferrite and numpy, as GPT-2 is, and the numpy version matches Hugging Face's fp32 model to 2e-5 in the logits. On ttsim, greedy from "The meaning of life is", ferrite writes " a question that has been asked", the same 6 tokens as numpy, each step's 49152 logits within 0.6 (they span 26). The prompt is 829 launches and 2.4M cycles; each later token reads the KV cache, about 30 s of simulation. What it took:

- **RMSNorm** and **SwiGLU** are a few ops each (`silu` is `x * sigmoid(x)`, `sigmoid` is `1 / (1 + e^-x)`).
- **RoPE** in Hugging Face's form, `x cos + rotate_half(x) sin`: a head's halves are 32 columns, a tile, so they are views, and `rotate_half` is `cat(-x2, x1)`; `cat` is tinygrad's, each tensor padded into place and the pads summed. The cos and sin tables are computed in fp32 and rounded to bf16, as Hugging Face does for a bf16 model (its fp32 model keeps them fp32, which was the numpy version's 0.012 against it until the check used fp32 tables).
- **Grouped-query attention without repeating keys**: the 3 query heads of each key and value head are reshaped into one matrix of 3 n rows (`(9, n, 64)` to `(3, 3 n, 64)`, row-major, a move), so one batched matmul per key and value head does its group, with the causal mask repeated down for the group; the result is reshaped back to 9 heads and merged.
- **A KV cache** as `[keys, values]` a block, grown by `cat` along the rows each step (a pad of the old cache and of the new row, and an add). Simple, and a copy of the cache each step; a preallocated one written in place would save that. Decoding with it equals the full recompute (numpy: 3e-5).
- **Single-row moves** were 3.6 times the rest of a decode step until the move kernel stopped making a row's 32 copies one by one (movement, above): a decode step of four blocks went from 1.25M cycles to 330k (250k once lines went as runs).

**A small CNN** (`conv2d`, `max_pool2d`; `test_mnist_cnn`). Convolution is im2col: one matmul of the weights (out, in k²) by the patches (in k², positions). With each channel flattened into a row of H W values, tap (ky, kx) of the kernel is those rows from ky W + kx on, so the patches are k² slices of one tensor, stacked (`cat`). Their column y W + x is the patch at (y, x) for every x, and the k - 1 columns of each row past the last x wrap around and are dropped from the result (2 in 28 for MNIST). Each tap is one move: the flattening (a reshape), k - 1 zeros on the end, the slice and the pad that puts it in its rows of the stack compose. Weights are (out, in, k k), PyTorch's with the kernel flattened, since tensors have three axes; for the same reason an image is (channels, height, width), one at a time. Stride 1 only: the flattened rows need it (a stride is a slice of the result, for now). A max pool is three reshapes and two maxes: the k rows of each block as a batch of k-row matrices and their max, then the k columns. Both are built from ops that have backward rules, so they have gradients (`test_autograd`). An MNIST-shaped network, a 3x3 convolution 1 -> 8 and relu, a 2x2 pool, a 3x3 convolution 8 -> 16 and relu, a pool and 784 -> 10, gets logits within 2% of numpy's in float64 in 46 launches and 321k cycles an image. The first `conv2d`, a slice, a reshape and a pad per tap (each its own move), took 34 launches and 505k cycles for the first layer; with moves composed, 16 and 118k. A tap still writes the whole patch tensor, zeros outside its rows, and one kernel sums the taps.

**Training** (`test/train.py`, `test_train`). A small GPT, GPT-2's blocks (`gpt2.layer`, the code that runs inference) 2 deep, 64 wide with 2 heads of 32, 64 characters of context and the output layer tied to the token embedding, learns README and LESSONS a character at a time, one window of 65 characters a step, with Adam at lr 3e-3. Weights, gradients and Adam's moments are fp32 tensors. PyTorch is the reference, with its own autograd and `torch.optim.Adam` (`gpt2.fns` has a branch for torch tensors), two ways: each step it takes ferrite's weights as they are and computes the same loss and gradients, and it trains by itself from the same first weights on the same text. Over 300 steps every loss is within 1e-04 of PyTorch's on the same weights and the gradients within 1e-02 of each weight's largest (2e-3 at the median step); the mean loss over 50 steps falls from 3.40 to 3.12, PyTorch's own run's from 3.41 to 3.07. `test_train` takes five steps on a text of its own, the numbers to 2999 written out: README and LESSONS change with every edit, and one edit made a step whose worst gradient error (0.0029) passed the test's 2e-3.

- **The two runs part, though each step is right.** Adam's first step moves every weight by lr times the sign of its gradient, and a gradient below the matmul's error (2^-11 of the largest, "Matmul precision") can come out either sign: after one step, 87 of 109,184 weights were a whole step from PyTorch's (74 of them key biases, which change nothing: softmax ignores a constant added to a row of scores). From there they are two models on the same text: gradients 4% apart by step 2, losses 0.1 apart by step 150, and once ferrite's loss was 7.3 where PyTorch's was 2.9, though at every step ferrite's loss and gradients are PyTorch's for ferrite's weights. So the step by step check is the test, and the curves have to fall alike.
- **The loss** is `cross_entropy`: `log_softmax` (x - max - log of the sum of e^(x - max)) times a one-hot of the targets, summed and averaged over the positions.
- **Adam** is PyTorch's, written with lazy ops: per weight a kernel each for m, v and the weight, each written back with `assign`, which computes the new value into DRAM of its own and has the weight take it (its old DRAM goes back once the launches queued so far are done), so the weight stays the same object.
- **A step** costs 696 launches and 377k cycles, 1.6 s on ttsim, 153 launches of them the forward. The fp32 matmuls are bf16x3, so each fp32 operand is two cast kernels (hi, then lo from what hi left): 242 launches a step. A kernel with two results, or an unpacker splitting fp32 as it reads, would remove them.
- **Transposes in the backward.** Each matmul's gradient takes A^T and B^T, and in fp32 a transpose was a move, a datum at a time: 2M of a step's 3M cycles. An fp32 matmul now splits a transposed operand first, so its bf16 parts transpose as bf16 does (read transposed as B, the tile transpose as A), and gather's backward builds its one-hot already transposed (a column of row numbers against the row of ids). The moves left, the pads that put q, k and v's gradients back into qkv's columns and the transposes of `A^T @ g` that a transposed operand's own gradient takes, were 450k cycles a datum at a time; as whole tiles and transposed tiles they are 9 launches and 28k.

**Fuzzing** (`test_fuzz`). Random expressions (elementwise ops with broadcasting, unary ops, reductions along each axis, matmuls, odd shapes, batches), and every kernel they turn into checked against numpy on the same inputs read back from the chip. Checking kernel by kernel keeps bf16 rounding that piles up through a tree from passing for a bug, or hiding one. The test runs 30 expressions; longer runs of the same code (thousands) found two limits the compiler did not respect: a kernel sweeps its rows at one width, so row reductions of tensors of different widths cannot share one (the narrower was reduced as if one tile wide), and it has two accumulators, so a third reduction in a pass crashed. `_expr` now computes such reductions first, on their own.

**What ttsim can and cannot check here.** ttsim runs each Tensix instruction the moment it can, in zero time, and ignores the busy conditions of `STALLWAIT`. Each TRISC now pushes as fast as it can, and TRISC2, with the least to push, runs ahead, so the waits really happen there. Breaking each one on purpose (and running the tests) shows: without the pack's `SEMWAIT`, the math's Dst-half wait or the SEM_L1 wait, ttsim stops on a semaphore taken while empty or posted while full (`test_threads_wait` alone hits all three); without BRISC's wait for `UNPACKED` or TRISC2's wait for `SENT`, results are wrong; without TRISC0's wait for `FETCHED` or the math's wait for `READY`, a test fails or hangs. Not caught on ttsim: the `STALLWAIT` before thread 0's report (unpacks are instant there), TRISC2's wait for `READY` and TRISC0's `tensix_idle` before setting it (ttsim's semaphores start at 0 and its thread 0 is always done by then), and the accumulator semaphores. Speed-up from the overlap cannot be measured on ttsim at all; that waits for silicon. The `STALLWAIT`s are what the ISA asks for, and only silicon will show a missing one.

**Two numbers to watch** (ROADMAP, stage 3). The benchmark, `python3 -m ferrite.bench [M K N]`, reports wall time on a card, simulated cycles on ttsim (a work count, not silicon speed), and DRAM reads against reading each input once (ttsim's DRAM is instant, silicon's is not). 512x768 @ 768x3072 on ttsim: 35k cycles, "93 of 166 TFLOPS" at four fidelity phases; 22k ("153") with A's row kept in L1, resident kernels and launches queued back to back; 17k with arguments and go multicast (past the "peak": ttsim does not time Tensix instructions, so on ttsim the benchmark now reports cycles only); 9k with tiles shared by multicast, 1.7k with the reads shared out ("Cutting the critical path"). DRAM reads: 14.9 times the inputs, 6.9 with blocks, 1.0 shared. A GPT-2 token (5 tokens of context, all 12 blocks and the logits) on ttsim: 2.07M cycles and 725 launches at first; 627k with kernels resident and launches queued; 140k at 126 launches with arguments, go and done for every worker at once, split K for one-row matmuls, the zero tile kept by the runtime, a layer's elementwise sums realized before its layer norm, straight-line kernel setup; 123k with NoC requests through preset initiators ("Cutting the critical path"); 117k with launches cut to 220 cycles ("Launch cost"). On ttsim queued Tensix instructions cost nothing ("How ttsim counts"), so what is left is the RISC-V work between them, about 220 cycles a launch and the cores' hand-offs; on silicon the MVMULs will count.

**ttsim's cycles are its model, not silicon's.** A kernel whose root is a binary op costs about 110 cycles a tile more than one whose root is unary (`x + y` 119 a tile, `exp(x + y)` 8, on one worker): the difference is in how ttsim times the math thread's last `STALLWAIT` of a tile, not in our code. The benchmark and the per-token numbers above count ttsim's cycles; use them to compare versions of our code, not to predict silicon.

**How ttsim counts** (`libttsim.cpp`, `clock_current_chip`). In one clock, each tile steps its RISC-V cores once and runs one Tensix instruction from each pipe that can go, and does it again for as long as any pipe ran one. So a Tensix instruction that is queued costs nothing, whether pushed, replayed or expanded from a MOP (all of which put it in the FIFO at once); clocks go by only while every pipe of a tile is empty or stalled, one RISC-V instruction a clock. A kernel's cycles on ttsim are the RISC-V instructions on its critical path while the Tensix waits: polling, handshakes, NoC requests. Two consequences:

- **The host's polls bound every measurement.** `pci.Sim.tick` runs ttsim 10 clocks a poll; it ran 1000 until 2026-10-18, which rounded each wait up to the next 1000. A profile that waits after every launch overstated a step by about 500 cycles a launch: ferrite's training step was 444k cycles, not the 766k quoted, tinygrad's 2.07M, not 2.58M, a one-tile add 390, not 700. Numbers earlier in these notes were taken that way; the ones from one wait over many launches (the benchmark, a token) were close.
- **The MOP expander would not show.** A profiling copy of ttsim (outside this repo: on each idle clock of a tile, the PC of each of its RISC-V cores, mapped to the kernel's source through an ELF built from the same C) put the benchmark matmul's idle clocks at: the math TRISC on a queued instruction waiting for data (99%), the unpacker TRISC polling BRISC's count of fetches, BRISC waiting for multicast flags and for the unpacker's reports, the packer waiting for BRISC to send. The math thread is already ahead (replay makes a matmul step 6 words for 64 `MVMUL`s), so the MOP expander, which only saves pushes, would change nothing on ttsim; batching the unpacker's per-step handshakes into one a tile did not either.

**Cutting the critical path.** A trace of one tile, clock by clock (the profiling copy of ttsim, writing each clock's Tensix instruction count, its RISC-V PCs and its FIFOs' fill), showed the benchmark matmul's shape: every tile did its Tensix work in one clock per column of B, about 3150 instructions, and waited about 900 clocks between. A receiver spent the wait in `await`; the column's leader spent it issuing B's 24 tile reads, about 36 RISC-V instructions each (the bank, the address, all nine registers of initiator 0), and everyone waited on it. Three cuts, measured on the benchmark: reads through an initiator set up once (`noc_get`), 8.9k cycles to 7.0k; arguments read through a plain pointer rather than a volatile one, so the compiler keeps them out of loops (the leader's gap shrank, the total did not move); the reads shared among the workers of a row or column, each doing a share, 7.0k to 1.7k. With results also written through a preset initiator (`noc_put`) and a block's place stepped from the last rather than divided out, a GPT-2 token went from 140.7k cycles to 122.7k, a one-tile add from 390 cycles to 360, ferrite's training step from 444k to 421k, a 1024 x 3072 add from 3.6k to 3.1k; tinygrad's step barely moved (2.07M to 2.05M), its time being elsewhere. On silicon, the shares spread the DRAM reads over every worker's NoC interface rather than a row's and a column's; the instructions saved matter less there, where a kernel this size waits on DRAM.

**Next for the compiler:**

1. The TRISCs push every instruction themselves. The MOP expander (which BRISC could not use) would turn a whole tile's math into one word, and the loops over units and tiles could run in it. It saves pushes only, which ttsim does not count and which replay already keeps few ("How ttsim counts"); measure it on the card, at low fidelity, where a matmul step is 16 cycles rather than 64.
2. Reads in flight ("Reads in flight") are 4 steps a worker, a guess: on the card, measure decode at other `DEPTH`s, with bf16 and bfp8 weights, against the card's DRAM bandwidth. (Tried before transaction IDs: B through 8 slots, steps told to thread 0 four at a time after one `noc_wait`, which on ttsim made a token 144k cycles to 164k in waiting for each chunk.)
3. Matmul reuse across cores is done for unbatched matmuls ("Tiles shared between workers"), each worker reading an equal share, and for one-row ones, batched or not ("A token's row, shared"). Batched ones of more rows (attention's heads in prefill) and matmuls in kernels that reduce still read their own copies.
4. Passes recompute: softmax computes exp twice. Its inputs are kept in L1 between passes now ("Lines in passes"); its intermediates could be too, when they fit. With few lines, line ownership leaves workers idle; splitting a line across workers would need a cross-worker reduction. Fusion beyond this: a matmul epilogue could stay in Dst (`(a @ b) + c` by unpacking c and adding into the same half, no pack/unpack of the product), and prologues (`(a + b) @ c`, per K step). Keeping a bf16 kernel's intermediates in fp32 (an fp32 pack, or moving Dst back into SrcA/SrcB) instead of rounding each to bf16 (fp32 kernels already do).
5. In a bf16 tensor a number is bf16 too, so `x * (1/768)` (a mean) multiplies by 1/768 rounded to 8 bits, 0.2% off. A mean could scale in fp32 at the end of its reduction, and a constant in general could ride into the SFPU program that reads it, as exp's does.
6. Movement in words: a run copies a datum at a time, where runs that line up in both tiles could go a word at a time, or by NoC reads within L1. And a move that writes its rows into a view of a bigger tensor would make a convolution's patches k² moves the size of a tap, with no sum after.
7. BFP8 ("Weights in BFP8") shared by multicast (B's region laid out the same in every worker of a grid column), so prefill's matmuls read it once too; BFP4 (576 bytes a tile) for smaller weights still.

## tinygrad on ferrite

`adapters/tinygrad_ferrite.py`, `test_tinygrad`. tinygrad is the frontend (its Tensor, nn, autograd, optimizers) and ferrite the compiler and runtime, as tt-tiny lays the stack out. tinygrad finds a device only as `tinygrad.runtime.ops_<name>`, so the adapter puts a module there (`FERRITE`), with an allocator whose buffers hold host bytes or a chip value. It takes over at `create_linear_with_vars`, where tinygrad would schedule a graph into its own kernels: by then the graph is tinygrad's primitives on shaped tensors (the ALU ops, `REDUCE`, `RESHAPE`, `PERMUTE`, `EXPAND`, `PAD`, `SHRINK`, `CAST`) with explicit `STORE`s into buffers and `AFTER`s that order them, and a graph that touches FERRITE runs in the adapter, op by op into ferrite's lazy tensors, which ferrite fuses and launches its own way. tinygrad gets back an empty schedule.

- **The graph's semantics.** A `BUFFER` reads as it is before any store in the graph; an `AFTER` reads its buffer again through its view chain, after the stores so far (reading the view computed before the store gave Adam zeros, and NaN). `REDUCE(op, n)` folds the leading n axes (tinygrad permutes the reduced ones to the front); binary ops broadcast numpy's way, with no `EXPAND`; `SHRINK` and `PAD` take (start, size) pairs. `COPY` onto FERRITE uploads.
- **Views** (`adapters/views.py`, shared with the other adapters). Movement stays a view of a ferrite tensor: shape, strides, offset, and a mask for padding (a small ShapeTracker), reshaped by merging and splitting axes where the strides line up. An op that needs the data folds the view into ferrite's three axes: the tensor as it is, a ferrite transpose for a swapped one (which a matmul reads in place), one move if the view's axes merge into three groups, block swaps for a pure reordering (each swap of two blocks of axes is one move, since a move reads its source in row-major order whatever its axes: attention's heads apart or together are two), and otherwise the host.
- **The fold.** Any rank goes to (1, all but the last axis, the last), so a short axis (6 tokens) does not pad its tiles to 32 rows, and an elementwise op takes its operands in the grouping one of them already has (a batched matmul's result, say) rather than moving them into the default.
- **Matmul.** tinygrad writes `a @ b` as a broadcast multiply summed. A `REDUCE(ADD)` of a `MUL` whose operands do not broadcast along the summed axes is a ferrite matmul: along the other axes, both spanning one is the batch, a alone the rows, b alone the columns. A product that only sums read is deferred, so it is never computed as the (64, 6, 128, 128) tensor it describes.
- **The host.** What ferrite does not do (uint32 and uint64, bit operations, `THREEFRY`: tinygrad's random numbers) runs on tinygrad's own CPU device, lazily, so tinygrad fuses what runs there as it would on its own: a subgraph of host values stays a tinygrad graph until it meets a chip value, is computed then, and goes up in that value's layout. Evaluated op by op into numpy instead, a dropout's random numbers made whole a padded view that tinygrad's `arange` sums: 10 GB for a moment. A weight that comes as bytes goes up in the shape of its first use, and one kept in a shape its uses do not fold to (tinygrad makes weights flat) is laid out again once.
- **JIT.** tinygrad's `TinyJit` replays the schedules it recorded, and the adapter makes none, so the runner (`python3 adapters/tinygrad_ferrite.py script.py`, which also sets `DEV=FERRITE` through tinygrad's own context variables, since tinygrad reads the environment when imported) turns it off.
- **Results.** `test_tinygrad`: elementwise ops, reductions, 3-D views, a matmul, softmax against tinygrad's CPU device, and an MLP trained with Adam for three steps to 1e-4 of the same on the CPU, every op on the chip. tinygrad's `examples/transformer.py`, unchanged (2 blocks 128 wide, 4 heads, batches of 64 sequences of 6), learns two-digit addition: its 10 rounds of 50 Adam steps ran to the end on ttsim, test accuracy 86.4% after the first and 99.99% after the last (1 of 10,000 wrong), about 7 hours with the code of the day. A training step is 1155 launches and 1.98M cycles, 16 s on ttsim, in 0.5 GB. It began at 52 s and 10.4M: views that did not fold went through the host (28 s a step, until block swaps), tensors folded as a batch of 6-row matrices padded every one to 32 rows, transposes became moves where a matmul could read them in place, products were made whole before their sums, and the move kernel went a datum at a time (6.1M cycles, 25 s, until whole tiles and runs).
- **Not done yet.** A store into part of a buffer (assigning to a slice); masked views over several merged axes (through the host); dtypes other than float32, bfloat16, int32 and bool (on the host); tinygrad's JIT.

## PyTorch on ferrite

`adapters/torch_ferrite.py`, `test_torch`, `test_transformers`. A `FerriteTensor` is a `torch.Tensor` subclass with no storage, holding a value of `adapters/views.py` (a view of a ferrite tensor), and every aten op on one comes to its `__torch_dispatch__`. There it becomes ferrite's lazy ops at once, so there is no graph to walk: eager PyTorch, its autograd (which works above the dispatch, so the backward's aten ops come the same way) and `torch.optim` run on the chip, and ferrite fuses until something reads a value back (`.cpu()`, `.item()`). `ferrite(model)` and `ferrite(x)` move parameters, buffers and tensors.

- **Ops.** About sixty aten ops are written out (elementwise, comparisons, `where`, sums and maxes over any axes, `mm` and `bmm`, which PyTorch makes every matmul into, views, `cat`, constants, casts). Anything else goes to PyTorch's own decompositions, core aten's first and then the rest, whose prims (`sum`, `var`, `broadcast_in_dim`, the elementwise ones) map back onto the same functions; only then to the CPU, its tensors brought over and sent back. `erf` (for `gelu`) is Abramowitz and Stegun's 7.1.26 from ferrite's exp, within 1.5e-7; cross entropy's `gather` and `scatter` are one-hots compared against positions.
- **In place.** An optimizer updates in place (`add_`, `mul_`, `addcdiv_`, `lerp_`): the out-of-place op, then the result kept in the tensor and computed now, so a training loop does not grow one lazy graph over all its steps.
- **Attention.** The tensor says it is on the CPU (PyTorch will not take a device of ours without C++), so PyTorch picks its fused CPU attention kernel. Its forward has a decomposition; its backward has none, so it is written here in PyTorch's ops, which come back to the dispatch: the softmax again from the scores (the forward's decomposition, written for export, keeps the attention weights where the kernel keeps their logsumexp), then the chain rule through the two matmuls.
- **Results.** `test_torch`: the ops against PyTorch on the CPU, an MLP for three Adam steps and PyTorch's own `TransformerEncoderLayer` for two, losses within 1e-3 of the CPU's, and nothing falling back to it.
- **Hugging Face transformers.** Its own Llama code, unchanged, runs SmolLM-135M from its folder (`AutoModelForCausalLM.from_pretrained`, then `ferrite(model)`): all 30 blocks' logits within 0.05 of PyTorch's on the CPU in fp32 (they spread 7.2), within 2.5 in bf16, the same top tokens, 85 s and 34 s on ttsim; `generate`, greedy with its KV cache, writes "The meaning of life is a question that has been asked" as the CPU does (6 tokens in 570 s); and fine-tuning with Adam follows the CPU's losses. Nothing falls back to the CPU but `generate`'s integer bitwise and. What it took: CPU tensors the model makes itself (RoPE's positions from `arange`) lifted onto the chip where they meet chip tensors; `index` by one tensor of ids (the embedding, the cache's positions) as ferrite's `gather`; `flatten`, `unflatten`, `prims.view_of`, `pow` by 1, 2, 3, ±0.5 and -1 (RMSNorm's backward wants the cube); integer results kept int32 (ferrite multiplies int32 in fp32, so generate's token bookkeeping had turned its ids into floats); grouped-query attention in the attention backward; the embedding's backward as the ids' one-hot, transposed, times the gradient, as ferrite's `gather` does, not `index_put` on the CPU with a 113 MB gradient each way; tied weights kept tied by `ferrite(model)`; and `constant_pad_nd` on views. PyTorch's decomposition of padding fills a tensor and copies the input into a view of it in place (`prims.copy_to`), which went to the CPU and was lost: the loss's labels, padded with -100, were all -100, and the loss was NaN. Padding with a value then showed a bug in `views.operand`, which took any axis of stride 0 for a broadcast and dropped its mask; an axis broadcasts only where nothing pads it. `test_transformers`: a small Llama of transformers' own with random weights (logits, `generate`, three Adam steps at a learning rate of 1e-3, losses within 1e-3; at 1e-2, Adam turns gradients that nearly cancel into full steps of either sign, and bf16x3 matmuls drift 0.01 apart in two steps), and SmolLM-135M's real weights with `LLAMA` set.
- **Not done yet.** In-place ops on views (they replace the view's own value, not its base's); dropout inside attention (its random mask is the CPU's); integers wider than 32 bits (int64 is held as int32); integer bit operations (on the CPU).

## Bring-up on a p150

Everything so far ran on ttsim, which models the chip from Tenstorrent's own knowledge but runs each instruction at once, ignores most busy conditions, and completes NoC requests instantly. The day the card arrives, go in this order; each step only needs the ones before it. The tests open the card themselves when `TTSIM` is not set (`pci.open_device`), so the commands are the simulator's without it, as root.

Before: `lspci -d 1e52:b140` shows the card; the IOMMU is off or in passthrough (`iommu=pt`), since `pci.Card` hands the device physical addresses; a few 2 MiB hugepages are free (`echo 4 > /proc/sys/vm/nr_hugepages`; each `Runtime` holds one). `pci.Card` unbinds tt-kmd itself.

| step | command | what it confirms (and what to suspect if it fails) |
|---|---|---|
| 1 | `pytest test -k "config_space or arc"` | BARs, the TLB config registers (`bh.TLB_CONFIG`, `TLB_FIELDS`), the NoC coordinates of ARC, ARC's boot status, message queue and telemetry tags, and that `POWER_ON` wakes Tensix (else try AICLK go busy, `0x52`) |
| 2 | `-k "dma or l1 or (dram and not freed)"` | the PCIe tile's loopback into host memory (`bh.PCIE`, bus addresses below 2^58), unicast L1 writes, DRAM bank coordinates and GDDR training |
| 3 | `python3 -m ferrite.hello` | soft reset bits, reset PCs and their override (`bh.TRISC_RESET_PC`), the firmware's jump table, the NIU's request registers (and that request initiators 1 and 2 keep theirs between requests: `noc_setup` presets them once, then every kernel's `noc_get` and `noc_put` and the dispatcher's go write only what changes), device writes into host memory, and the dispatcher: its multicasts from a core (the rectangle in `NOC_RET_ADDR_HI` with translated coordinates, one acknowledgement per worker, the counter clear) and the workers' atomic increments. A hang here with every worker done (their mailboxes say so) points at the count; one before any worker starts, at the multicast's acknowledgements (the dispatcher waits for exactly one per worker: more, from tiles in the rectangle that are not workers, would hang it rather than let a go overtake the arguments) |
| 4 | `-k "every_core or relaunch or moves_data or queue or hung"` | the launch path end to end; instruction cache invalidation (`bh.CFG_IC_INVALIDATE`, a no-op in ttsim, so only here can a stale kernel show) |
| 5 | `-k "tile_math or tensor_math"` | the backend config indices (`bh.TENSIX_CFG_FIELDS`, from ttsim's `tensix_regs.json`, not the ISA), instruction encodings, `.ttinsn`, semaphores from the TRISCs, unpack and pack of bf16 |
| 6 | `-k "matmul or stream or bfp8"` | MVMUL, the 3-bit address modes (from ttsim's `tensix_isa.json`; the ISA pages are Wormhole's), fidelity phases and stopping after fewer (`fidelity`), the replay buffer; workers multicasting to a row or a column of the grid, or for a token's A to several whole rows (`multicast`: rectangles across the non-Tensix columns, a worker clearing its outstanding count after, flags counted and zeroed); bfp8 (`bfp8`: the packer writing it, the unpacker reading it); and a step's reads waited for by their transaction ID, from thread 0's TRISC ("Reads in flight"). If the grid's matmuls are wrong or hang while one worker's are right (`stream`, `blocks` on one worker), look at the multicasts; if a cast to bfp8 is right and a matmul by it wrong, at where the unpacker looks for a slot's exponents and values ("Weights in BFP8"); if matmuls are wrong now and then, at the per-ID counters (`DEPTH = 1` leaves one read in flight) |
| 7 | `-k "sfpu or reduc or softmax or any_shape or views or batch or movement"` | `SETADC` stored with a slot worked out at run time (inputs kept in L1 between passes, read by their place on the line), 2-byte loads and stores to L1 from BRISC (`move_kernel`), SFPU encodings, LReg 15 as 2 x lane, lane flags, `SFPARECIP`, `SFPTRANSP` (a column max that is wrong while a row max is right), `Haloize_mode`, and switching it inside the unpack thread (`haloize`; if `q @ k.T` is wrong while `k.T` alone is right, look at the `STALLWAIT`s around the `RMWCIB`) |
| 8 | the whole suite, a few times over | the waits ttsim never makes happen: the `STALLWAIT`s before reports and packs, TRISC2's wait for `READY`, `tensix_idle` before setting it (NOTES above: "What ttsim can and cannot check here"). A failure that comes and goes points here |
| 9 | `GPT2=... pytest test -k gpt2`, then `test/gpt2.py` | everything at once, and the first real timings: the last token's kernels by cycles on the chip's wall clock (`Runtime.profile`; if they are all 0, look at `bh.WALL_CLOCK`) |
| 10 | `python3 -m ferrite.bench`, `python3 -m ferrite.bench 512 768 3072 2`, then `python3 -m ferrite.bench 1 768 3072` and the same with `4 bfp8` | real TFLOPS against the peak, what two fidelity phases gain, decode's GB/s against the card's DRAM bandwidth with bf16 and bfp8 weights (and so what reads in flight and BFP8 gain: try other `DEPTH`s), and DRAM reads against the inputs: the numbers ttsim could not give (ROADMAP, stage 3) |

For a hang, `Runtime.wait` names the stuck workers; read their PC snapshots (`0xFFB1_3138`, five words) with `chip.read32` to see where each core sits (ttsim does not model them, so this is untested too).

## Still unknown or untested

- The real-card backend (`pci.Card`) has never run: the p150 has not arrived. It assumes root, the IOMMU off or in passthrough, and free 2 MiB hugepages (Bring-up, above).
- Whether the all-on power message is enough to wake Tensix on silicon after kmd clock-gated it, or whether `0x52` (AICLK go busy) is needed too.
- Whether the host-to-PCIe-tile loopback in `test_dma` (BAR read that turns into a device read of host memory) behaves on silicon as it does on ttsim. Device-initiated writes from a core's NIU are the path that matters and are untested.
- ISA does not document BAR2 (iATU, DMA engine), the DRAM tile's internal address map, ARC's message protocol, or the power-on value of soft reset. ttsim models them; real silicon may differ.
- ttsim does not model `mhartid`, `fence.i`, the PC snapshot registers, NoC request splitting, or most of BAR2, and it completes every NoC request instantly, so a unicast's outstanding count is back to 0 before anyone reads it. Instruction cache invalidation is a no-op in ttsim, so `test_relaunch_without_reset` cannot catch a stale-instruction bug.
