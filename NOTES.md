# Notes: how ferrite works

How ferrite drives a Blackhole, from the PCIe BARs up to the kernels its compiler emits; where each fact about the chip
comes from; and what is still unknown. Facts the code uses live in `ferrite/bh.py`; ROADMAP.md has the plan.

Sources: **ISA** = tt-isa-documentation/BlackholeA0, **sim** = ttsim `src/`, **kmd** = tt-kmd, **umd** = tt-umd.

Contents: the chip from the host (address map, TLBs, reset, the cores, what tt-kmd does); the launch loop and the
command queue (`runtime.py`); the Tensix coprocessor and the compiler (the pipeline, matmul, fusion, elementwise,
reductions and passes, shapes and movement, dtypes, autograd); the models; ttsim; the record of the numbers; what the
compiler does next; tinygrad on ferrite (and PyTorch through it); serving; bring-up on a p150; and what is still unknown.

## Address map

### PCIe function

Vendor 0x1E52, device 0xB140 (sim `pcie.cpp`, kmd). Three 64-bit prefetchable BARs (ISA `PCIExpressTile/README.md`):

| BAR | Size | Contents |
|---|---|---|
| BAR0 | 512 MiB | `0x0000_0000-0x193F_FFFF`: 202 TLB windows of 2 MiB (TLBs 0-201). TLBs 0-31 can do strided multicast; TLB 201 is reserved for the kernel driver. |
| | | `0x1FC0_0000`: TLB config, `u32[3]` per TLB for TLBs 0-209, then `u32 strided[32]` at `0x1FC0_09D8` |
| | | `0x1FD0_4000`, `0x1FD1_4000`: the PCIe tile's NoC0 and NoC1 NIU registers |
| | | `0x1FE0_0000-0x1FFF_FFFF`: ARC on PCIe 1 only; reserved on PCIe 0, which is the one a p150 uses |
| BAR2 | 1 MiB | PCIe controller (DBI): eDMA read channel 0 at `0x100-0x1A8`, iATU at `0x1000` (outbound region r at `0x1000 + 0x200*r`, inbound interleaved between). Not in ISA; offsets from kmd `blackhole.c`, umd `blackhole_dma_transfer.cpp`, sim. |
| BAR4 | 32 GiB | 8 TLB windows of 4 GiB (TLBs 202-209) |

### NoC

17 x 12 grid. Raw NoC0 coordinates (ISA `Diagrams/Src/NoC.lua`, sim `tile.cpp`): DRAM at x=0 (banks 0-3) and x=9 (banks 4-7), ARC (8,0), PCIe 0 (2,0) and PCIe 1 (11,0), Ethernet on y=1, Tensix at x=1..7,10..16, y=2..11. NoC1 numbers the same grid from the other corner: (16-x, 11-y).

Firmware turns on **coordinate translation** at boot (`NIU_CFG_0` bit 14) and programs every tile's translation tables, so harvested Tensix columns move to the highest x and software never sees which physical columns are dead (ISA `NoC/Coordinates.md`). ferrite uses translated coordinates everywhere:

| Translated (x, y) | What |
|---|---|
| x 1..7, 10..14, y 2..11 | Tensix, 120 on a p150 (x 15, 16 are its 2 harvested columns: firmware 19.5+ harvests 2 on every p150, umd `CHANGELOG`, `cluster_descriptor.cpp`; before 19.5 all 140 run) |
| x 17..18, y 12..23 | DRAM: bank b at (17 + b//4, 12 + 3*(b%4) + port), port 0..2, all three ports reach the same 4 GiB |
| (19, 24) | the PCIe tile connected to the host |
| x 20..31, y 25 | Ethernet |
| y 0 and 1 | not translated in x: ARC is (8, 0) |

A NoC address is (x, y, 64-bit address inside that tile).

### Inside a Tensix tile

As the tile's own cores see it; the last column says whether the NoC reaches the same address (ISA `TensixTile/BabyRISCV/README.md`):

| Address | What | Over NoC |
|---|---|---|
| `0x0000_0000-0x0017_FFFF` | L1, 1.5 MiB. Code runs only from here. | yes |
| `0xFFB0_0000` | the core's own data RAM: 8 KiB for BRISC and NCRISC, 4 KiB for each TRISC. Stack goes here. | no (yes via slow aliases at `0xFFB1_4000`...) |
| `0xFFB1_2000-0xFFB1_2FFF` | tile control and debug registers, including soft reset and reset PCs | yes |
| `0xFFB1_3138-0xFFB1_314B` | PC snapshot of each core | yes |
| `0xFFB2_0000`, `0xFFB3_0000` | NoC0 and NoC1 NIU registers (the tile issues NoC requests here) | yes |
| `0xFFE0_0000`... | Tensix coprocessor: GPRs, instruction push, PC buffers, mailboxes, config | no |

MMIO registers take exactly one 4-byte access, from either side.

### DRAM

Eight 4 GiB banks; the address inside a DRAM tile is the byte offset in its bank, starting at 0 (umd soc descriptor, kmd `test/tlbs.cpp`; sim models 4080 MiB per bank). ISA does not document the DRAM tile's address layout. On silicon, GDDR training must be done before first use: telemetry tag 22 has 2 bits per bank (trained, error); umd waits up to 300 s and retrains with ARC message `0xB6`.

### Host memory, from the device

The device reaches host memory by sending NoC requests to the PCIe tile at (19, 24). Its address space (ISA `PCIExpressTile/README.md`):

| NoC address | Goes to |
|---|---|
| below `0x0400_0000_0000_0000` (2^58) | the host, as a bus address, through the host IOMMU |
| bits 58/59 set | same, with relaxed ordering / no-snoop |
| `0x1000_0000_0000_0000` (bit 60) | through the outbound iATU (16 regions, programmed in BAR2) to the host |
| `0xF800_0000_0000_0000` | PCIe controller DBI |

So a host buffer at bus address B is NoC address (19, 24, B), with no iATU setup: firmware sets up the windows, and kmd's DMA-mask comment says the same (an IOVA below 2^58 is used directly as a NoC address, kmd `blackhole.c`). kmd and umd still route pinned memory through the bit-60 iATU window (umd's host base `4 << 58`, tt-metal's `0x1000_0000_0000_0000`), so the direct path is one neither uses, and it rests on firmware having set window 0 up again after each boot or reset. test_dma checks it on ttsim; on the card it is bring-up step 2. If it fails there, the fallback is kmd's: outbound iATU region r at BAR2 + `0x1000 + 0x200 r` (base at +`0x08`/`0x0C`, limit at +`0x10`/`0x20`, target at +`0x14`/`0x18`, CTRL_1 = `1 << 13`, CTRL_2 = `1 << 31`, CTRL_3 = 0; kmd `blackhole.c` 86-120, 878-911), and NoC address `0x1000_0000_0000_0000` + offset for a host buffer. kmd gives each pinned buffer a region of its own, at most 1 TiB; with the IOMMU off, one region mapping [0, 1 TiB) onto itself would cover every hugepage, and the only change elsewhere is bit 60 on the bus address `Runtime` takes from `alloc`. ttsim models that path too (`translate_pci_dma_addr`: windows 4-7 go through the outbound regions, and it checks the registers written; an offset no region covers passes through unchanged, so a test must map one somewhere else), so the fallback can be tested there before the card; it is not written, since it needs BAR2, which nothing else uses.

## TLB setup

A TLB window turns a range of BAR0 (or BAR4) into a range of one tile's NoC address space. Each TLB has a 96-bit config at `BAR0 + 0x1FC0_0000 + 12*i`, written as three 32-bit uncached writes. 2 MiB TLBs (ISA `PCIExpressTile/HostToDeviceTLBs.md`, matches sim and umd):

| Bits | Field |
|---|---|
| 0-42 | NoC address >> 21 |
| 43-48, 49-54 | x_end, y_end (the target, or the far corner of a multicast rectangle) |
| 55-60, 61-66 | x_start, y_start (multicast only) |
| 67-68 | noc: NoC0 or NoC1 |
| 69 | multicast |
| 70-71 | ordering: 0 relaxed, 1 strict AXI, 2 posted writes, 3 counted writes |
| 72 | linked (never safe to set) |
| 73, 75, 76-77 | static VC enable, buddy, VC class (kmd names 74 stream_header and 75-77 static_vc; same bits) |

4 GiB TLBs: bits 0-31 are address >> 32, then x_end at 32, y_end 38, x_start 44, y_start 50, noc 56-57, mcast 58, ordering 59-60, linked 61, static VC 62.

Write the three dwords with 32-bit stores (odd TLBs are not 8-byte aligned), and the address must be window aligned (kmd, umd). umd turns on static VC for windows that only write or only read, and leaves it off for a window that does both: a read+write window on a static VC "crashes the host" (umd `architecture_tlbs.cpp`).

ferrite moves one shared 2 MiB window (TLB 0, strict ordering) whenever an access crosses into another 2 MiB block or goes to another tile or rectangle, and gives the doorbell a TLB of its own (`Chip.map`). Unicast uses dynamic VC. Multicast (`Chip.write(..., start=...)`) sets x_start/y_start, mcast, and static VC class 2, as umd does. Slow on purpose: simple first. Faster later: more windows of their own, posted ordering for bulk writes, BAR4 windows for DRAM.

## Reset sequence

Per Tensix tile, `RISCV_DEBUG_REG_SOFT_RESET_0` at `0xFFB1_21B0`, reachable over the NoC (ISA `TensixTile/SoftReset.md`). A set bit holds a core in reset:

| Bit | Core |
|---|---|
| 11 | BRISC |
| 12, 13, 14 | TRISC0, TRISC1, TRISC2 |
| 18 | NCRISC |

Other bits reset parts of the Tensix coprocessor. There is no atomic set/clear; it is read-modify-write. Power-on value is `0x47800`, all five cores held (sim; ISA does not say). umd releases with `0x80047000`: bit 31 is "staggered start", which spreads core start-up across the chip (power, not function; sim ignores it).

To run code on a core: write `0x47800` (hold everything), write the program into L1, write `0x47000` (release BRISC only), poll L1 for its result with a timeout, write `0x47800` again. `Chip.halt` holds a rectangle; `Runtime` boots it and releases BRISC and the TRISCs.

Leaving reset: the instruction cache is invalidated, GPRs are zeroed, the PC is set (below), and the core's data RAM zeroes itself over up to 2048 cycles unless `RISCV_DEBUG_REG_DISABLE_RESET` (`0xFFB1_2224`) says not to. So: load code while the core is held, and do not preload data RAM over the NoC without setting that bit.

## What the cores run out of reset

Nothing of ours: there is no boot ROM in a Tensix tile. A released core fetches from L1 at its reset PC (ISA `SoftReset.md`):

| Core | Reset PC |
|---|---|
| BRISC | `0x0` (fixed) |
| TRISC0/1/2 | `0x6000`/`0xA000`/`0xE000`, or `RISCV_DEBUG_REG_TRISCn_RESET_PC` (`0xFFB1_2228/222C/2230`) if bit n of `0xFFB1_2234` is set |
| NCRISC | `0x12000`, or `0xFFB1_2238` if bit 0 of `0xFFB1_223C` is set |

The baby cores are rv32im with Zicsr, Zaamo (no lr/sc), Zba, Zbb, and a partial F (no fdiv/fsqrt). No C extension: its encoding space holds `.ttinsn`. ferrite compiles with plain `clang --target=riscv32-unknown-elf -march=rv32im` and links a flat binary at 0 with lld. Gotchas (ISA `BabyRISCV/`):

- `mhartid` reads 0 on every core per ISA; ttsim does not implement it and kills the process. Tell cores apart by entry point.
- `fence.i` does not flush the instruction cache (ttsim rejects it). New code needs a reset release, or a write to `RISCV_IC_INVALIDATE` in Tensix config from a core.
- The L0 data cache (4 x 16 B) is not coherent with NoC or host writes: poll L1 with a `fence` or an atomic in the loop.
- Stores to the same region (e.g. L1) are processed in order, so "write the result, then write the done flag" is safe. Across regions a `fence` is not enough: store, load it back, use the value, then signal.
- Unsupported instructions are undefined behavior, not traps.

Elsewhere on the chip, firmware is already running when we arrive: ARC runs the board management firmware and set up NoC translation and the PCIe windows; Ethernet core E0 runs Tenstorrent's Ethernet firmware.

## What tt-kmd does that a userspace driver must do instead

What kmd does for a Blackhole at probe, open, reset and remove (kmd `enumerate.c`, `blackhole.c`, `chardev.c`, `memory.c`, `pcie.c`), and where ferrite stands:

| kmd | ferrite |
|---|---|
| `pci_enable_device`, 58-bit DMA mask, bus mastering | `Card`: unbind kmd, write sysfs `enable`, set memory + bus master in `PCI_COMMAND` |
| Max Read Request Size 4096 in PCIe Device Control | `Card` sets it too (untested): reads of host memory, the dispatcher's ring among them, in requests of up to 4 KiB |
| Maps BAR0 TLB config + NIU, BAR2, BAR4; reserves TLB 201 for its own NoC accesses; hands other TLBs out per fd | `Card` mmaps sysfs `resource0` alone (BAR4's 32 GiB may not all be assigned), and reads and writes it a word at a time (8 bytes, or 4), never libc's memcpy, which may go a byte at a time on uncached memory (`test_card_copies`); it zeroes TLBs 0-31's strided multicast registers (`0x1FC009D8`, which kmd zeroes at each configure); with kmd gone every TLB but 201 is ours (`bh.TLB_COUNT` stops before it); ferrite uses TLB 0, and the next free one for each runtime's doorbell (TLB 1 for the first) |
| Waits for ARC: `0x80030408` bit 0 (500 ms); umd waits for `& 7 == 5` (300 s after a reset) | `Chip.__init__` waits for `& 7 == 5`, 2 s (tested on sim) |
| ARC messages `0xA0` (ASIC_STATE0, then reads `0x80030410` bit 1 for a power-cable fault), `0xC1` (watchdog, 10 s), `0xC7` (firmware log buffer); drops a response nobody read before sending | `Chip.__init__` sends `0xA0` first (unbinding kmd sent `0xA3`, ASIC_STATE3), and `Chip.arc_msg` drops a response left in the queue (`test_arc`); no watchdog or log buffer. It checks the PCIe tile's `NIU_CFG_0` bit 14 (the NoC translates coordinates, which `bh.py`'s are) |
| Power policy: with no fd open, ARC message `0x21` with all flags 0 (minimum AICLK, GDDR PHY down, **Tensix clock-gated**); opening an fd sends `0x7FFE0F21` (everything on); remove sends `0xA3` | `Chip.__init__` sends `0x21` with all 15 flags valid and set (`0x7FFF0F21`: max AI clock, GDDR PHY awake, Tensix and L2CPU on) through `Chip.arc_msg` (tested on sim). Never powers down again. Then `0x52` (AICLK go busy), as umd sends it, and up to 0.2 s for telemetry's AI clock to come within 5% of 1,350 MHz, as umd waits (`Chip.aiclk` keeps what it reads: 1,000 on ttsim, and the benchmark records it) |
| Pins host memory: IOVA from the IOMMU, or physically contiguous pages without one; programs an outbound iATU region so the device sees it at `0x1000_0000_0000_0000 + offset` | `Card.alloc`: a locked 2 MiB hugepage (`MAP_HUGE_2MB`, whatever the host's default size), bus address from `/proc/self/pagemap` (IOMMU off or passthrough). The device uses the bus address directly: kmd's own comment says an IOVA below 2^58 is a valid NoC address, so no iATU. With an IOMMU on, VFIO type1 `VFIO_IOMMU_MAP_DMA` would supply the IOVA; not written |
| One MSI, only for the firmware log | none needed |
| Reset: set `PCI_COMMAND` bit 6 as a marker, config writes `0x934 = 1` then `0x930 = 0x11` (or ARC `0x56` arg 3), wait >= 2 s, wait for the device to reappear and firmware to clear bit 6, restore config space and MPS (via DBI at NoC `(x,0)` `0xF800_0000_0000_0078`), wait for ARC again | `pci.reset` (`python3 -m ferrite.chip reset`): the same marker and config writes through sysfs `config`, polled until the marker clears or the card leaves the bus and comes back (10 s), then the kernel's own remove and rescan, which restore config space and MPS as at boot; `Chip` then waits up to 300 s for ARC. Untested |
| Telemetry table: `*0x80030434` (tags) and `*0x80030430` (values), each tag word is `id \| index << 16` | `Chip.telemetry`. `Chip.__init__` waits for ARC to publish the table, checks the tags it needs are there, takes the Tensix column count from tag 34 (enabled columns; good ones come first in translated x) and waits up to 300 s (umd's) for tag 22's two bits for each bank in tag 36 to leave 0: 1 is trained, 2 or 3 a failure, which it reports (umd retrains with `0xB6`) |
| "NoC cleanup": puts cores back in reset when a process dies, before its pinned memory goes | a `Runtime` halts its cores at exit (`atexit`), and before it takes its hugepage: a dispatcher left running would go on reading and writing a page the next process may get. A process killed outright still leaves its cores running until the next `Runtime` |

ARC messages (kmd `msgqueue.c`, umd `blackhole_arc_message_queue.cpp`): `*0x8003042C` (SCRATCH_RAM[11]) points at a control block whose word 0 is the base of 4 queues and word 1 is `entries | queues << 8`. Queue i (0 = kmd, 3 = applications) is a 32-byte header (`+0` request wptr, `+4` response rptr, `+0x10` request rptr, `+0x14` response wptr; pointers wrap at 2N) followed by N request slots and N response slots of 32 bytes (`u32 header, u32 payload[7]`). Write the slot, bump the request wptr, poke the ARC (kmd: write 0 to `0x800B0000`; umd: write `0x10000` to `0x80030100`), poll the response wptr for up to 1 s. Status is the low byte of the response header, below 240 means OK. ferrite uses queue 3 and umd's poke (ARC_MISC_CNTL IRQ0); ttsim models both pokes and answers kmd's and umd's messages, but kills the process on an unknown code, and returns all-zero responses (so `0x57` "get harvesting" is not usable there; telemetry is).

## The launch loop and the command queue

`ferrite/runtime.py`. Built and tested on ttsim.

**Cores.** `Runtime(chip, start, end)` takes a rectangle of Tensix in translated coordinates. Its last core runs the **dispatcher**; the rest are **workers**. A rectangle of good columns in translated space covers exactly those cores: harvested and non-Tensix columns in between opt out of multicast. The workers are also a grid of whole NoC rows (`Runtime.grid`: 9 rows of 12 on ttsim's 120 cores; the dispatcher's row is short and sits out), for kernels that multicast along rows and columns.

**L1 layout** (ours). A worker's tile:

| Address | What |
|---|---|
| `0x0` | firmware, starting with one jump per core: BRISC at `0x0` (its reset PC), TRISC i at `0x4 + 4i` (set as its reset PC) |
| `0x1000` | mailbox: `[go, kernel, arguments, workers] [done, the dispatcher's x \| y << 6, scratch, index]` |
| `0x1020` | the TRISCs' `[go, done 0, done 1, done 2]` |
| `0x1040` | `SYNC`: 64 bytes for a kernel's cores to talk through; its first 8 words (counters) are zeroed before each launch, the rest written before they are read |
| `0x1080` | `FLAGS`: 32 words for a kernel's workers to signal each other over the NoC, each written by one of them and zeroed by its own worker at the end |
| `0x1100` | two argument buffers (launches alternate) |
| `0x2000` | the loaded kernels, 500 KiB: each a header of four entry offsets, then a program per core |
| `0x7F000` | a tile of zeros, 4 KiB (an fp32 tile, whose second half is a bf16 one), written once at boot: the compiler's slot 0 |
| `0x80000` | kernel data (`L1_DATA`) |

The dispatcher's tile: firmware at `0x0`; config at `0x1000` (`[doorbell, ring lo, hi, ring size, status lo, hi, workers' rectangle, workers]`); its outbox at `0x1400`; the count of the workers' reports at `0x80000`; command staging from `0x80040`, above the kernels, since loading one writes the dispatcher's tile too.

**Boot** (host, once): multicast reset and worker firmware over the rectangle, a unicast mailbox per worker with its index and the dispatcher's coordinates, the dispatcher firmware and config over the top of the dispatcher's tile (its TRISC jumps park them), its count of reports and its outbox zeroed (a dispatcher before it on the same tile leaves its own there, which `wait` would read as this one's), a TLB of its own aimed at the doorbell, the TRISC reset PCs and their override bits, then multicast release of every BRISC and TRISC.

**Loaded kernels** (`Runtime.load`). A kernel goes into every worker's L1 once, by one multicast write over the rectangle, and stays: launches name its address. Images run wherever they land: clang's medany model reaches code and data PC-relative, with linker relaxation and jump tables off, and the header holds entry offsets. When the 500 KiB are full, the next load waits for the queue and evicts them all (`evict`, counted in `evictions`); a block of commands is sent as far as it goes first, since its later kernels would land where its earlier ones are (`Runtime.block`). A kernel's zeroed statics are zeroed again at each launch (`KENTRY` clears `.bss` before `kmain`), since nothing reloads it. Its TLB orders writes strictly, so a kernel has landed before the doorbell that launches it (to confirm on silicon).

**Commands** (host). A launch is one command (`Runtime.command`): a 16-byte header `[length, kernel address, argument bytes, workers]`, then the arguments, the same for every worker, 64-byte aligned. Commands go into a ring in host memory back to back, then the new write pointer into the dispatcher's doorbell (`Runtime.send`): the host's only PCIe access, for one launch or for a block of them (`Runtime.block`, a recording's; `test_queue` counts). Commands never straddle the ring's end: a header of length 0 marks the tail unused. Pointers are free-running 32-bit byte counts, so the ring size is a power of two, and the host waits (with a timeout) for the space the dispatcher has freed.

**The dispatcher** (BRISC firmware, about 1.2 KB), in a loop:

1. Poll the doorbell. Once it has run every command it read, read all the host has written since (to the ring's end, at most `STAGE`, 64 KiB) in one NoC read to the PCIe tile (19, 24), and run them from its L1: a read of host memory waits on PCIe (about a microsecond on a card, nothing on ttsim), so a recorded block of 358 launches costs a few reads rather than two a launch.
2. Multicast the arguments to every worker and wait for every acknowledgement.
3. Fire the go: the launch number, the addresses of the kernel and the arguments, and how many workers it is for, into every mailbox. It is always the same 16 bytes from its outbox, so request initiator 1 holds that multicast from the start, the outbox is written as soon as the command is in, and the go itself is one store.
4. Poll the count of reports until every worker has added to it, doing only that while the next launch is staged.
5. Write the launch's times (`profile`) and then `[read pointer, launches done]` into host memory, as posted writes (no acknowledgement) on one static VC. Two requests from one place to another on the same VC stay in order, the PCIe tile makes the VC the AXI ID and every write to the host a posted PCIe write, which keep that order (ISA, NoC ordering, written for Wormhole), so the host never sees a launch done before its times. The dispatcher waits only for their bytes to leave its outbox before it writes the next (`NIU_MST_WRITE_REQS_OUTGOING_ID`), never on PCIe, and their missing acknowledgements leave the multicasts' count alone.

One launch runs at a time, but the next command's arguments are written (into the other buffer) while the last one runs, so it goes as soon as the last worker reports.

**Multicast from a core** (the dispatcher's `multicast`): a write with `NOC_CMD_BRCST_PACKET`, path reserve and a static VC of class 2 (ttsim insists on all three), the rectangle in `NOC_RET_ADDR_HI` as `end | start << 12`, and `NOC_CMD_BRCST_SRC_INCLUDE` off, since the dispatcher sits in the rectangle it multicasts to and its L1 holds other things at the mailbox's address. Each recipient acknowledges, so `NIU_MST_REQS_OUTSTANDING_ID` goes up once and down once per recipient (ISA `NoC/Counters.md`): the dispatcher counts `NIU_MST_WR_ACK_RECEIVED` up to the number of workers instead, then clears the outstanding counters (`0xFFFF` at `NIU + 0x60`; ttsim takes nothing else), which is safe because nothing else is in flight then.

**A worker** (firmware for all four cores, about 680 bytes). BRISC, once at boot, presets request initiators 1 and 2 for `noc_get` and `noc_put` (`noc_setup`). Then, each launch:

- BRISC polls `go` with a `fence` in the loop, and sits the launch out if its index is not below the launch's worker count. It turns the arguments' first word, a number of units, into its own share `[first unit, how many]` (even, in order), zeroes `SYNC`'s counters, and invalidates the instruction caches of BRISC and the TRISCs (Tensix config 185, bits 0-3; then `fence`, read config back, `fence`, so the invalidate has landed before anyone jumps). It writes the TRISCs' go, calls its program, waits for the kernel's own transfers (`noc_wait`) and for the three TRISCs' done, notes the launch as done in its own mailbox (the host reads it if a launch hangs), and adds 1 to the dispatcher's count with a NoC atomic increment (`NOC_AT_LEN_BE` = `1 << 12 | 31 << 2`, a 32-bit add of `NOC_AT_DATA`; posted, so no counter moves at either end).
- A TRISC polls its go, calls its program (if the kernel has one for it), waits until its Tensix thread has run everything it pushed (`tensix_idle`, the Manual TTSync load), and writes its done.

**Launch cost.** A queued launch takes 146 cycles on ttsim (220 when the dispatcher read each command's header and body itself and waited for its two status writes' acknowledgements), and a one-tile add, launch included, 0.30k. The arguments and the go are one multicast each and the reports one counter, whatever the number of workers; a launch goes to no more workers than it has units of work (`Runtime.launch(kernel, args, units)`: GPT-2's attention kernels have a unit for each of its 12 heads); the dispatcher fires a go it set up in advance; the firmware zeroes only `SYNC`'s counters; and each program's setup is straight-line (`.ttinsn`, and stores for what a replay records). A card adds NoC latency to all of it.

**Profiles** (`Runtime.profile`, `test_profile`). The dispatcher reads its tile's wall clock (`RISCV_DEBUG_REG_WALL_CLOCK_L`, one count a cycle, ISA `DebugTimestamper.md`; ttsim's own clock) when it fires a launch's go and when it sees the launch's last report, and writes the pair into a ring of 1024 entries in host memory before the launch's status: every launch's time on the chip's own clock, with no polling in it. `Runtime.launch` takes a name (Tensor names a kernel by its ops, operands first: a softmax is "max2 sub exp sum2 recip mul"), and `profile(since)` adds up the launches after one by name. A GPT-2 token on ttsim (replayed, with its KV cache): plain matmuls 17k cycles in 37 launches, layer norms 8k in 25, residual sums 8k in 25, the MLP's up-projection with gelu 7k in 12, the attention projection with its bias 6k in 12, attention 6k in 12, the KV cache's puts 4k in 12, the embeddings 2k; 60k in all. `models/gpt2.py` prints this for its last token, the first profile to take on the card (ROADMAP, Stage 1).

**The host's part, and replay** (`tensor.jit`, `test_jit`). ttsim counts the chip's clocks only, so the host's Python never shows in its numbers; on a card it will. Building and issuing a GPT-2 token op by op takes the host 7.3 ms for its 140 launches, where the card should need about 0.5 ms to read the weights. Replay skips that work, as tinygrad's JIT does:

- `jit(f)` runs f's first call as usual and records its second: every launch (`Runtime.log`), and the DRAM the call takes stays taken (`Runtime.pinned`), since the replays write it again.
- Each later call copies its inputs into the second call's (a launch each) and sends the recorded launches as one block of commands, packed into the ring's bytes once (and again if the kernels they name have left L1: `Runtime.evictions`), with one write to the doorbell. Nothing is built or compiled. Where the kernels do not fit in L1 together (a training step's), `Runtime.block` sends the block in parts, one before each eviction, and packs it again every call.
- What it asks of f: inputs of fixed shapes and dtypes, nothing else it reads changing between calls, and no reading back. Its result is the same tensor every call, and so is every tensor it made and kept (a gradient in `.grad`); `assign` writes in place, so a recorded step can update its weights.

A decode step meets that with a KV cache of a fixed size and each token's place as data rather than a shape ("A Llama-family model"): a SmolLM-135M token, 358 launches, takes the host 0.1 ms replayed, against 21 ms built and issued op by op, and a GPT-2 token, 140 launches, 0.1 ms against 7.3. A training step does too, with its step's numbers as inputs ("Training"): 6.3 ms replayed on ttsim against 26 ms, most of it ttsim writing kernels back into L1, since a step's kernels are 552 KiB and L1 holds 500. On a card each launch costs the chip time too, a microsecond or more, so fewer launches a token matters there as well.

**Waiting** (`Runtime.wait`) polls the status words in host memory, never the chip. `Tensor` does not wait for its launches: they run in order, so each kernel sees the results of those before it, and only reading a result back (`tobytes`, `tolist`) waits. Reading back is a launch too (`readback_kernel`): the workers copy the tensor's tiles into host memory (the rest of the runtime's hugepage, about 1 MiB, so a bigger tensor goes in parts), and the host reads them there. Read over the BARs, each load would be a PCIe round trip. A tensor of fewer than 32 rows sends only the rows of each face that hold values: a token's logits, 1,536 tiles of one row, are 96 KB rather than 3 MB. A timeout counts from the last launch that finished (`until`): a long queue is not a hang, a launch that never finishes is. On timeout it reads the dispatcher's own count of launches done and each worker's mailbox, and names the workers that have not finished the next launch, or says that the chip has done them all and the status never reached the host.

**DRAM** (`Runtime.dram_alloc`, `dram_free`). A tensor takes the same address range in all 8 banks (tile i in bank i % 8). First fit over a sorted list of holes, 64-byte aligned; a freed block merges with the holes beside it. A `Tensor` frees its DRAM in `__del__`, which CPython runs as soon as the last reference goes, so intermediates and old results go back right away (a reference cycle would hold them until the garbage collector runs: `realize`'s walk is a plain function, not a closure, for that reason). A freed block goes back only once every launch queued before the free is done (`reclaim`), since those may still read or write it; an allocation that finds no room waits for the queue first. DRAM a recorded call took (`pinned`) never goes back. ttsim models 4080 MiB a bank.

**Device API**, prepended to every program (`DEVICE`): `noc_me()` (own translated coordinates, `NOC_ID_LOGICAL`), `noc_read`, `noc_write`, `noc_get`, `noc_put`, `noc_wait`, `l1_settle`. Requests go through NIU 0. `noc_read` and `noc_write` use request initiator 0, writing all nine of its registers; `noc_get` (a read into this L1) and `noc_put` (a write from it), each of at most one packet, use initiators 1 and 2, which the firmware sets up once at boot (`noc_setup`: the read or write command, this tile's coordinates on its side), so each writes only the four registers that change and the go: 17 RISC-V instructions a read. An initiator keeps its registers between requests (ttsim keeps four sets, `offset / 0x800`); tt-metal's "stateful" NoC calls do the same. Requests are acknowledged (`RESP_MARKED`), on a dynamic VC, and carry transaction ID 0, so `NIU_MST_REQS_OUTSTANDING_ID(0)` counts them, except a matmul step's reads ("Reads in flight"). Rules (ISA `NoC/MemoryMap.md`, `NoC/Counters.md`, enforced by ttsim):

- At most 16 KiB per request (`noc_read`/`noc_write` split; ttsim does not model hardware splitting).
- Source and destination agree in their low 4 bits for L1, low 6 bits when DRAM is involved.
- Reads must be acknowledged. Inline writes to L1 are broken on Blackhole; we never use inline writes.
- Wait for `NOC_CMD_CTRL` bit 0 to clear before touching an initiator; read `NOC_CMD_CTRL` back before reading counters.
- Before the NIU reads data a core just stored: `fence`, load from L1, `fence` (`l1_settle`). After data lands: `fence` before reading it (the L0 data cache). Every `fence` is also a compiler barrier (`"memory"` clobber), or the compiler can cache L1 across it.

**Not built yet:**

1. **Commands other than "launch":** host-to-DRAM copies, events, waiting on another queue.
2. **NCRISC**, a second data mover, stays in reset. It could take the sends home off BRISC, or fetch for a second NoC.
3. **Ordering of the host's ring writes before the doorbell** relies on x86 ordering cached stores before an uncached MMIO write. Fine on x86, and needs a barrier anywhere else.

## The Tensix coprocessor, and the compiler

`ferrite/compiler.py` (the kernels; `ferrite/tensor.py` builds the trees of ops they compute), encodings and register numbers in `ferrite/bh.py`. Tested on ttsim by `test/test_sim.py`, from `test_tile_math` on; each paragraph below names its tests.

**Who drives it.** Three Tensix threads, each an in-order instruction FIFO; any thread can issue to any unit (unpackers, FPU, packer, ...), the threads only differ in their per-thread state (ADCs, RWCs, GPRs, ThreadConfig). TRISC t pushes to thread t, through that thread's MOP expander; BRISC can push to all three (`0xFFE4_0000 + 0x10000 t`, skipping the MOP expander), but a BRISC push and a TRISC push in the same cycle drop the TRISC's, so only one of them may feed a thread. ferrite: each TRISC feeds its own thread and BRISC only moves data (ISA `BabyRISCV/PushTensixInstruction.md`).

**Instruction words.** `opcode << 24 | fields` (ISA `Diagrams/Src/Bits32.lua`; ttsim `data/bh/tensix_isa.json` agrees and names the fields). A TRISC pushes one by storing it to `0xFFE4_0000`, or by executing it: `.ttinsn` is the word rotated left by 2, written straight into the code (opcodes are below `0xC0`, so the low bits are never `0b11` and it cannot be read as RISC-V). Either way a full FIFO stalls the TRISC. The generated programs are mostly `.ttinsn` words (`compiler.tt`, as `.word`s, since clang has no `.ttinsn`), one instruction a word where a store takes three. A word that differs by Dst half or frame (a Dst row, a slot) is a store of the word with a C variable added (`field`: `h` is the half's first row, `fr` the tile's frame), so a fused kernel writes each tile's code once. What a `REPLAY` records goes through stores instead (`_pushes`): a TRISC fuses up to four `.ttinsn`s in a row, and fused ones must not be what it records.

**Configuration.** Three kinds, all needed:

- *Backend config*: 32-bit words at `0xFFEF_0000`, two banks (thread chooses with `CFG_STATE_ID`), a RISC-V store hits bank 0. The ISA docs name the fields but defer every index, shift and width to tt-metal's `cfg_defines.h`; ours come from ttsim's `tensix_regs.json` and must be checked on silicon.
- *Thread config*: 16-bit registers per thread, written only by `SETC16` from that thread, so they are set in-band at the start of the kernel. Reset values are undocumented, so every one we depend on is written.
- *ADCs and RWCs*: per-thread address counters (`SETADC*`) for unpackers and packer, and register-window counters (`SETRWC`) for the FPU.

TRISC0 writes the backend config, then `fence`, reads back a config word, `fence`, and only then pushes; it initialises the semaphores, waits for its thread to run all that (`tensix_idle`), and sets `READY` in `SYNC`. TRISC1 and TRISC2 push their own thread config and setup (address modes, replay recordings, the packer's counters: nothing that reads the backend config or a semaphore) and then wait for `READY` before anything else: the semaphores' power-on values are not documented. All of it is straight-line code generated per kernel, not loops over tables in L1, and the three set up at the same time.

**Tile layout** (ours; the ISA has no notion of a tile). A 32x32 tile is four 16x16 faces in row-major order (top-left, top-right, bottom-left, bottom-right), each face row-major: element (r, c) is at `(r//16*2 + c//16)*256 + r%16*16 + c%16`. An unpacker copies the 1024 datums linearly into Src rows, so face f is Src rows 16f..16f+15, which is what `MVMUL` wants; Dst and the packer keep the same order. Elementwise ops do not care. Tensors are tiles in row-major tile order, tile i in DRAM bank i % 8 at `base + i//8` tiles of its dtype (2048 bytes for bf16), a view's and a repeat's tile (i, j) of matrix b being tile `b // rep * bstride + i * stride + j + offset`.

**Precision.** Dst is kept in fp32 (`Fp32_enabled`); the packer rounds it to bf16 (`(bits + 0x8000) >> 16`, the only fp32-Dst-to-bf16 mode ttsim allows is `Read_32b_data` with In = bf16). With 4 fidelity phases a bf16 x bf16 product is exact before that rounding (bit-exact on 8192 random pairs). `ELWADD`/`ELWSUB` align the two 11-bit mantissas with round-half-up first, so about 0.4% of random sums differ from the fp32 sum by a last-place bf16 step. fp32 tensors would lose 13 mantissa bits in SrcA/SrcB (TF32), so they are unpacked into Dst and computed on the SFPU ("fp32 tensors").

**Where the docs and ttsim disagree.** `UNPACR` bit 7 is `MultiContextMode` in the ISA and `ovrd_thread_id` in ttsim; both say it must be 1. Bit 0 is "write 0" in the ISA, `last` (must be 1) in ttsim; we follow ttsim. The Blackhole README says "4x packer", the PACR page says one packer with four Dst read ports. `SETDVALID` is unsupported on Blackhole (use `UNPACR_NOP`). Blackhole's `addr_mode` field is 3 bits (bits 16:14 in ttsim's `tensix_isa.json`); the ISA pages are Wormhole's, with 2 bits plus an `ADDR_MOD_SET_Base` that Blackhole dropped.

### The pipeline

**Threads** (`fused_kernel`). Each thread has one job, so unpack, math and pack work on different tiles at the same time. L1 holds an array of tile slots; the unpackers' Z counter (Z stride: one tile) and the packer's channel-1 Y counter (that Y stride: one tile) pick the slot, so moving between slots never touches config:

| Thread | Job | Per tile (or matmul step) |
|---|---|---|
| 0 | unpack, and report | `SETADC` each unpacker's Z to its slot, `UNPACR` into SrcA and SrcB; after a frame or a matmul step, wait for the unpackers and `SEMPOST` SEM_UNPACKED |
| 1 | math | per result (the address modes for elementwise ops and matmul are all set at setup, so one kernel can mix them): `SEMWAIT` for a free Dst half, aim at it (`SETC16 MATH_Offset` = 0 or 64), zero it if the op accumulates (`ZEROACC` four 16-row blocks); the FPU program (one per matmul step); at the end: wait for the FPU, `SEMPOST` SEM_DST |
| 2 | pack | `SEMWAIT` SEM_DST, aim the packer at the Dst half (ADC ch0 Y) and the L1 slot (ADC ch1 Y), 16 `PACR`, wait for the packer, `SEMGET` SEM_DST, `SEMPOST` SEM_L1 (an intermediate) or SEM_PACKED (an output) |

Handoffs:

- **Unpack to math**: SrcA and SrcB have two banks each, and the hardware does the rest (`UNPACR` waits for a bank the FPU has released, the FPU for one the unpacker has filled).
- **Math to pack**: SEM_DST counts results in Dst waiting to be packed (max 2, one per half). Math waits while both halves are full, pack while none is.
- **Pack to unpack** (fused chains): an intermediate is packed into L1 and unpacked by a later op. Pack posts SEM_L1 for each; before an op that reads an intermediate, unpack takes one for every op packed since it last looked (`drain`). Packs happen in op order, so that covers whichever earlier op it reads (a plain count would not: the op might read an older intermediate than the one just posted).
- **Between BRISC and the TRISCs**: words in `SYNC`, each written by one core and read with a `fence` first (the L0 data cache never sees another core's writes). BRISC cannot read semaphores, so TRISC0 and TRISC2 relay theirs: they read SEM_UNPACKED or SEM_PACKED (TRISCs see the semaphores at `0xFFE8_0020 + 4i`), take one with a store of 1, and bump a count in `SYNC`. A semaphore holds 15, and a post onto a full one breaks the contract, so neither TRISC pushes a 16th report before it has relayed one: TRISC2's results wait for their slot to go home (two at most), and TRISC0's frames for BRISC's fetches (two ahead) and its steps for `landed`, which counts the reports out, since a step kept in L1 waits for nothing else.

| word | written by | means |
|---|---|---|
| `FETCHED` | BRISC | frames fetched; TRISC0 waits for the next before unpacking it |
| `ISSUED` | BRISC | matmul steps whose reads have gone out ("Reads in flight") |
| `UNPACKED` | TRISC0 | SEM_UNPACKED posts relayed; BRISC refills a slot once what was in it is unpacked |
| `READY` | TRISC0 | config and semaphores set up |
| `PACKED`, `RING` | TRISC2 | results packed, and where each is (slot) and goes (tile), four entries |
| `SENT` | BRISC | results sent home; TRISC2 packs into an output slot only after its last result there is sent |

**Four programs, one schedule.** A kernel is a program per core, all four running the same loops over units, passes and tiles, each doing its own part of every tile:

- BRISC: wait until the frame's slots are free (`UNPACKED`), fetch the tile's inputs, bump `FETCHED`; for a matmul, issue each step's reads into its stream slots and bump `ISSUED`. While it waits, it sends home whatever `PACKED` says is ready, in order, and bumps `SENT`. At the end, it waits until all its results are sent.
- TRISC0: wait for `FETCHED` (or a step's reads to land), relaying SEM_UNPACKED meanwhile; then the unpacks, `drain` before an op that reads an intermediate, and the report.
- TRISC1: the math, alternating Dst halves (it tracks `h` itself).
- TRISC2: the packs, tracking `h` the same way; for the result, first claim its output slot (`output`), then relay SEM_PACKED until every result is counted.

A result goes home as soon as it is packed, and the only waits between the cores are on data: a slot to be refilled, a tile to be unpacked, a result to be sent. No core waits for one that is waiting for it: every wait loop on BRISC also sends, and every one on TRISC0 or TRISC2 also relays.

**No push order to get right.** When BRISC fed all three threads through one stream of stores, a full FIFO stalled BRISC, so it could never queue work a thread would block on before pushing what unblocks it. With a TRISC per thread, a stalled TRISC holds up only its own thread, whose work waits on the others anyway.

**Replay buffers and address modes keep the pushes small.** Each TRISC pushes one instruction a cycle (four if they come in a row), so words per tile are its code and time per tile. Each thread has a 32-entry replay buffer (`REPLAY` with `load` records the next N instructions; without it, plays them back; it sits after the MOP expander). Each kernel's setup records the runs that repeat: one 16-`MVMUL` fidelity phase and one 9-word `ELWMUL` phase in the math thread, 15 `PACR`s in the pack thread. The last instruction of a sequence that also has to release the Src banks is pushed by itself with `clear_dvalid`. Elementwise ops use address modes 0-1 and matmul 4-7, all set once at setup, so a kernel can mix them with no per-op rewrites. Words pushed, all three threads together: 26 for an add or sub tile, 27 for a mul tile, 11 for a matmul step (12 when A streams too) and 17 more for its output tile; what is left is per-tile control (slots, Dst half, semaphores). `test_replay_keeps_pushes_small` holds these numbers, and a matmul by a diagonal of full-mantissa values, whose every output is one product exact only if all four fidelity phases ran, catches a replay one instruction short.

**Replay budget.** The math thread's 32 entries are shared out per kernel: SFPU bodies first (32 runs a tile, longest first), then the matmul and mul phases (4). A body's 32 runs are a loop on TRISC1 (`compiler.Loop`) of its one `REPLAY` word, or of its words if it did not fit, still correct, just more pushes; the loop keeps the code small (written out, the replays were a fifth of a training step's kernels) and costs nothing on ttsim, where the math thread runs ahead: the fp32-grade transcendentals (37 to 54 words) always go that way; reciprocal (12), sqrt (28), relu, the binary ops and the folds are replayed.

**ttsim's FIFOs.** ttsim runs each pipe's instructions in order, as many in a clock as can go ("How ttsim counts"). A TRISC's `.ttinsn` stalls while its thread's FIFO holds more than 52 entries, like silicon's stall on a full FIFO; stores to `0xFFE4_0000` have no such check there (only what a replay records and a few words worked out at run time, between `.ttinsn`s that stall, go that way), and a 512-entry overflow kills the process.

**Only slots below 256 can be unpacked.** An unpacker's input address takes only the low 8 bits of its Z counter (ISA `ADCs.md`; ttsim agrees, its Z is 13 bits wide but the unpacker sees 8), so frames, kept values and A's rows all sit below slot 256 (`UNPACKABLE`); what does not fit streams instead.

### Matmul

**One pair of tiles** (`compiler.matmul`). `MVMUL` does `Dst[8x16] += SrcB[8x16] @ SrcA[16x16]`: SrcB rows from its row counter (a multiple of 8), SrcA rows from its counter (a multiple of 16 in ttsim), Dst rows from the instruction's `dst` field plus the Dst counter. So the left tile goes to SrcB (unpacker 1) and the right tile to SrcA (unpacker 0). Output face (i, j) = sum over k of left face (i, k) @ right face (k, j): 8 face products of 2 `MVMUL`s each, 16 per fidelity phase, 4 phases (SrcA gives 5 mantissa bits a phase, SrcB 7). The `dst` field carries the output rows; the Src counters walk in the order i, k, h (half), j, which needs only four address modes (slots 4-7): SrcA +16 rows (next j), SrcA -16 / SrcB +8 (next h), SrcA +16 / SrcB +8 (next k or i), and the same plus fidelity +1 at the end of a phase. Counters wrap at 64, so that last step lands back on row 0. The last `MVMUL` of the last phase gives both banks back to the unpackers.

**Whole tensors.** A matmul is an op in a fused kernel (alone, it is a one-op kernel). Each worker owns some output tiles; each is K steps through the pipeline: the left (i, k) and right (k, j) tiles, 64 `MVMUL`s into the same Dst half, which accumulates over k in fp32; then one pack. Error on random bf16 inputs is under 2^-8 of sum |a*b| (1.4e-3 measured on 64x96 @ 96x128). Which tiles a worker reads, and how often, is what the rest of this section is about:

- **A's row stays in L1.** Each matmul in a kernel has a row of slots for A's tiles. A worker's result tiles run along rows, so while they stay in row i only B's tiles are fetched; A's row comes in with the steps of the first tile in a new row (`fresh`). Unpacker 1 walks the row by itself: its Z is set to the row's first slot once, and each step's `UNPACR` adds 1 (`AddrMode` bits 0-1, Ch0ZInc). A row that does not fit below slot 256 streams beside B.
- **Blocks.** With one matmul and no passes, a unit is a block of up to 4 x 4 result tiles, done column by column: the block's rows of A and its current column of B stay in L1, unpacker 1 walking A's row (its start worked out at run time and pushed with a store) and unpacker 0 walking B's column. Each A and B tile is read once a block rather than once a result tile. Part-blocks at the edges leave out the tiles past the matrix (`test_matmul_blocks` puts a canary after the result).

**Tiles shared between workers** (`Runtime.grid`, `test_matmul_multicast`). Workers sharing what they read is the only way below a block's reads. A matmul of more than one row of tiles, unbatched, alone in its kernel but for elementwise ops after it, gives grid worker (gy, gx) one block of the result cut to the grid (rows/9 by columns/12 tiles, rounded up, so as many workers are busy as the result allows):

- Each worker of a grid row reads its share of the block row's rows of A from DRAM and multicasts it along the row; each worker of a grid column reads its share of each of the column's columns of B in turn and multicasts it down the column, into one of three buffers.
- After every recipient has acknowledged a share comes its sender's flag (`FLAGS`: a word for each worker of a grid row, then of a grid column), multicast the same way and counting the shares that worker has sent. A worker waits for every flag of a column before computing it, and zeroes its own flags at the end of the kernel: it has seen every flag of the launch by then, and none is written before the next go (a new Runtime zeroes them too).
- Three buffers need no message to say one is free: a worker posts its share of column c only once its own unpacker is done with column c - 2, and a worker writing column c has seen every share of column c - 1, so every other worker is done with column c - 3, whose buffer c reuses.
- A multicast leaves the NIU's outstanding count wrong (up once, down once a recipient), so BRISC waits for everything else first and clears the count after, as the dispatcher does.
- When A's rows and three buffers do not fit below slot 256, `Tensor.matmul` cuts K into parts that do (`compiler.shared_k`), each part's matmul adding the sum of those before as its epilogue (rounded to bf16 between parts, as split K's are below).

The benchmark, 512x768 @ 768x3072, reads 1.00 times its inputs in 1.6k ttsim cycles; 512x3072 @ 3072x768 (GPT-2's MLP down, in parts) 1.2 times.

**A token's row, shared** (`bcast`, `test_matmul_multicast`). A matmul of one row of tiles (a token, or a few) gives each grid worker a block of the result's columns, and the first grid row reads A's tiles in shares and multicasts them to every worker, flagging each share as above; B, whose tiles no two workers share, streams in behind one wait for A. A batch (K split in parts) gives each matrix whole grid rows of its own, its blocks padded out to them, and its first row shares its part of A. So a token reads its activations once, not once a worker (`ferrite.bench 1 768 3072`: 1.0 times its inputs where it was 2.0).

**B's matrices picked on the chip** (`matmul(..., index=)`, `test_matmul_indexed`): a mixture of experts' matmul. Given an int32 (rows, k) tensor of indices, batch entry b of the result is row b // k of A (a batch of 1, or of rows times k by `repeat_interleave`) by the matrix of B its index picks, (b // k, b % k). BRISC fetches the indices' tiles, 32 tokens' each, before anything else (below `OUTS`, past the slots and a block float's buffers: room for 75, 2400 tokens a call) and adds `ids(b)` times B's batch stride to each of its tiles' addresses: nothing else changes, so B may be a block float, and a token's 8 experts are a batch that gets a grid row each, its row shared ("A token's row, shared"). The experts come from the chip's own choice, so a replayed decode step reads the experts its token chose, with nothing coming back to the host. Each entry is bit for bit the plain matmul by its expert.

**Split K.** A unit is at least a result tile, so a matmul with few of them leaves workers idle however long K is: a token's MLP down-projection, (5 x 3072) @ (3072 x 768), is 24 result tiles of 96 steps. When an unbatched matmul of one row of tiles has few enough result tiles that s times them still fit on the workers, and each part keeps at least 4 K tiles, `@` cuts K into s parts (2, 4 or 8; `split` of A's columns and B's rows, views, no copy), multiplies them as a batch, and sums the parts lazily, so the sum fuses with what comes after (the bias, the residual): the down-projection becomes 96 units of 24 steps. Each part is rounded to bf16 before the sum, one more rounding than Dst's fp32 sum over all of K; GPT-2's tokens stay numpy's but for one near tie ("GPT-2 small, the real thing"). On silicon it also spreads the weights' DRAM reads over more cores. A matmul of more rows keeps K whole: as a batch, its parts would lose the blocks' sharing above and each worker would read its own tiles, 2 to 3 times the inputs in all.

**Reads in flight** (`DEPTH`, 4). On silicon a DRAM read is long next to the step it feeds (a worker's share of the card's bandwidth moves a 2 KiB tile in about 500 ns, and latency comes on top), so a worker with one read at a time would wait on latency rather than bandwidth. Step k's reads carry NoC transaction ID k % 4 + 1 (the packet tag's bits 10-13; ISA `NoC/Counters.md`), and B streams through 4 slots (A, when it streams, through 4 more):

- BRISC issues a step's reads as soon as its slot is free and counts the step in `ISSUED`. Thread 0's TRISC, which waits for the step anyway, then waits for that ID's `NIU_MST_REQS_OUTSTANDING_ID` to reach 0, which the NIU decrements as each read's data lands in L1 (every core of a tile may read the NoC's registers). So up to 4 steps' reads are in flight a worker. A frame's reads keep ID 0 (`noc_wait`).
- The ordering this relies on (ISA `MemoryOrdering.md`): BRISC reads initiator 1's `CMD` back and fences before it bumps `ISSUED`, so the NIU has counted the reads first, and thread 0 reads the counter only after seeing `ISSUED` (its loop's branch orders the two loads).
- Thread 0 does the waiting because BRISC is the critical path: BRISC watching the IDs itself added about 30 instructions a step (a GPT-2 token, 111k cycles to 147k); thread 0 watching costs 3%. On ttsim reads land at once, so the depth itself shows nothing there; on the card, try other depths (bring-up step 10).

**Matmul precision.** A product of bf16s is exact after four fidelity phases and Dst sums in fp32, but the FPU adds each group of 8 products after aligning them to the largest at 12 bits (ttsim's model, `mvmul`), so a matmul is good to about 2^-12 of its larger terms, whatever Dst holds. Rounded to bf16 (2^-8) that never shows; written as fp32 it does: 1.6e-4 relative on 64 x 96 @ 96 x 70. An fp32 matmul goes as bf16x3 (each operand hi + lo, both bf16; hi@hi + hi@lo + lo@hi summed in fp32), which reaches that limit rather than bf16's 4e-3 rounding of the operands. hi is a cast; lo is the operand less itself rounded to bf16 by `ftob`, an SFPU program that rounds as the packer does (half up: the bits plus 2^15, the low 16 cleared), cast to bf16 in the same kernel. More would take the SFPU, or splitting the dot products so they do not share an exponent.

**Fewer fidelity phases** (`matmul(fidelity=)`, `tensor.FIDELITY`, `test_matmul_fidelity`). A phase multiplies 7 of A's 8 significand bits (SrcB: its top 7, or its last) by 5 of B's (SrcA: its top 5, or its last 3) (ISA `SrcASrcB.md`, `SrcAFidelityBits`). ferrite runs them in order 0-3 (top by top, top by B's last, A's last by top, last by last), and `SETRWC` puts every step back at phase 0, so a matmul can stop after any of them:

- Three phases leave out under 2^-11 of a product, two drop A's last bit (a truncation toward zero of up to 2^-7), one keeps 5 bits of B.
- Rounded to bf16, on random 128 x 768 @ 768 x 256: three phases are four's to the bit in error (worst 1.0e-3 of the sum of |products|, mean 1.0e-4); two give a worst 1.45e-3, mean 1.9e-4; one 6e-3 and, with all products positive, a 1.9% bias.
- GPT-2 at two and three phases keeps its logits within the 1.5 of numpy's it has at four; SmolLM at two picks numpy's 6 tokens out of 6 with logits within 0.54 (0.61 at four).

Four stays the default (exact products, as `test_matmul_exact` wants); fp32's bf16x3 matmuls always take four. On ttsim fewer phases cost the same (it runs queued `MVMUL`s at no cost); on silicon each phase is one `MVMUL` a 16 x 16 block, so two phases should double a matmul's math rate.

**Weights in BFP8 and BFP4** (`cast("bfp8")`, `cast("bfp4")`, `test_bfp`). A token reads every weight once, so on silicon decode waits on DRAM, and a bfp8 tile is 1088 bytes where bf16's is 2048: 64 exponent bytes, one for each run of 16 values (a face's row), then 1024 bytes of a sign and 7 bits of magnitude, a value being `magnitude * 2^(exponent - 133)`. From ttsim (`tensix.cpp`):

- **The cast is the packer's**: `Pack_out_format` BFP8 (6), `Exp_section_size` (config word 68, bits 16-31, in 16-byte units) 4. From an fp32 `Pack_in_format` it cuts each value to bf16 and rounds it once, half up, to its run's largest exponent; from a bfp8 one it first rounds to 6 bits, then again. So a cast to bfp8 packs from fp32 (the packer reading Dst 64 bytes a row), and matches a numpy model to the bit.
- **bfp4** is bfp8 with 3 bits of magnitude, two values a byte (the low nibble first): 576 bytes a tile. The unpacker shifts each up into bfp8's place and goes on as for bfp8, so everything below holds for both (one kind a kernel; `BFP` in compiler.py). The packer can make it too (from its bfp8, the low 4 bits dropped: toward zero), but 3 bits want rounding: SmolLM2-360M's MLP rounded so is 21% off and moves its logits three times as far as rounded to nearest (and changes its next token), so `cast("bfp4")` is a BRISC kernel of its own (`bfp4_kernel`) that takes each run's largest exponent from the bf16 values and rounds each to the nearest 3 bits, as Tenstorrent's host conversion does (ties up where it takes them to even), whole words in and out.
- **The unpacker** makes each value the bf16 it is (7 bits fit in bf16's 8) on its way into SrcA, and `MVMUL` multiplies it like any other; its out format must say bfp8 too. It finds slot z's exponents at `base + 64 z` and its values after an exponent section as long as the tile descriptor's Z dimension makes it (64 bytes a slot), at `+ 1024 z`, and a slot's first datum must stay below 65536, so 64 slots at most. bfp8 tiles cannot sit in the 2 KiB slots: a matmul's bfp8 B goes in regions of its own past slot 255 (`B8`), exponents first, BRISC reading each tile there in two pieces (`getb`): slots to stream through, a block's column (up to 64 tiles of K), or one region for each of the multicast matmul's three buffers, each share multicast in two runs, its exponents and its values.
- **Switching**: thread 0 sets unpacker 0 to the block float and the region for the matmul's steps and back after (`bfp_b`: format, out format, Z dimension and base, written a byte at a time with `RMWCIB` between `STALLWAIT`s, as `haloize` switches the transpose), so what follows the matmul in its kernel (a bias, gelu, another matmul) unpacks bf16 as before.
- **Results**: a matmul by a bfp8 or bfp4 B is bit for bit the bf16 matmul by the same values, whichever way B comes in. With their weight matrices in bfp8 (numpy given the same values; `models/gpt2.py ... bfp8`), GPT-2 picks numpy's token 8 times of 8 and SmolLM 6 of 6, each writing the same text as with bf16 weights; a GPT-2 token reads 131 MB of weights where bf16 reads 247 MB.
- **On ttsim** a bfp8 matmul costs about 30% more cycles than a bf16 one, BRISC's second read a tile; on silicon the two reads take a few nanoseconds against the 250 ns or so the tile's bytes take. Whether silicon finds bfp8 slots where ttsim does waits for the card.
- **A KV cache in bfp8**, as Tenstorrent's models keep theirs (`test_bfp8_cache`). `put` writes bf16 rows into a bfp8 tensor, each run of 16 rounded as the cast rounds (to its largest exponent, half up; a 0 without its sign, which the unpacker would read as -inf), a run's exponent byte and its 16 value bytes written in place in the tile. Attention reads it as it lies: its values as a block-float B, its keys as a block-float B read transposed (`("Tbfp8", input)`: fetched as any block float is, unpacker 0 transposing each face of it on its way in and the math walking the faces transposed, "Transpose"), each key and value head repeated for the query heads it serves (`repeat_interleave`, in place). Both matmuls are bit for bit the bf16 ones by the same values.

**Weights in FP4.** DeepSeek V4 Flash's and MiMo-V2.6-Flash's experts come in FP4 (E2M1: a sign, 2 bits of exponent and 1 of mantissa, so 0, 0.5, 1, 1.5, 2, 3, 4 and 6), two to a byte, each 32 along the input axis sharing a power of 2, as gpt-oss's MXFP4 does. No unpacker format reads E2M1 (ttsim's `tensix.cpp`: its 4-bit format is bfp4, and FP8's E4M3 and int8 take 8 bits). bfp4 cannot hold them: in a run of 16 whose largest value is 4 or 6 times its scale the smallest step is 1, so its 0.5s and 1.5s round. On DeepSeek V4 Flash's block 3 (experts 0 and 1: gate, up and down), bfp4 moves 17% of the weights and half the runs and puts each matmul's result 12% off (by its norm, for Gaussian inputs), with the runs along the input axis or the output's alike; bfp8 moves none, either way. So such a model is held exactly at about twice the bytes it ships in (DeepSeek V4 Flash: about 300 GB against 160). Measured by a script outside this repository (`cmp/fp4/fp4.py`, beside the others COMPARE names) that fetches the experts' tensors by HTTP range and rounds them with `gpt2.bfp`.

### Fusion

**Fusion** (`fused_kernel`, `Tensor` is lazy). Ops build a tree; `realize` (or `tolist`) compiles the whole tree into one kernel, so `(a @ b) * d - c` or `(a @ b) + (e @ f)` is one launch. A matmul's own operands are realized first: each of its output tiles needs a whole row and column of them. Equal subtrees become one op. Slot 0 is the runtime's zero tile, then come the matmul stream slots; per output tile, a frame of slots holds the elementwise inputs, then one slot per op in post order; the last is the result. BRISC fetches the inputs into the frame; then, op by op, an elementwise op is unpacked from its operands' slots, computed into the next Dst half and packed into its own slot, or a matmul runs its K steps and is packed. Intermediates live in L1 only, and only the result goes to DRAM. Two frames alternate, so tile n + 1 is fetched while tile n computes, and results go home while both happen. Every intermediate packed into L1 is rounded to its dtype, exactly as it would be on its way to DRAM, so a fused chain is bit for bit the same as one launch per op (`test_fusion` checks); only a unary op run in place sees the unrounded result ("Where a unary op runs"). A single op is just a one-op chain. A kernel computes in one dtype (its root may be written in another, a cast), and its matmuls read realized tensors (no fused prologue).

**Too big for one kernel.** A kernel holds at most 15 ops (SEM_L1 is 4 bits). `realize` counts the ops a kernel would get and, while there are too many, realizes a part on its own first (`_fit`): a value two of the tree's ops read, the biggest that fits (the residual stream an RMSNorm reads twice), else the first part that fits down the operand with the most ops, so what is on top (a layer norm) stays whole.

**Numbers.** A number in an expression is a 1 x 1 tensor of its tensor's dtype, uploaded once a runtime (`Runtime.numbers`). In a kernel without passes it gets a slot of its own, read once by each worker rather than once a tile (`test_numbers_once`: `x * 0.5 + 1.5` over 768 tiles reads x and two tiles a worker), placed past any matmul's rows and buffers.

### Elementwise

**The SFPU: tinygrad's elementwise primitives** (`compiler.SFPU`). A 32-lane fp32 vector unit that works on Dst, issued from the math thread right after the FPU, over the same Dst half. Facts (ISA `VectorUnit.md`, `SFPLOAD.md` and the per-instruction pages; ttsim `tensix.cpp`):

- LRegs 0-7 are writable; 8 = 0.8373, 9 = 0.0, 10 = 1.0, 11 = -1.0 are constants. Writing 12-15 configures load macros instead of computing, so never use them as a destination.
- An `SFPLOAD`/`SFPSTORE` moves 4 Dst rows x 8 columns (even columns at address 4r, odd at 4r + 2). So 32 of them cover a tile, and the address is the instruction's immediate plus the Dst counter plus the math thread's `MATH_Offset`. With fp32 Dst use mod0 3; the 16-bit modes address raw rows.
- We load with address mode 2 (no step) and store with 3 (Dst counter + 2), so one body repeated 32 times walks the tile: a loop of one `REPLAY` word where the body fits the replay buffer, of its words where it does not ("Replay budget").
- `SFPMAD` is a fused multiply-add with one rounding; denormals flush to zero in and out. Blackhole stalls for the 2-cycle MAD latency by itself (Wormhole needed `SFPNOP`s), with listed exceptions none of our programs hit.
- `SFPSWAP` mod 1 leaves the min in vd and the max in vc. `SFPARECIP` (Blackhole only) is a reciprocal estimate within 0.6%: inf for 0 and denormals, 0 above 2^126. There is no exp instruction in ttsim (`SFPARECIP` mode 2 is rejected).
- Condition codes are shared by all threads: `SFPENCC` mod 10 imm 3 turns lane flags on with all lanes set, mod 0 sets them all again, mod 10 imm 2 turns them off. `SFPIADD` with an immediate narrows the enabled lanes (mod 1: where the sum is negative, mod 9: where it is not), `SFPSETCC` mod 0 sets them where a value's sign is set, and while flags are on every instruction writes only enabled lanes, `SFPLOADI` included, so a constant loaded then is a conditional assignment.
- `SFPGT` mod 8 (Blackhole only) writes all ones where vd > vc as ordered floats (sign and magnitude, so -0 < 0) and 0 elsewhere, a mask for `SFPAND`, `SFPOR`, `SFPNOT`. `SFPEXEXP` mod 1 gives the biased exponent as an integer, `SFPSETEXP` mod 1 replaces the exponent with an immediate, `SFPCAST` mod 0 turns a sign-and-magnitude integer into a float. `SFPMAD` rounds to nearest even (ttsim's model, Blackhole), so adding and taking away 1.5 2^23 rounds to an integer, and x * 1 + 0 turns -0 into 0.

The programs are tinygrad's elementwise primitives: exp2, log2, sin, sqrt and reciprocal; max, cmplt and cmpne; where. Everything else in `Tensor` is built from them, as in tinygrad (`minimum` is `-max(-x, -y)`, `rsqrt` is `sqrt().reciprocal()`, `==` is `1 - (x != y)`), except that exp, log and cos are programs of their own. Their constants (log2(e), ln 2, a quarter turn) stay in fp32 inside the program; as numbers they would be bf16 tensors, and exp(10) as `exp2(10 * log2(e))` with log2(e) rounded to 8 bits is 2% off.

Each transcendental reduces x to a small range by exact steps, then a polynomial (fit offline toward minimax, coefficients as fp32 literals) does the rest, so fp32 tensors get fp32's accuracy: within a step or two of numpy's float32 (2^-23 is 1.2e-7), checked in `test_fp32`. Over the whole fp32 range:

| program | error | at |
|---|---|---|
| exp2, exp | 8e-8 relative | x in [-126, 128], [-87, 88.5] |
| log2, log | 9e-8, 1.6e-7 relative | x from 1e-35 to 1e35, and near 1 |
| sin, cos | 1.0e-7, 1.6e-7 absolute | \|x\| up to 200; 3e-10 and 3e-8 within 1e-3 of a zero |
| sqrt, rsqrt | 3 ulps (1.5e-7) relative | x from 1e-3 to 100 |

- **exp2, exp**: n = round(t), t = x or x log2(e) (adding and taking away 1.5 2^23 rounds to an integer and leaves it in the sum's low bits, where an integer subtract reads it), r = (x - n) ln 2, or for e^x x - n ln 2 in two parts (Cody-Waite: n times 0.693359375, 9 bits, is exact), e^r by 7 coefficients on [-ln2/2, ln2/2], then times 2^floor(n/2) and 2^ceil(n/2), each built from its exponent bits. x is held to |t| <= 150 first, which sends a NaN to an end, so in an fp32 kernel (`fexp`) a NaN lane (`nans`: |x| past inf's bits in `SFPGT`'s total order) gets x back at the end. Two multiplies, not adding n to the exponent: they overflow to inf and flush to 0 exactly where the result does (2^127.5 is finite though n is 128).
- **log2, log**: x = 2^e m, m in [1, 2) (`SFPEXEXP`, `SFPCAST`, `SFPSETEXP`), halved where above sqrt 2 with e one more (`SFPGT` sets the lanes), so u = m - 1 is in [-0.29, 0.41] and `log2(x) = e + u q(u)`, q of 9 coefficients, relative, so log2 near 1 keeps its digits (just below 1 there is no cancellation of e = -1 against log2(m) near 1). Times ln 2 for log. Edges by lane flags: inf and NaN give themselves, negatives NaN, zero -inf.
- **sin, cos**: k = round(x / pi + phase), phase 1/2 for cos, r = x - k pi in two parts (3.140625, 8 bits, then the rest; what is left of x is within a factor of 2 of it, so exact), plus pi/2 in two for cos: r is in [-pi/2, pi/2], `sin(r) = r p(r^2)` by 5 coefficients, and k's low bit, shifted to the sign and `SFPXOR`ed in, gives (-1)^k. (Reducing in turns instead, folded at 1/2 - f, loses digits at the fold, as an fp32 model of the program showed.) From |x| = 2^24 on, an fp32 x is a whole number and the rounding trick fails: 0 there; inf and NaN give NaN.
- **sqrt**: x + 0 (so -0 is 0), the bit trick `0x5F3759DF - bits(x) / 2` for 1/sqrt(x) (within 3.5%), three Newton steps `y *= 1.5 - x/2 * y^2` (two leave 80 ulps), times x: within 3 ulps. Edges: 0 (where the Newton steps would overflow), inf and NaN give themselves, negatives NaN.
- **reciprocal**: the `SFPARECIP` estimate and two Newton steps `y += y(1 - xy)`, only in lanes where x is a normal number. 0 and inf would make `0 * inf = NaN`, so those lanes keep the estimate (inf and 0), and in an fp32 kernel (`frecip`) a NaN's lane gets the NaN back.
- **relu**: `max(x, 0)` with one `SFPSWAP` against 0.
- **max, cmplt, cmpne** take two operands, which the SFPU only sees in Dst: the unpacker and FPU put x + 0 in the op's Dst half and y + 0 128 rows on, and the program loads both and stores over x. `SFPSWAP` gives the max; a comparison is an `SFPGT` mask (both orders, ORed, for cmpne) ANDed with 1.0's bits, after x + 0 has made -0 into 0. `SFPGT`'s total order puts NaN past inf, so in an fp32 kernel cmpne also ORs in x being NaN (NaN is not itself) and cmplt ANDs in neither being NaN, as IEEE has them (`fcmpne`, `fcmplt`).
- **where** has a third operand and Dst has no room for one (fp32 Dst is 512 rows, and the halves, the scratch and the accumulators fill them), so `c.where(x, y)` is `keep(c, x) + drop(c, y)`: two binary programs that AND x, or y, with the mask `|c| > 0` (or its complement), and an add. Each pick is exact and the add has a zero on one side, so `where` is exact, and an inf in the side not picked does not turn into a NaN as `c * x` would. A masked softmax can use -inf (`test_elementwise`).

In fp32 a NaN goes through every program as IEEE says (`test_fp32`). In a bf16 kernel a NaN is inf before the SFPU sees it (and packing to bf16 makes one inf too), so its programs take no time for NaN: exp's NaN check, 8 words of each of its 32 runs a tile, made a softmax 60% slower. `test_sfpu` and `test_elementwise` feed ±inf, ±0, a denormal and ±1e30 to every program, and compare comparisons and picks with numpy exactly.

**Where a unary op runs.** In place, on the Dst result of the op below it, if nothing else reads that result (`relu(a @ b + c)` is two ops in one kernel, the matmul and the add, with relu run on the add's result). Otherwise its operand goes through `x + 0` (slot 0 is the runtime's zero tile) into Dst first. In place it sees the fp32 result, not one rounded to bf16, so it can be more accurate than op by op: `exp(x + y)` fused is `exp` of the fp32 sum.

**gelu** is GPT-2's tanh form, built from what is there: `0.5 x (1 + tanh(z))` is `x / (1 + e^(-2z))`, so `x * (1 + exp(x (-k c x^2 - k))).reciprocal()` with `k = 2 sqrt(2/pi)`, `c = 0.044715`. One kernel; within 2% of numpy after the bf16 rounding of each step.

### Reductions and passes

**Reductions** (`sum(axis)`, `max(axis)`, numpy's with the axis kept as 1; `reduce_step`, `ACROSS`, `MASK`, `COMBINE`). Axis 0 folds the batch into one matrix, axis 1 the rows into one row, axis 2 each row into one column. Each tile along the axis is unpacked beside the zero tile (the runtime's) and added to zero into Dst. The first goes into an accumulator (Dst rows 256-319, or 320-383 for a second reduction in the same pass). Each later one goes 128 rows further on, where an SFPU pass folds it in: load both, `SFPSWAP` for max or a multiply-add by 1.0 for sum, store; 32 passes of 4 words, replayed. The line's last tile is masked first if it is cut short (`MASK`: `mask_columns` for axis 2, `mask_rows` for axis 1; the batch has no padding).

At the end of the line, the accumulator is folded inside the tile (`ACROSS`), so the result fills its tile and broadcasts as it is:

- **Along each row** (`across_rows`): row r sits in Dst rows `(r // 16) * 32 + r % 16` (columns 0-15) and 16 rows on (16-31), so four `SFPLOAD`s (even and odd columns, both faces) hold 4 rows, a row per 8-lane group. After folding those four, `SFPSHFT2` mod 3 rotates each group by one lane; rotating by 1, 2 and 4 and folding each time leaves the row's result in all 8 lanes, which goes back to all four places. 8 groups of 21 words, pushed directly since the addresses differ.
- **Down each column** (`across_cols`): column c is one lane of the loads at the even or odd addresses of its two faces, a row of it in each 8-lane group, so 8 loads fold to one register holding four partial results, one per group. `SFPSHFT2` cannot cross groups; `SFPTRANSP` (ISA `SFPTRANSP.md`, ttsim `tensix.cpp`) treats LRegs 0-3 as a 4 x 4 of lane groups and transposes it, so three copies and one `SFPTRANSP` put each group across a register of its own, and folding the four leaves the column's result in every lane, which goes back to all 8 places. 4 runs of 30 words.
- **Through the batch**: nothing; the tiles were folded as they came.

Each accumulator has a semaphore (1 while free): the first step of a line takes it, and the pack gives it back, so the next line cannot overwrite an accumulator still being packed. Sums are fp32 throughout, rounded once. `test_reductions`, `test_reduce_axes` (exact maxes of all-negative values with the last tile cut short, so the masks are tested), and `test_fuzz`, which draws the axis at random.

**Lines in passes, one launch** (`fused_kernel`). If an expression reduces, a work unit is a whole line of tiles along the axis (a row of tiles, a column of them, or one tile position through the batch), and each worker owns lines. A line is done in passes, each a sweep along it; a reduction's result is readable only in the pass after the one that swept its operand, and each pass recomputes what it needs rather than keep whole lines of intermediates in L1. Softmax, `e * e.sum(2).reciprocal()` with `e = (x - x.max(2)).exp()`, is three passes in one launch:

1. Sweep x into the row max.
2. Compute e tile by tile and sweep it into the row sum; the reciprocal runs in place on the accumulator.
3. Recompute e and multiply by the reciprocal.

What a line reads comes from DRAM once:

- An input read in more than one pass keeps its line of tiles in L1 from the first (while the line fits below slot 256), and one a tile long along the axis (a constant, a row's scale) gets a slot of its own, fetched once a line. BRISC refills a kept slot for the next line once the line before's last read of it is unpacked. The unpackers find a kept tile by its place along the line, so its slot is worked out at run time: a `SETADC` stored with the slot added.
- A matmul computed in more than one pass (attention's scores, under a softmax that sweeps them three times) keeps its B's tiles for the line in L1 from the first pass, with A's row. The scores and softmax of one 64-wide head over 512 tokens read 2,352 tiles; each line still reads all of kᵀ, which the lines of a head could share.
- Values one tile long along the axis (reduction results, ops on them like `x.sum(2) * (1/n)`, inputs of 1 there) are computed once per line, in the first tile of the pass that needs them, into slots of their own after the two frames.

A kernel reduces along one axis: `_tree` takes the first reduction's, and a reduction along another axis is computed first, on its own, as is an op that is 1 along an axis the kernel keeps (it would repeat there). `realize` also works out first, on its own, a long matmul (K over 256 columns, which each pass would recompute), and an elementwise value that a reduction reads and something else reads too: GPT-2's residual stream is a lazy sum (x, the bias and a split K's parts) by the time a layer norm reads it, and realized first it runs a tile per worker, where inside the norm's kernel it would run on as few workers as there are rows.

Book-keeping happens at run time, in each program, because what a tile does depends on whether it is a pass's first or last: which Dst half each op gets (TRISC1 and TRISC2, each counting the same way), how many `SEM_L1` posts an unpack must take before reading an intermediate (TRISC0 takes all packed so far: `drain`), and which frame or stream slot is free again (BRISC, counting thread 0's reports the way TRISC0 pushes them).

**Softmax and layer norm** (`Tensor.softmax`, `layernorm`; `test_softmax_and_layernorm`) are built from these:

- softmax: `e = (x - x.max(axis)).exp(); e * e.sum(axis).reciprocal()`
- layer norm: `d = x - x.mean(axis); d * ((d * d).mean(axis) + eps).rsqrt()` (the caller applies gamma and beta), with `mean` a sum times `1/n`

Each is one launch, matching float64 to about 2% (softmax) and 0.05 + 2% (layer norm), the bf16 rounding of each intermediate. A 64 x 768 softmax reads x once (1.20k ttsim cycles), a layer norm 1.08 times (0.40k).

### Shapes and movement

**Any shape** (`Tensor`, `fused_kernel(shapes=...)` takes each input's (batch, rows, columns)). A tensor is padded to whole tiles, and the padding has one rule: zeros, except that a dimension of 1 fills its tile with copies (a row vector's tile holds the row in all 32 rows, a column's in all 32 columns, a scalar's everywhere). Uploads follow it, and so does every kernel's result:

- **Results go home tidy.** In a tile at the result's last row or column, the math thread zeroes the padding in Dst before the pack (`mask_columns` with 0, `mask_rows`: SFPU stores into the lanes past the edge, picked as below). Inside a kernel the padding is whatever the ops made of it (`exp(0)` is 1); in DRAM it is zero, so a matmul can sum over a padded K: zero columns of A meet zero rows of B. (Multiplying by a 0/1 mask instead would not do: an inf in the padding times 0 is NaN.) A dimension of 1 stays filled by itself: an op on filled tiles gives filled tiles, a row reduction writes all 32 columns, and a matmul with a filled B gives a filled result.
- **Reductions mask their last tile.** Padding would count in a sum, and with all values negative a padding 0 would win a max. After the last tile of a line lands in Dst, an SFPU pass (`mask_columns`, or `mask_rows` down the columns) stores the identity (0, or -inf for max) into the columns past the edge. Which columns an `SFPSTORE` lane holds is fixed (lane l of a store at an even or odd address: column 2 (l % 8) or one more, plus 16 in the right faces), and `LReg[15]` holds 2l in every lane (ISA `LReg.md`; ttsim agrees), so `LReg[15] & 14` compared with the first padded column (`SFPIADD` with an immediate, flags on) enables exactly the padded lanes, and the store only writes enabled lanes. 32 stores at most, only in a row's last tile.
- **Broadcasting is numpy's**: shapes match, or one side has 1 where the other does not; a number is a 1 x 1 tensor. It is tile reuse, not a hardware broadcast: the fetch for output tile (i, j) takes the 1-wide input's tile (i, 0), (0, j) or (0, 0), and the filling makes that tile right everywhere. A computed operand one tile wide stays in the expression and is worked out once per row in a kernel that sweeps rows in passes, for each tile that reads it otherwise; one with a single row (repeated down) is realized first in its own kernel. `sum(2)` and `max(2)` give a column (rows x 1), `sum(1)` and `max(1)` a row; along an axis that is already 1 they are the tensor itself (32 copies would add up). `(R, 1) @ (1, C)` is broadcasting, not a matmul (a filled K would add up 32 times). A row reduction whose operand is one tile wide inside a wider kernel is reduced in the pass's first tile, not swept once per column tile (`test_any_shape`).

**A batch dimension** (`Tensor(..., batch=)`, `shape` is (batch, rows, cols)). A batch is its matrices one after another in DRAM; a batch of 1 repeats across a bigger one (broadcasting, as numpy's leading dimension). Kernels take each input as address and tile strides for batch and row plus an offset, and units run through the batch. Elementwise ops, reductions and matmul (matrix by matrix, or by one matrix for all) all work on batches. `x.split(n, axis)` cuts a matrix into a batch of n in place, which is how attention's heads become a batch: GPT-2's attention is two batched kernels (scores with softmax, then times the values) instead of a loop over twelve heads (`test_batch`).

**Views** (`x[b]`, `x[rows, cols]` or `x[batch, rows, cols]` with step-1 slices on tile boundaries, `split`). A view shares its owner's DRAM: tile (b, i, j) of the view is tile `b * bstride + i * stride + j + offset` of the owner's, and every kernel takes each input as (address, batch stride, row stride, offset), so views go straight into kernels with no copy. The view keeps its owner alive, and only the owner frees. A view ends on a tile boundary or at the tensor's end, so its padding follows the rule too; any other slice is a move (below). GPT-2's q, k and v are views of one qkv result, split into heads by `split`. `x.repeat_interleave(n)` repeats each matrix n times along the batch in place: a kernel reads its matrix b as the one stored at b // n (the n compiled into the kernels that read one; a move, transpose or gather, which read tiles by their place, gets a copy). Grouped-query attention's keys and values serve each query head this way, with no copy.

**Results into views** (`realize(into)`, `merge`). A fused kernel takes its result's address and strides the way it takes each input's, so it can write into a view of another tensor: `x.merge()`, the inverse of `split`, realizes a batch into the column blocks of one matrix, and the realized batch becomes a view of it. Attention's heads come back side by side this way, with no copy.

**Transpose** (`x.T`, `transpose_kernel`). Result tile (i, j) is input tile (j, i) transposed. BRISC fetches the tile face by face with the two off-diagonal faces swapped (four 512-byte NoC reads), and unpacker 0 transposes each 16x16 face on its way into SrcA (`Haloize_mode`, backend config word 72 bit 8; ISA `UNPACR_Regular.md` swaps the row's low 4 bits with the column; unpacker 1 ignores it); then `x + 0` through the FPU, which is exact. `.T` is lazy: a matmul whose B is a transpose reads it that way itself, each tile as it lies (one read), with `Haloize_mode` on for unpacker 0 around its K loop (`haloize`: a `STALLWAIT` that holds the config unit until unpacker 0 has finished, `RMWCIB1` on byte 1 of word 72, a `STALLWAIT` that holds the next unpack until the config unit has), and the math thread walking the faces where they lie: B^T's face (k, j) is SrcA's face 2j + k, so SrcA steps by 32 for the next j or h, by -16 for the next k and by 16 for the next i, five address modes where an untransposed B needs four (`matmul_phase(transposed=True)`, recorded as `mmT`; `walk` rewrites slots 4-6 and 2 around the matmul's steps and puts them back), as Tenstorrent's own matmul walks a transposed operand. Anything else realizes it with the transpose kernel, which fetches each tile face by face, the off-diagonal faces swapped (an elementwise op walks faces in order), with the bit on throughout (bf16; an fp32 or int32 transpose is a move). Reading transposed costs what reading costs: GPT-2's attention, which reads its keys transposed, went from 5.69k ttsim cycles a token to 4.86k when a key tile became one read rather than four quarter-tile ones (`test_matmul_multicast` counts them). A weight read every token is still transposed once at load (`wte.T`, from when a transposed read cost four). Breaking `haloize` fails `test_batch`; breaking the walk fails it, `test_matmul_multicast` and `test_gpt2_layer`.

**Movement at any granularity** (`reshape`, `permute`, `expand`, `pad`, slices at any offset and step, numpy's; `Tensor._move`, `Tensor._map`, `move_kernel`). Each is one map from the result's elements to the source's: element (b, r, c) of the result is element `offset + b sb + r sr + c sc` of the source counted in row-major order, inside per-axis bounds `lo <= . < hi`, and 0 outside. A permute permutes the strides, an expand sets a stride to 0, a slice moves the offset and multiplies the strides by the steps (negative ones too), a pad moves the offset back and sets the bounds, and a reshape reads the source in order. Swapping rows and columns of bf16 stays the Tensix transpose above, and slices of whole tiles stay views.

- **The kernel** is BRISC alone, since a NoC read cannot put 2 bytes just anywhere. It loads and stores 2 bytes at a time in L1, which ttsim allows and silicon should (rv32im has them; bring-up step 7), and fetches source tiles whole into a cache in L1 as it needs them (127 slots, by tile number mod a prime so that power-of-two strides spread out).
- **A result tile** that is a source tile as it is (a pad, slice or cat on tile boundaries) comes by one NoC read; one that is a source tile transposed (`.T` of fp32 or int32) is transposed face by face, the off-diagonal faces swapped. Any other starts as a NoC copy of the runtime's zero tile, so padding and everything outside the bounds cost nothing, and takes the datums inside the bounds in lines along its rows or down its columns, whichever lie in the source as runs (along a source row or down a source column), the longer if both. A run is copied up to a face's edge by stepped pointers; a line that is not one steps through the source by its stride, split once into matrices, rows and columns, so no datum takes a division (a negative step finds each place again by dividing).
- **A dimension of 1** fills its tile as the padding rule wants, so a moved tensor goes straight into any kernel: a column is made once and copied across, and a row is made once and doubled down the tile by NoC copies inside L1, as `gather` does.
- **A chain of moves is one launch.** A permute, expand, pad or slice (`_map`) says for each axis of its result which axis of the source it reads, from where and by what step, so on a move not yet made it composes with that move's map, and the bounds pulled back through it bound the new move (a pad's zeros are the source's edges, pulled back). A reshape does not compose (unravelling an index is not affine), so it starts a move of its own. `test_movement`: fixed cases and random chains against numpy, bit for bit.

**Rows by index** (`gather`, `put`). `x.gather(ids)` is the embedding lookup: a BRISC-only kernel that reads the indices from an int32 tensor of one row on the chip, and copies each row's two runs (left and right face) out of the table's tiles. A NoC read from DRAM keeps its low 6 address bits, so a run comes in as the 64-byte block holding it and is copied into place; the tile starts as a NoC copy of the runtime's zero tile, and a single row comes in once and fills its tile by NoC copies within L1, doubling. `x.put(ids, rows)` is its inverse, in place: a unit for each row in each matrix and tile column, so the work goes as the rows put, not as the tensor's tiles. Each worker reads the places and chains the rows that land in each tile row; the unit of a tile row's first row reads the tile once and each row's tile of `rows` once, copies the rows' runs in, in order (a later row to the same place stays), and writes the tile back, so no two workers write one tile; 32 rows that fill a tile in order (a prompt's) are that tile as they are. It was a unit for each tile of the tensor, each reading every place: a KV cache's put cost as its whole cache, 2.54M of a 32-user SmolLM step's 3.38M ttsim cycles at 1,056 places a user, where it now costs 159k. A KV cache of a fixed size takes a token's keys at its place this way, the place data rather than a shape.

### Dtypes

**fp32 tensors** (`dtype="fp32"`, `cast`, `float()`, `bfloat16()`; `test_fp32`). 4 KiB tiles, the same layout. SrcA and SrcB hold 19 bits, so fp32 cannot go through the FPU. In an fp32 kernel the math thread unpacks each operand straight into its own Dst half (`fill`: unpacker 0 in its second config context, which has unpacking to Dst on and which the math thread selects with its `UNPACK_MISC` thread config; the 32-bit Dst row is channel 1's Y at 64 bytes a row; that thread's `SRCA_SET` must be off), waits for the unpacker (`FILLED`), and the SFPU does every op, add, sub and mul included, each rounded once, so a fused fp32 tree is numpy's float32 exactly. Because the math thread owns its Dst half, filling it needs no new handshake: it waits for a free half, fills it and computes, in order. It also takes over the unpack thread's other duties in such a kernel (waiting for BRISC's fetches, draining SEM_L1, reporting frames); the unpack thread only relays the reports to BRISC.

- **One dtype a kernel.** bf16 cannot be unpacked into Dst (ttsim does not model it) and fp32 cannot go into SrcA whole, so a kernel computes in one dtype: its inputs and slots are of it (slots one tile of it apart, since the unpackers' Z stride counts datums: `slot_base`). A binop of bf16 with fp32 casts the bf16 side first, as tinygrad does, and a number takes its tensor's dtype, so fp32 constants are exact.
- **Casts, and matmuls written as fp32**, pack their result in another format than the kernel computes in, into two 4 KiB buffers at `OUTS` (the packer's base and slot stride are config). A cast at the root of a tree is in the tree's kernel, in place on the op below it: the pack thread switches the packer to the result's format for the root's pack and back (`repack`: the config bytes that differ, by `RMWCIB` once the packer is idle; in the ISA, `Dstacc` is only the packer's intermediate format). In a bf16 kernel the result is rounded to bf16 first (`ftob`, the packer's own rounding), so a fused cast is bit for bit the value cast on its own (`test_fused_cast`). The packer's Dst row stride is in bytes of its source format, 64 for fp32 and 32 for bf16. Its modes: `Read_32b_data` with `Dstacc` = `Pack_in_format` = `Pack_out_format` = fp32 (0x100) or bf16 (0x155); bfp8 packs from fp32 ("Weights in BFP8").
- **Movement and gather** move 4 bytes a value; an fp32 transpose is a move, since the unpacker transposes only on its way into SrcA. A matmul's fp32 operand that is a transpose is split into its bf16 parts first, and those transpose as bf16 does (read transposed as B, the tile transpose as A), so a matmul's backward, all A^T and B^T, moves nothing.
- **Not fp32-grade**: matmul ("Matmul precision").

**int32 tensors** (`dtype="int32"`; `test_int32`). Two's complement in DRAM and L1, and in Dst and the LRegs too: the unpacker (format 8, into Dst only), `SFPLOAD`, `SFPSTORE` in its INT32 mode and the packer (mode 0x188) move the bits as they are. `SFPSTORE`'s FP32 mode flushes denormals, which are the small positive integers, so everything that stores integers or picks bits (the int programs, `keep`, `drop`, `relu`) stores in the INT32 mode (`RAW`; the ISA says as much). An int32 kernel is an fp32 kernel's shape (the math thread fills Dst) with integer programs: add and sub by `SFPIADD`, wrapping as int32 does; max and comparisons through sign-magnitude (`SFPCAST` mode 3, its own inverse), the order `SFPGT` and `SFPSWAP` use, a comparison giving 1, not 1.0; `keep`, `drop` and `relu` as they are, since they only look at the sign or at zero. `SFPMUL24` multiplies 23 bits, so multiplies, reductions and float functions go through fp32, exact below 2^24, and a matmul is the FPU's, for floats only.

- **Casts** between floats and integers are SFPU programs on the root's result before its pack: an integer to sign-magnitude, then `SFPCAST` to float (to nearest); a float to an integer toward zero by shifting its mantissa, hidden bit in (`SFPEXMAN`), by its exponent - 23 (`SFPSHFT` takes a signed amount from a register), 0 where the exponent is negative, negated where the sign is set. `SFPSTOCHRND` would round, but only into 16 bits.
- **Mixing**: a float number with int32 makes fp32 (an int number stays int32), int32 with a float tensor meets in fp32, and `where` turns a condition of another dtype into 0 or 1 of the picked values' dtype first. Negation is `0 - x` for int32, exact, where `x * -1` would go through fp32.

**Upload and download** (`frombytes`, `tobytes`) move a dtype's values between row-major order and tile order with no per-value Python work. Upload goes by 8-byte words: each word of a row's runs of 16 values goes to its place in every tile of the row's band in one strided copy, and each DRAM bank's tiles (tile i is bank i % 8's) go in one write, about 15 times faster than a run at a time: GPT-2's 124M weights are on ttsim's chip in 2 s, SmolLM2-360M's in 6. Download goes the same way back, a row at a time: each word of its runs comes from every tile of its band in one strided copy. The host's part of reading a row of Llama-3.1-8B's 128,256 logits is 0.2 ms; done a face row of a tile at a time it was 6.4 ms, a quarter of a token at B2's 41.3 tokens/s. And it was quadratic: a slice that copied the rest of the buffer for every tile made 64 MiB take 164 s (8 MiB, the most any test reads, 0.7 s), until the bring-up rehearsal read back 256 MiB.

### Autograd

**Autograd** (`requires_grad_`, `backward`, `gradient`; `test_autograd`). tinygrad's way: a rule per op (`_backward`), applied from the result back in reverse order of making, each rule a few of the same lazy ops, so the backward pass is ordinary tensors, fused into kernels as the forward is. A tensor made from one that requires a gradient remembers how (`_ctx`: the op, its operands, its arguments), and keeps that past realizing, which throws `op` and `srcs` away; without `requires_grad` nothing is kept, so inference holds no graph. What the forward fused stays lazy, so the backward recomputes it rather than store it.

- **Rules** are tinygrad's: add, sub and mul by the chain rule; max splits a tie in half; a comparison and where's condition get none; `keep` and `drop` pass g through the same pick; exp, exp2, log, log2, sin, cos, sqrt and reciprocal from their result or input; a cast casts back; a sum broadcasts back and a max goes to its maxima, shared; a matmul is `g @ B^T` and `A^T @ g`.
- **Broadcasting**: an operand that was broadcast gets g summed over those axes (`_unbroadcast`). A gradient that is itself broadcast (a sum's) stays that way through elementwise rules and is made whole (`expand`) only where every element is needed: matmul, movement, and the leaves.
- **Movement and views record what they mean**, not the copy's map: reshape, permute, expand, pad, slice, index, split, merge, transpose, repeat, each undone by its inverse (a slice by a pad, a merge by a split, an expand or a repeat by a sum). A slice with a step other than 1 or -1 has no backward yet. gather's backward is a one-hot matmul, `onehot(ids)^T @ g`, so repeated rows add.
- **An op, not its implementation**: an fp32 matmul is bf16x3, and is recorded as one matmul, whose backward is two more fp32 matmuls (differentiating through its bf16 parts would round the gradients to bf16), made from the parts the forward kept and g's, split once for both.
- **Transposes cancel**: when a matmul's B is a transpose, its gradient is made transposed, `(g^T A)^T`, and a transpose of one not yet made is what it transposes, so the transpose's own rule hands on `g^T A` and no fp32 transpose (a move) is made: the tied output layer's `wte.T`, attention's `k.T`.
- `test_autograd` checks every op's backward against numpy's central differences in float64, through a loss `sum(f(x) * w)` with random w, in fp32 with odd shapes and broadcasting: within 2e-4 (fp32 and the SFPU programs), 2^-11 for matmuls (the FPU's sums). Then a bf16 leaf (its gradient comes back through the cast), a tensor read twice, and `.grad` adding over two passes.

- **Fewer, wider matmuls**: each block's q, k and v projections are one matrix, and gate and up another (`fuse`, at load).
- **RoPE** in Hugging Face's form, `x cos + rotate_half(x) sin`, with `rotate_half(x)` as `x @ turn`, a fixed matrix of 1s and -1s (exact, each entry one of x's), so all of RoPE is one kernel for every head of q, k and v together: the tables hold a head's cos and sin for each, v's 1 and 0, so v's heads come through exactly (x times 1, plus 0) and a token's keys and values come out side by side, into one cache tensor a block (its keys' heads, then its values') by one `put`. The cos and sin tables are computed in fp32 and rounded to bf16, as Hugging Face does for a bf16 model.
- **Grouped-query attention without copying keys**: each key and value head is read once for every query head it serves, in place (`repeat_interleave(3)`), so the 9 heads stay one batch through scores, mask, softmax and values, and are written straight into their columns of one matrix (`merge`); the mask is one row for all.
- **A KV cache of a fixed size**, a row for every place the generation reaches: each token's keys and values are put at its place (`put`), its RoPE rows gathered from the tables by place, and its mask built on the chip from the places, so every decode step launches the same 358 kernels (11 or 12 a block, then the norm and the logits; a replay adds a copy of each of its two inputs) and is replayed from a recording (`jit`): the host's part of a token is 0.1 ms ("The host's part, and replay"), the chip's 158k ttsim cycles. `test_kv_cache` replays its steps against numpy. A long prompt goes a chunk at a time (`llama.prefill`, `test_chunked_prefill`), as Tenstorrent's prefill takes one: each chunk's keys and values are cached before the next chunk reads them, so attention's scores are a chunk's rows by the cache's places, not the prompt squared. B3's 32,768 tokens would take 68 GB of scores at once for Llama-3.1-8B's 32 heads, twice the card's DRAM; the benchmark sends them 1,024 at a time (2 GiB of scores), and 4,096 at once. On ttsim, 32,768 tokens through a block of one head, 1,024 at a time, each chunk's attention over all the cache's places as B3's is, give numpy's pick, the logits within 0.08 of their span of 39. B2's model has run in part: one block in Llama-3.1-8B's shapes (`test_llama_8b_shapes`, with `LLAMA8B=1`: 4,096 wide, 32 query heads sharing 8 KV heads, an MLP of 14,336, Llama 3's RoPE scaling), random weights at TT's performance precision, picks numpy's tokens for a 64-token prompt and two decode steps, its logits within 0.4%, 0.3% and 0.9% of their span; a decode step is 20 launches for the block and the logits. On ttsim its upload and casts take 144 s (the MLP's gate and up to bfp4 is 114,688 tiles), past `Runtime.wait`'s default minute.
- **Several sequences at once** (`forward`'s `slots`, `test_batched_decode`): the next tokens of each in turn, their caches side by side in one (`kv_cache` of `size` rows, sequence u's the u-th part, which `slot` views), so one `put` writes every sequence's keys and values. Each token's attention reads its own sequence's rows and no other's: the cache is a batch of each key head and sequence (`Tensor.split` by rows, in place), and the queries the rows of the same batch, a key head's query heads side by side for each of the sequence's tokens; that is one move of q from the token's row (RoPE's kernel writes the heads side by side again, `merge`, where a key head's query heads already are) and one of the output back, with the mask laid out as the scores are (`around`: a column of places, made once a step). So a key head's rows are read once for all its query heads, where a batch of query heads, each with its key head repeated, read them once a query head (3 times for SmolLM-135M, 8 for Qwen3.6), and every sequence's for every token. A decode step of SmolLM-135M for 32 sequences of 32 places each is 453 launches and on ttsim 814k cycles (25k a token), against 340k when each read every sequence's rows: the attention kernels are a third of what they were (13k cycles against 43k), and the two moves a block 586k, since a move copies a datum at a time ("Next for the compiler", 6). At 1,056 places each it is 994k against 4.26M ("Rows by index": the cache's put cost as the whole cache then). - **Gated DeltaNet** (`delta`). One matmul makes q, k and v (16 key heads of 128, 32 value heads of 128) and z, b and a, in fp32. q, k and v go through a causal conv of 4 taps over the tokens (its last 3 inputs kept between calls) and SiLU; q and k each to length 1 and q scaled by 128^-1/2, each key head serving two value heads. Each value head keeps S, 128 by 128: a token decays it by e^g (g = -exp(A_log) softplus(a + dt_bias)), corrects it toward its value by beta = sigmoid(b), S = e^g S + beta k (v - e^g S^T k)^T, and reads it with its query; the reads are RMS-normed per head and gated by SiLU(z). In fp32 from the conv on, as transformers computes it, with the conv's taps, the decay, dt_bias and the norm kept in fp32 (`weight_format`), so no step casts them.

The cumulative sums and the chunk's masks are products by triangles of ones, kept on the chip (`triangle`). Each state is written back in place (`assign`) once what reads it is computed (`realize`), so a replay (`jit`) carries it from step to step as a KV cache's `put` does.

**A small CNN** (`conv2d`, `max_pool2d`; `test_mnist_cnn`). Convolution is im2col: one matmul of the weights (out, in k²) by the patches (in k², positions). With each channel flattened into a row of H W values, tap (ky, kx) of the kernel is those rows from ky W + kx on, so the patches are k² slices of one tensor, stacked (`cat`). Their column y W + x is the patch at (y, x) for every x, and the k - 1 columns of each row past the last x wrap around and are dropped from the result (2 in 28 for MNIST). Each tap is one move: the flattening (a reshape), k - 1 zeros on the end, the slice and the pad that puts it in its rows of the stack compose. Weights are (out, in, k k), PyTorch's with the kernel flattened, since tensors have three axes; for the same reason an image is (channels, height, width), one at a time. Stride 1 only. A max pool is three reshapes and two maxes: the k rows of each block as a batch of k-row matrices and their max, then the k columns. Both are built from ops with backward rules, so they have gradients. An MNIST-shaped network (a 3x3 convolution 1 -> 8 and relu, a 2x2 pool, a 3x3 convolution 8 -> 16 and relu, a pool and 784 -> 10) gets logits within 2% of numpy's in float64, in 46 launches an image. **Training** (`test/train.py`, `test_train`). A small GPT, GPT-2's blocks (`gpt2.layer`, the code that runs inference) 2 deep, 64 wide with 2 heads of 32, 64 characters of context and the output layer tied to the token embedding, learns README and LESSONS a character at a time, one window of 65 characters a step, with Adam at lr 3e-3. Weights, gradients and Adam's moments are fp32 tensors. PyTorch is the reference, with its own autograd and `torch.optim.Adam` (`gpt2.fns` has a branch for torch tensors), two ways: each step it takes ferrite's weights as they are and computes the same loss and gradients, and it trains by itself from the same first weights on the same text. Over 300 steps every loss is within 1e-4 of PyTorch's on the same weights and the gradients within 1.6e-2 of each weight's largest (1.5e-3 at the median step), and both losses fall alike (a mean of 3.41 over the first 50 steps to 3.07 over the last; PyTorch on its own, 3.39 to 3.01). `test_train` takes five steps on a text of its own (the numbers to 2999 written out), so editing the docs cannot move it.

- **The two runs part, though each step is right.** Adam's first step moves every weight by lr times the sign of its gradient, and a gradient below the matmul's error (about 2^-12 of the largest, "Matmul precision") can come out either sign: after one step, 87 weights were a whole step from PyTorch's (74 of them key biases, which change nothing: softmax ignores a constant added to a row of scores). From there they are two models on the same text, so the step-by-step check is the test, and the curves have to fall alike.
- **The loss** is `cross_entropy`: `log_softmax` (x - max - log of the sum of e^(x - max)) times a one-hot of the targets, summed and averaged over the positions.
- **Adam** is PyTorch's, written with lazy ops: per weight a kernel each for m, v and the weight, each written back with `assign`, which computes the new value in place, into the weight's own DRAM (a kernel reads each tile of an elementwise input before writing that tile; a matmul, which reads whole rows, would be computed first on its own). The step's bias corrections are 1 x 1 tensors, not numbers, so they can change while the kernels stay the same.
- **A step** is one call, recorded and replayed (`jit`): the window's token ids, its targets' one-hot and Adam's two scales are its inputs, and its loss, gradients and updates are written to the same DRAM each step. It is 427 launches and 272k ttsim cycles. Each fp32 matmul is three bf16 matmuls written as fp32 and their sum, and each fp32 operand two kernels, hi and lo ("Matmul precision"); its parts are made once and kept for the backward, which splits only the incoming gradient. Adam is 84 launches, three a weight.

**Fuzzing** (`test_fuzz`). Random expressions (elementwise ops with broadcasting, unary ops, reductions along each axis, matmuls, odd shapes, batches), and every kernel they turn into checked against numpy on the same inputs read back from the chip. Checking kernel by kernel keeps bf16 rounding that piles up through a tree from passing for a bug, or hiding one. The test runs 30 expressions; longer runs of the same code (thousands) found two limits the compiler did not respect, and `_expr` now computes such reductions first, on their own: a kernel sweeps its rows at one width, so row reductions of tensors of different widths cannot share one, and it has two accumulators, so a third reduction in a pass cannot either. Runs of 2000 (`FUZZ=2000`) flag something else now and then: sin or cos of an argument the tree's bf16 roundings have moved by a few hundredths (numpy computes the tree unrounded, so the oracle is only as exact as the tree is well conditioned; sin and cos are held to +-8, and of exp's 4e9 they were noise).

## ttsim

**What ttsim can and cannot check here.** ttsim runs each Tensix instruction the moment it can, in zero time, and ignores the busy conditions of `STALLWAIT`. Each TRISC pushes as fast as it can, and TRISC2, with the least to push, runs ahead, so the waits really happen there. Breaking each one on purpose (and running the tests) shows: without the pack's `SEMWAIT`, the math's Dst-half wait or the SEM_L1 wait, ttsim stops on a semaphore taken while empty or posted while full (`test_fusion` alone hits all three); without BRISC's wait for `UNPACKED` or TRISC2's wait for `SENT`, results are wrong; without TRISC0's wait for `FETCHED` or the math's wait for `READY`, a test fails or hangs. Not caught on ttsim: the `STALLWAIT` before thread 0's report (unpacks are instant there), TRISC2's wait for `READY` and TRISC0's `tensix_idle` before setting it (ttsim's semaphores start at 0 and its thread 0 is always done by then), and the accumulator semaphores. The `STALLWAIT`s are what the ISA asks for, and only silicon will show a missing one.

**ttsim-chaos** (`test/ttsim-chaos.patch`, against ttsim v1.11.5 at 464814f: `git apply` it in a ttsim checkout and build as ttsim builds). ttsim with what it leaves out, each part off unless its environment variable is set:

- `TTSIM_CHAOS_NOC=lo,hi`: a Tensix tile's NoC request is carried out `lo` to `hi` clocks after it is issued. Until then a read, or a write that is acknowledged, counts in `NIU_MST_REQS_OUTSTANDING_ID` and a write in `NIU_MST_WRITE_REQS_OUTGOING_ID` (which ttsim keeps at 0); its source is read, its data lands, and its acknowledgements and read responses are counted only then. Requests on a static VC between the same two places keep their order, as the NoC guarantees; requests on dynamic VCs may overtake each other. The request's registers are kept as they were at issue, and Ethernet tiles (Tenstorrent's firmware) are left alone.
- `TTSIM_CHAOS_TENSIX=p`: each time a Tensix pipe could run its next instruction, it waits a turn with probability `p`.
- `TTSIM_CHAOS_RISCV=p`: each clock, a Tensix tile's RISC-V core skips its step with probability `p`.
- `TTSIM_CHAOS_SEED=n`: the random generator's seed.
- `TTSIM_CHAOS_UNHARVESTED=1`: a p150 of 140 Tensix, none harvested, as its firmware runs it before 19.5 (ttsim models the 120 of 19.5 on). It found the split K that read 2 to 3 times a matmul's inputs ("Split K").

The suite passes under each: NoC delays of 1-20, 0-100 and 0-400 clocks; Tensix 0.3; RISC-V 0.3; NoC 0-200 with Tensix and RISC-V at 0.3 and at 0.5; the models, tinygrad and PyTorch with NoC 0-200 and both at 0.3; and unharvested, alone and with NoC 0-200 and both at 0.3; and over 100 seeds more, 20 of them wide (NoC 0-200 and 0-1000, Tensix and RISC-V 0.3 and 0.5, half unharvested) and 80 at NoC 0-200 with both at 0.3, but for one run of `test_train` ("Still unknown or untested"). It catches what ttsim cannot: without BRISC's wait for a frame's reads (`ready`'s `noc_wait`) or thread 0's wait for a matmul step's reads (`landed`), ttsim passes and ttsim-chaos fails at once. Run over twenty seeds, it found TRISC0 pushing a matmul's steps kept in L1 more than 15 reports ahead of thread 0, whose next post landed on a full SEM_UNPACKED: one run in twenty at Tensix and RISC-V 0.5, and every run with the Tensix stalled nine turns in ten (`TTSIM_CHAOS_TENSIX=0.9`), under which the suite now passes ("Between BRISC and the TRISCs"). (The firmware's wait for a kernel's writes before it reports is belt and braces: every kernel waits for its own writes' acknowledgements first, and nothing fails without it.) Still not modelled: the busy conditions `STALLWAIT` and `SEMWAIT` wait on (the units still finish at once), so the waits listed above stay silicon's to check.

**How ttsim counts** (`libttsim.cpp`, `clock_current_chip`). In one clock, each tile steps its RISC-V cores once and runs one Tensix instruction from each pipe that can go, and does it again for as long as any pipe ran one. So a Tensix instruction that is queued costs nothing, whether pushed, replayed or expanded from a MOP (all of which put it in the FIFO at once); clocks go by only while every pipe of a tile is empty or stalled, one RISC-V instruction a clock. A kernel's cycles on ttsim are the RISC-V instructions on its critical path while the Tensix waits: polling, handshakes, NoC requests. So:

- **The host's polls bound every measurement.** `pci.Sim.tick` runs ttsim 10 clocks a poll (it ran 1000 until 2026-10-18, rounding each wait up to the next 1000).
- **The host's own work costs nothing**, nor does the math, nor DRAM, which answers at once. These cycles compare versions of our code; they do not predict silicon.

**ttsim's cycles are its model, not silicon's.** A kernel whose root is a binary op costs about 50 cycles a tile more than one whose root is unary (`x + y` 120 a tile, `exp(x + y)` 72, on one worker): the difference is in how ttsim times the math thread's last `STALLWAIT` of a tile, not in our code.

**Cutting the critical path.** A profiling copy of ttsim (outside this repo) writes, for each idle clock of a tile, the PC of each of its RISC-V cores, mapped to the kernel's source through an ELF built from the same C, or a per-clock trace of a tile (its Tensix instruction count, its PCs, its FIFOs' fill). It showed where a matmul waited: the math TRISC on queued instructions waiting for data, the unpacker TRISC polling BRISC's count of fetches, BRISC waiting for multicast flags and for reports, and above all a column's leader issuing B's tile reads, about 36 RISC-V instructions each, while everyone waited on it. Reads through a preset initiator (`noc_get`, 17 instructions) and the reads shared out among a row's and a column's workers fixed that. It also showed what not to do: the math thread is already ahead (replay makes a matmul step 6 words for 64 `MVMUL`s), so the MOP expander, which only saves pushes, would change nothing on ttsim. Writing each tile's code once, its frame picked at run time, took a bfp8 token's matmul from 1.50k cycles to 0.77k and a softmax from 1.39k to 1.22k, doing the same work: the pack thread no longer sat polling for BRISC's sends. Not because the frame's words became stores (ttsim does not stall a store on a full FIFO, silicon does): pushed as `.ttinsn`s picked by a branch, the matmul is still 0.77k. The stores cost the benchmark matmul 3% then (1.51k to 1.56k; later work made it 1.49k).

## Next for the compiler

1. **The MOP expander.** The TRISCs push every instruction themselves; the MOP expander would turn a whole tile's math into one word, and the loops over units and tiles could run in it. It saves pushes only, which ttsim does not count and which replay already keeps few; measure it on the card, at low fidelity, where a matmul step is 16 cycles rather than 64.
2. **Reads in flight** are 4 steps a worker, a guess: on the card, measure decode at other `DEPTH`s, with bf16 and bfp8 weights, against the card's DRAM bandwidth. And where they go: every worker reads each bank through its first port (`bh.DRAM`, `BANK`), so 8 of the 24 DRAM endpoints carry all of them across the NoC, where tt-metal gives each bank a reader beside it for its DRAM-bound matmuls (`get_optimal_dram_bank_to_logical_worker_assignment`). If decode falls short with `DEPTH` tuned, the port nearest each worker is the next thing to measure.
3. **Sharing in more matmuls.** Batched matmuls of more than one row (attention's heads in prefill) and matmuls in kernels that reduce still read their own copies: each line of attention's scores reads all of kᵀ, which the lines of a head could share.
4. **Passes recompute**: softmax computes exp twice; its intermediates could stay in L1 when they fit. With few lines, line ownership leaves workers idle; splitting a line across workers would need a cross-worker reduction. A matmul epilogue could stay in Dst (`(a @ b) + c` by unpacking c and adding into the same half), and a bf16 kernel's intermediates could stay fp32 instead of rounding each to bf16 (fp32 kernels already do).
5. **Constants in fp32.** In a bf16 tensor a number is bf16 too, so `x * (1/768)` (a mean) multiplies by 1/768 rounded to 8 bits, 0.2% off. A mean could scale in fp32 at the end of its reduction, and a constant in general could ride into the SFPU program that reads it, as exp's does.
6. **Movement in words**: a run copies a datum at a time, where runs that line up in both tiles could go a word at a time, or by NoC reads within L1. Attention over each sequence's own rows moves q and its output each block: those two moves are 586k of a 32-sequence SmolLM step's 814k ttsim cycles. Moves are 69% of a four-slot Qwen3.6 step on ttsim too (the cut's two blocks, 220k of 317k cycles). A result of one column (a column vector's tile holds it 32 times, so broadcasting reads the tile as it is) was copied across a datum at a time, each place computed afresh: along each row's two runs it is 6.4k cycles where it was 39k for Gated DeltaNet's q and k as columns, and the step 236k. The experts' weighted sum reshaped each token's 8 choices into one matrix's rows, fetching 8 source tiles a result tile one after another (free on ttsim, whose NoC answers at once, and a NoC round trip each on a card): it now reads each choice's entries in place, every 8th a view (a batch slice with a step), in one kernel, and the step is 217k, a launch fewer a block. Of the rest, the most is the conv's pads (13k each, a division or two a line). A move that writes its rows into a view of a bigger tensor would make a convolution's patches k² moves the size of a tap, with no sum after.
7. **Long K in one kernel.** A matmul whose block's rows of A and three buffers of B do not fit below slot 256 is cut along K into parts that do (`shared_k`), each a kernel of its own, whose sum goes to DRAM in bf16 for the next part to read back and add to. B1's 4,096³ is such a matmul: on a grid of 12 columns by 9 rows a worker's block is 15 by 11 result tiles, so K goes in 10 parts of 13 tiles, and on ttsim it reads 5.5 times its inputs from DRAM, the partial sums most of it (about 600 MB written and read back, against 64 MB of inputs). On the card it would wait on DRAM (0.7 ms at 512 GB/s, against 0.4 ms of `MVMUL`s at two phases), and its sums are bf16 between parts where B1 asks for fp32. K in chunks inside one kernel, each result tile's partial sum kept in L1 in fp32 and unpacked into Dst again for the next chunk (ttsim models the packer's L1 accumulation too, in fp32), would read A and B once a block. A block's 165 partial sums in fp32 are 660 KB, where 506 KB of L1 is free past the slots (302 KB past a block-float B's buffers), and the unpackers' Z counter reaches slots below 256 only: so the block in two or three parts by columns, A's rows shared again for each (1.5 to 2 times the inputs in all), with the partial sums in a region the unpacker reaches another way. The catch is A: shared anew each chunk, its rows need the three buffers B's columns have (a worker may overwrite a buffer only once every worker of its grid row is done with it), so 3 x 15 rows and B's 3 buffers leave chunks of about 5 K tiles below slot 256, and reloading each partial sum every 5 steps is a large share of the work. A loop order or blocking that keeps fewer of A's rows live (or a second way to address L1 for them) comes first; the card will say how far DRAM, not the `MVMUL`s, bounds B1. Three designs, weighed and not written: (a) the parts stay launches of today's kernel, each adding its sum into the block's partial sums kept in the worker's L1 by the packer (`Pack_L1_Acc`, which ttsim models in fp32 and bf16), the last sending them home: the inputs read once and no partial sums in DRAM, but state kept in L1 from one launch to the next; (b) one kernel, A's rows shared afresh for each part once every worker of the grid row is done with the last (a count each adds to on the others by NoC atomics), the partial sums in L1 as in (a); (c) the chunks of 5 above. In bf16 a block's partial sums (330 KB) fit, rounded between parts as today; in fp32 (660 KB) only half a block's do, so A is read twice (1.5 times the inputs), and the last part must load an fp32 tile into Dst inside a bf16 kernel, which thread 0 has to do between its own unpacks, since unpacker 0's two contexts share `SEC0_format`.
8. **Fewer launches a token**: on a card each launch costs the chip a microsecond or more. A SmolLM block is 11 launches, every third one 12: the residual stream is realized only when an RMSNorm's tree passes 15 ops (then it goes first, as a value two of the tree's ops read), so the RMSNorms in between add up every matmul output since. A kernel that also wrote an intermediate (the residual) would keep each at one kernel. (A split K's sum stays lazy through a split into heads and a matmul by a small matrix, `_terms`, so RoPE takes the q, k and v projection's parts as they are: that was a kernel a block. Turning split-K off would save it too (162k ttsim cycles a token against 170k, when it was a kernel a block), but on a card the split gives a token's matmuls the workers its DRAM reads need in flight: 512 GB/s at about a microsecond's latency is some 512 KB, 64 workers at `DEPTH` 4.)
9. **Fewer kernels**: a training step's 117 fused kernels are 552 KiB against 500 KiB of L1 for code, so a replay writes some back every step. Many are the same ops at another shape (Adam's three, for each weight's); shapes as arguments rather than constants would share them.

## tinygrad on ferrite

`adapters/tinygrad_ferrite.py`, `test_tinygrad`. tinygrad is the frontend (its Tensor, nn, autograd, optimizers) and ferrite the compiler and runtime, as tt-tiny lays the stack out. tinygrad finds a device only as `tinygrad.runtime.ops_<name>`, so the adapter puts a module there (`FERRITE`), with an allocator whose buffers hold host bytes or a chip value. It takes over at `create_linear_with_vars`, where tinygrad would schedule a graph into its own kernels: by then the graph is tinygrad's primitives on shaped tensors (the ALU ops, `REDUCE`, `RESHAPE`, `PERMUTE`, `EXPAND`, `PAD`, `SHRINK`, `CAST`) with explicit `STORE`s into buffers and `AFTER`s that order them, and a graph that touches FERRITE runs in the adapter, op by op into ferrite's lazy tensors, which ferrite fuses and launches its own way. tinygrad gets back an empty schedule.

- **The graph's semantics.** A `BUFFER` reads as it is before any store in the graph; an `AFTER` reads its buffer again through its view chain, after the stores so far (reading the view computed before the store gave Adam zeros, and NaN). `REDUCE(op, n)` folds the leading n axes (tinygrad permutes the reduced ones to the front); binary ops broadcast numpy's way, with no `EXPAND`; `SHRINK` and `PAD` take (start, size) pairs. `COPY` onto FERRITE uploads. A buffer tinygrad views at an offset (a slice of a realized tensor, read back) reads through to the whole one (`Part`); a value with nothing in it (a dimension of 0) is the host's, zeros, or a reduction's identity.
- **Views** (`View`, `materialize`). Movement stays a view of a ferrite tensor: shape, strides, offset, and a mask for padding (a small ShapeTracker), reshaped by merging and splitting axes where the strides line up. An axis of 1 can be all padding (a pad's slice), which expanding or merging it keeps. An op that needs the data folds the view into ferrite's three axes: the tensor as it is, a ferrite transpose for a swapped one (which a matmul reads in place), one move if the view's axes merge into three groups, block swaps for a pure reordering (each swap of two blocks of axes is one move, since a move reads its source in row-major order whatever its axes: attention's heads apart or together are two), and otherwise the host.
- **The fold.** Any rank goes to (1, all but the last axis, the last), so a short axis (6 tokens) does not pad its tiles to 32 rows, and an elementwise op takes its operands in the grouping one of them already has (a batched matmul's result, say) rather than moving them into the default.
- **Matmul.** tinygrad writes `a @ b` as a broadcast multiply summed. A `REDUCE(ADD)` of a `MUL` whose operands do not broadcast along the summed axes is a ferrite matmul: along the other axes, both spanning one is the batch, a alone the rows, b alone the columns. A product that only sums read is deferred, so it is never computed as the (64, 6, 128, 128) tensor it describes.
- **The host.** What ferrite does not do (uint32 and uint64, bit operations, `THREEFRY`: tinygrad's random numbers) runs on tinygrad's own CPU device, lazily, so tinygrad fuses what runs there as it would on its own: a subgraph of host values stays a tinygrad graph until it meets a chip value, is computed then, and goes up in that value's layout. Evaluated op by op into numpy instead, a dropout's random numbers made whole a padded view that tinygrad's `arange` sums: 10 GB for a moment. A weight that comes as bytes goes up in the shape of its first use, and one kept in a shape its uses do not fold to (tinygrad makes weights flat) is laid out again once. A host value that reads no buffer (a constant's arithmetic, an `arange`) is the same every time: it goes up once and is kept, or is a plain number if its values are all one. A buffer of at most a tile row's 32 values (an optimizer's step numbers) goes up as soon as it is read, so its arithmetic runs on the chip; on the host it was spread there to every weight's shape and uploaded each step, which halved an MLP's Adam step's Python when it stopped.
- **Functions.** A `CALL` of a tinygrad function (`@function`, as `examples/beautiful_mnist.py` writes its model) runs as its body, the arguments in for its parameters and its outputs stored into the buffers the call made for them (tinygrad's own `resolve_function`; its next step, which hands the stored value on as the call's result, is tinygrad's scheduling, which the adapter does not do). A precompiled function (`@function(precompile=True)`, as tinygrad's LLM code wraps each block) is inlined too: tinygrad would cache its program, and ferrite runs the graph. The function's own buffers (its `ALLOC`s) become fresh buffers each call, as tinygrad's schedule makes them, and a store may go through a bare `STAGE`, which keeps its source's buffer.
- **Buffers.** tinygrad's allocator gives a freed buffer to the next one of its size; the FERRITE one does not (`lru = False`), since a buffer's holder keeps a chip value in its own shape and dtype, and the next owner read it as its own (two fp32s as BatchNorm's int64 count).
- **JIT.** tinygrad's `TinyJit` replays the schedules it recorded, and the adapter makes none, so on FERRITE it is ferrite's replay instead (`tinyjit`, over `_TinyJit.__call__`, on `tensor.Recording`, which `tensor.jit` uses too): the first call runs, the second is recorded, and each later one copies its inputs into the second's and sends its launches as one block, running nothing on the host. A buffer the recorded call stored into (a weight, Adam's moments) has its new value copied back into the tensor the recording read it from, a launch each, so the next replay reads it there; and a store of a value computed already copies it, since a replay writes over its tensors in place. A call that works on the host with what it finds there (random numbers, whose counter lives there; a value brought down), stores in another layout or into an input, takes an input that is not a whole buffer on the chip, or binds a symbolic variable runs every time instead, correct and slow; tinygrad's own checks of the inputs and the result raise as they would. A small MLP's Adam step: 0.1 ms of host replayed, against 19 ms, its losses tinygrad CPU's. tinygrad's `examples/transformer.py` uses dropout, whose random numbers the host makes (threefry, on 64-bit counters ferrite does not have), so its steps run every time, as before. The runner (`python3 adapters/tinygrad_ferrite.py script.py`) sets `DEV=FERRITE` through tinygrad's own context variables, since tinygrad reads the environment when imported.
- **Results.** `test_tinygrad`: elementwise ops, reductions, 3-D views, a matmul, softmax, integers and bools, and stores into parts of a buffer, against tinygrad's CPU device; an MLP trained with Adam for three steps, to 1e-3 of the same on the CPU; and a layer for five under TinyJit, replayed; every op on the chip. tinygrad's `examples/transformer.py`, unchanged (2 blocks 128 wide, 4 heads, batches of 64 sequences of 6), learns two-digit addition: its 10 rounds of 50 Adam steps ran to the end on ttsim, test accuracy 86.4% after the first and 99.99% after the last (1 of 10,000 wrong), about 7 hours with the code of the day. tinygrad's own basic checks of a backend (`test/test_tiny.py`) all pass, but for the two for images; of its `test_ops`, 356 of 420 pass (most of the rest the FPU's matmul precision); of its `test_jit`, 32 of 50 (the rest look at tinygrad's own kernels), and of `test_setitem`, `test_assign`, `test_nn` and `test_optim` 108 of 149 that run (the rest: several devices, its own kernel counts and scheduler errors, symbolic shapes, bitcasts); with `RUN_SLOW=1`, 45 of `test_nn` and `test_optim`'s 73 (most of the rest SGD's steps, which compare to 1e-6 through a matmul's gradient, the FPU's 2^-11). A training step is 1155 launches and 1.98M cycles, 16 s on ttsim, in 0.5 GB. What it took to get there, from 52 s a step: views folded into ferrite's axes rather than through the host, short axes not padded to whole tiles, transposes read in place by matmuls, products not made whole before their sums, and moves by whole tiles and runs.
- **A store into part of a buffer** (`t[2:4, 3:5] = x`, `x.assign` to a slice, a KV cache's rows): the part is a view of the buffer's elements, and the buffer's contents are worked on on the host, the part's elements replaced, then go back as bytes; a value read from the buffer before keeps what it had. Correct, and slow for a big buffer: a store of whole rows could be a `put` on the chip.
- **PyTorch**, through tinygrad's own frontend (`extra/torch_backend` in tinygrad's repository: PyTorch's `"tiny"` device, which hands aten ops to tinygrad Tensors), runs on FERRITE as on any tinygrad device, with FERRITE as tinygrad's default (the runner sets it). `test_torch_frontend` (tinygrad at 0026302, PyTorch 2.11): elementwise ops, a sum, a matmul, softmax, layer norm and a conv2d against PyTorch on the CPU, each on the chip (the matmul and the conv to the FPU's precision), and an MLP's three Adam steps within 1e-4 of the CPU's losses (4.4e-5 measured).
- **tinygrad's LLM code** (`tinygrad/llm`'s `Transformer`, which its CLI builds from a GGUF file: the other model code a server could run; `test_tinygrad_llm`). It runs on FERRITE: two SmolLM-135M blocks, converted to GGUF from the same safetensors (llama.cpp's tensor names and its q and k permutation, which tinygrad undoes), bf16 weights (`HALF=0`), give ferrite's numpy model's logits within 0.024 of their 54-wide span, the same tokens, and `test_tinygrad_llm` checks the same on random weights in SmolLM's shapes. It is far from like for like yet. tinygrad's GGUF loader leaves most weights as lazy bitcasts of the file's bytes on the host (even with `REALIZE=1`, five of a block's seven), so each call unpacks them there and sends them up. With every weight on the chip (as `test_tinygrad_llm` loads them), a decode step of those two blocks is 186 launches against ferrite's own model's 32 (`models/llama.py`), because:
  - its activations are fp32 (`.float()` after the embedding), so each bf16 weight's matmul is an fp32 one, which ferrite runs as two bf16 matmuls (the activations split into bf16 parts, 10 kernels; a weight cast to fp32 is read as the bf16 it was, its transpose in place, so neither the cast nor the transpose runs: 264 launches before);
  - its KV cache is fp16, which the adapter does not carry, so the cache lives on the host and each step's keys and values come down to it (11 readbacks);
  - its place is a symbolic variable, so no step is replayed: each runs op by op through the host, seconds a token on ttsim;
  - it ignores Llama 3.1's RoPE scaling (`rope_freqs.weight` is unused, only YaRN is handled), so on Llama-3.1-8B its logits would not be Hugging Face's: a change to tinygrad, not to the adapter;
  - it cannot say a weight's format or a matmul's fidelity phases, which TT's performance precision needs.

  For a like-for-like B2, tinygrad's path needs bf16 activations, or the adapter to multiply fp32 by bf16 as one bf16 matmul; a cache in a dtype the chip holds (fp16 on the chip, or a cache dtype tinygrad lets its caller choose); replay of a step whose place is symbolic; formats per weight; and Llama 3's RoPE scaling in tinygrad.
- **Not done yet.** Shapes with tinygrad's symbolic variables in them on the chip (they run on the host); a store through a bitcast or a pad; masked views over several merged axes (through the host); dtypes other than float32, bfloat16, int32 and bool (on the host); a jitted call with random numbers, replayed.

## Serving

`models/serve.py` (`test_serve`, `test_serve_sessions`, `test_chat_tools`, `test_fetch`), an OpenAI-compatible server for a Llama-family model: ROADMAP's Stage 2 asks it to serve Qwen3.6-35B-A3B with tool calls and reasoning, keeping each session's caches and states in host memory between its turns.

- **Slots.** The engine's KV cache has `slots` slots of `places` rows, side by side as several sequences' are ("A Llama-family model"), and each step is one call of `forward` for every slot (its `slots`). A free slot takes part too, its token at its last row, which no sequence reaches (one may hold `places - 2` tokens), so the step's shapes never change and it is replayed (`jit`) whoever comes and goes. A prompt is prefilled into its slot `chunk` tokens at a time, a chunk between two steps (a slot still prefilling idles on its last row), so a long prompt slows the others' tokens rather than stopping them (`test_serve` watches a 50-token one go in 16 at a time between another's tokens); the step after its last chunk takes it in.
- **The prefix cache.** Each slot remembers the tokens whose keys and values its rows hold. A prompt goes to the free slot that holds the longest start of it (of slots holding as much, the one used longest ago) and only the rest is prefilled, from its last token at least, whose logits give the first new one: a system prompt or a conversation so far costs nothing the second time, and nothing is copied. `test_serve` checks that a prompt run again gives the same tokens with one token prefilled, and that a free slot's step spoils nothing its slot holds.
- **Gated DeltaNet's slots** (`test_qwen3_5_sequences`). Each slot has its own states, a batch entry of each block's (`kv_cache`'s sequences; `llama.slot` gives a slot's as views of them, and its part of each KV cache). A prompt's chunk takes its slot's states alone; a decode step a token of every slot (`step`), the slots' heads one batch, and a `live` row (1 or 0 a slot) keeps the states of a free or prefilling slot, which runs on its last row, as they were. In place, as the step replays: on ttsim each slot's logits are within 0.2% of its sequence decoded alone on the chip, and its prompt's bit for bit.
- **Sessions on the host.** A KV cache's rows serve any start of what they hold, but Gated DeltaNet's states are for exactly the tokens they took in. So a slot goes on from what it holds only when the prompt begins with all of it; and a session (its tokens, its slot's rows of each cache in whole tiles and its states, as bytes) is saved on the host when its prompt is in and when its request ends, up to `keep` bytes (4 GiB unless said), the least recently used going first. A prompt takes the free slot that holds the most of it, or, when a saved session holds more, the slot used longest ago with that session put back into it (its rows by `put`, its states by `assign`); a slot whose states are past where the prompt parts from them takes its states from 0. That is an agent's turn: Qwen3.6's template keeps each assistant turn's reasoning after the last question, so the next prompt is the last one, its answer and the tool's result, and goes on from the session saved when the answer ended; one that parts after the prompt goes on from the one saved when the prompt was in. `test_serve_sessions`: three requests on two slots, then two such turns once both slots hold others, each with its new tokens alone prefilled and every token's logits within 3% of numpy's from nothing. For an attention model the same saving lets a prompt go on from a session no slot holds any longer.
- **Speculative steps** (`Engine.speculate`, `test_serve_speculative`), for a model with a multi-token prediction layer: each step is two replayed calls, one verifying every slot's token and its draft (`check`), one drafting the next (`guesses`). The pick for the first token is sampled as it would be without a draft; if it is the draft, the second token's logits count too and a second pick follows, so the tokens are the model's own at any temperature, one or two a step. The drafting call takes the layer over the step's two places (the second the first again where the draft was turned down, so its cache has a row for every place); a prompt's prefill runs the layer over the prompt's places too, the last giving the first draft. A session saved after a turned-down draft keeps the states before it; a slot that goes on from such states takes them as its own first. `test_serve_speculative`: with an oracle's drafts (numpy's own next tokens) 9 of 9 compared are taken; with the layer's own at random, 0 of 18; three requests on two slots give numpy's logits either way, and an agent's next turn goes on from a session saved after a turned-down draft, its new tokens alone prefilled.
- **Tools** (`chat`'s tools, `qwen`, `calls`; `test_chat_tools`). Qwen3.5's and Qwen3.6's template written out, as the others are (its own is Jinja): the tools in the system turn with its words on how to call them, the reasoning of each assistant turn after the last question, tool calls as `<tool_call><function=...><parameter=...>` XML, tool results in a user turn; the strings are Qwen3.6's own `chat_template.jinja`'s, through transformers, and `llama.Tokenizer` encodes them as its tokenizer does, token for token. The answer's tool calls come out as OpenAI's `tool_calls` (each value as its tool's schema types it), with `finish_reason` `tool_calls`; streamed, the text stops where a call begins (and holds back what may begin one), and the calls come after it. `tool_choice` (`serve.chosen`, `test_tool_choice`) is a shape the answer keeps to (a thinking model's after its reasoning): `none`, no `<tool_call>`; `required`, the answer a call of the tools from its first character, whole before it may end; a function by name, calls of it alone. `Request.pick` keeps a shape by checking the token it draws: taken if the text it makes can still begin the shape (an end of sequence only once the text is a whole one), else drawn again with that token left out, so no step masks 248K tokens, and one where the model is in the shape already checks one. `response_format` (`serve.formatted`) is a shape too, for completions as well as chats: `json_object`, an object; `json_schema`, a value of its schema (type, properties, required, additionalProperties, items, minItems and maxItems, enum and const, anyOf and oneOf, `$ref` into `$defs`; a string's pattern or a number's bounds not kept to), by a prefix parser of the text, 0, 1 or 2 as tool_choice's. With tools offered and tool_choice auto, the answer is the format or a call. Between JSON's tokens goes one space, tab or newline at most and a number has 32 characters at most, since either could go on for ever (held to a shape, a model's whitespace does: vLLM's Qwen models' has), and a comma comes only where a key or an item may follow, so no start leads nowhere: 480 answers of random logits to four schemas all parse and end. A model with no end of sequence ends when nothing more fits.
- **Requests.** On the host from each token's logits (`Request.pick`, `test_sampling`): the presence, frequency and repetition penalties first, as vLLM applies them (presence and frequency by the tokens made, repetition by those and the prompt's), then greedy at temperature 0, else sampled at that temperature from the `top_k` most likely, the fewest of those whose probabilities sum to `top_p`, and of those the ones at least `min_p` of the most likely's (a seed makes it repeat). The fewest are sought among the 1,024 most likely first, and among all only when those hold too little: a sort of Qwen3.6's 248K tokens is 5 to 8 ms of the host's a token, against a decode step of eight users' 28 ms on the card; a peaked distribution's token now takes 1.3 ms and one sampled from all 0.7. Log probabilities (`logprobs`, `top_logprobs`; a completion's `logprobs`) are the model's own, from its logits before any penalty or temperature, as vLLM gives them, with each streamed piece's tokens. Until an end-of-sequence token (`generation_config.json`'s, or `config.json`'s), a stop string, `max_tokens`, or a full slot. Text goes out as it is made, held back only while a stop string might be beginning at its end or a character's bytes are still coming. A streamed request whose client has gone ends at its next token, or takes no slot if it is still waiting (a whole one runs to its end: nothing tells its handler sooner).
- **HTTP** (`http.server`, a thread a connection): `/v1/models`, and `/v1/completions` and `/v1/chat/completions`, whole or as server-sent events; chat messages go into the model's template, Llama 3's, ChatML or gpt-oss's harmony, told apart by `tokenizer_config.json`'s or `chat_template.jinja`'s (a template is Jinja, which the standard library cannot run; Llama 3.1's default system message, with its dates, is left out), their special tokens taken as tokens. A prompt longer than a slot is refused, and a request with no text for 600 s ends with a 504: a hung chip is reported. Usage counts the prompt's cached tokens (`prompt_tokens_details`' `cached_tokens`: those its slot or a saved session held, which were not prefilled), as OpenRouter bills them, and comes as a stream's last chunk too, as OpenRouter's own API sends it; OpenRouter sends an agent's next requests back to a provider that cached its last when cached tokens cost less there.
- **Thinking.** A model whose template has `<think>` (Qwen3's) gives its reasoning apart from its answer, in `reasoning_content` beside `content`, whole or streamed (`answer`: before `</think>` and after; all reasoning until it comes); told not to think (`chat_template_kwargs`' `enable_thinking: false`, as vLLM takes it), its prompt ends with an empty reasoning, as Qwen3's template writes it, and the text is the answer. gpt-oss's harmony is a third kind of template: its own system message (its identity, knowledge cutoff, today's date, `reasoning_effort`, low, medium or high, and its channels), a first system message as a developer's, the turns, and its text an analysis channel (the reasoning) then a final one (the answer).
- **A model id** (`fetch`): Hugging Face's files for it, downloaded once into `~/.cache/ferrite/hub` (from `HF_ENDPOINT` if set, with `HF_TOKEN` for a gated model): config, tokenizer, the configs of generation and chat it has (and a chat template in a file of its own), and its weights in one file or the shards its index names; a finished download is marked and not asked for again.
- **Measured.** On ttsim, SmolLM-135M (bf16, two slots of 128 places): three requests at once over HTTP ("The meaning of life is", "The capital of France is", "Once upon a time", the third waiting for a slot) and then "The meaning of life is a", whose start a slot holds, each come back with numpy's greedy text (" a question that has been asked", " Paris. It is the largest", ", there was a curious little", " question that has been asked by"). `test_serve` checks the same on a random model: three requests on two slots, numpy's greedy tokens for each, and the same again from the prefix cache.
- **Not yet.** Several choices a request, tool calls of templates other than Qwen3.5's; more requests at once than slots (they wait).

## The cost model

`models/cost.py` (`test_cost`): what a model costs to serve, from its config alone (`llama.config`), as ferrite would run it. A card holds the weights in the formats a mode gives them (`bf16`, `bfp8`, `bfp4`: Tenstorrent's performance precision, `experts`: every expert matrix in bfp4), a GiB for kernels and activations, and sessions: each a KV cache row a token in every attention block (a sliding window's at most) and Gated DeltaNet's states (twice when speculating). A decode step for n users reads every matrix but the experts and the embedding, the experts its tokens pick (each block's E (1 - (1 - k/E)^tokens)), each token's own session's rows, and the states, read and written; it waits on DRAM or on its matmuls, whichever is longer, then on its launches, counted on ttsim at Qwen3.6's shapes (`cmp/qwen36/launches.py`, four slots: 27 a Gated DeltaNet block, 12 an attention block with its norms, 18 a mixture of experts more, 11 the rest, 65 a DeltaNet block taking a token and a draft, 45 the drafting call). The card is its specification until the probe has measured it (`python3 -m ferrite.probe 8 probe.json`, then `probe=probe.json`): 512 GB/s of which a step reaches 0.7 (a guess), 664 TFLOPS at one fidelity phase (two taken), a microsecond a launch, PCIe 4.0's 25 GB/s; at $1,299 the card, $600 its share of a host, three years and 375 W at $0.15 a kWh, $0.128 an hour. Llama-3.1-8B in Tenstorrent's performance precision reads COMPARE's 6.20 GB a token within 2%.

What it says of Qwen3.6-35B-A3B on one card, its experts in bfp4 (21.7 GB) and sessions of 32K tokens (`python3 models/cost.py path/to/Qwen3.6-35B-A3B experts kv=bfp8`):

- **25 sessions a card** with the KV cache in bfp8 (`kv=bfp8`), each 0.36 GB of rows (10.9 KB a token) and 66 MB of states; 14 in bf16 (0.67 GB). A step for one user reads 3.1 GB in 10.2 ms: 98 tokens/s, $0.37 a million; for eight, 9.5 GB in 28 ms: 35 tokens/s each, 283 a card, $0.13 a million; for sixteen 344 a card, $0.10 (in bf16, eight make 227 a card, $0.16), against its providers' $0.70 to $1.80.
- **A session's rows are most of what a step reads** once a few users share it: a token reads its session's whole cache, 0.36 GB at 32K places in bfp8 (0.67 in bf16), against 2.5 GB of weights for any number of users.
- **A session's rows are read once a step**, a key head's for all its query heads ("Several sequences at once"). They were read once a query head, eight times for Qwen3.6, which made a step at eight users four times as long.
- **Launches are a sixth of a one-user step**: 1,661 a token, 1.7 ms of its 10.2 at a microsecond each, 810 of them the Gated DeltaNet blocks' (27 each, where a chunk of one took 86) and 720 the experts' (18 a block).
- **Speculation pays only when most drafts are taken**: a token and a draft both read the whole cache, and the DeltaNet blocks launch more, so a step with a draft costs 59% more than one without at one user and 87% more at eight, the share of drafts that must be taken for it to pay. Short contexts make it cheaper.
- **A prompt's token** is 8.6 GFLOP at 32K places: 39,000 tokens/s a card were its matmuls never idle, a tenth of a cent a million. A session back from the host takes 18 ms over PCIe.

## Two cards (ROADMAP, Stage 4): the plan

What Tenstorrent's sources say, read for the route that needs none of their runtime, and the first step, on ttsim: `pci.open_device(n)` opens chip n of a multi-chip build (one library, its clock and the host memory it reaches shared), a runtime runs on each, `Chip.links` finds the links up and to which chip's channel (each side's peer is the other's ASIC id), and `Chip.send` moves data from one Ethernet tile's L1 into its peer's, the host itself writing the TX queue's registers over the NoC, which reaches them (`test_two_chips`, on ttsim's `bh_x2`: a P300's two chips, linked twice). And from DRAM to DRAM with no code on the Ethernet tiles at all (`Tensor.to`, `link_kernel`): a worker on each chip, the sender's reading a tensor four tiles at a time into one of two slots in its Ethernet tile's L1 and writing the TX queue's registers over the NoC to send it, then a flag, into the same places in the peer's; the receiver's waiting for each flag, writing the chunk into its tensor and sending back a credit, for which the sender waits before it fills a slot again. On ttsim a tensor of 24 tiles goes across each link and back, and a model split across the two chips (`test_two_chips`: its first block on one, its second and its head on the other, each chip with its own copy of the RoPE tables, its own mask and its own KV cache, the hidden state crossing the link between the blocks) gives the whole model's logits within 0.13% of their span of numpy's: the shape of Stage 2's 70B on two cards, by `llama.layer` and `Tensor.to` alone, which `forward` does not yet do itself. ttsim carries a link write at once, so the flags and credits are checked there for what they count, not for timing: the card will tell, and how fast (a worker's NoC round trips for each register written are the first suspect). Sources, in their repositories: tt-isa-documentation `BlackholeA0/EthernetTile/` (its `ethdump` sample above all: a userspace program that runs its own code on an Ethernet tile while Tenstorrent's firmware keeps the link), tt-metal `tt_metal/hw/inc/internal/tt-1xx/blackhole/eth_fw_api.h` and `dev_mem_map.h`, `hw/inc/internal/ethernet/tunneling.h`, and tt-umd's Blackhole topology discovery.

- **The tiles.** 14 Ethernet tiles on NoC0 y=1 (x 1-7 and 10-16), each 512 KiB of L1, two RISC-V cores (E0, E1) and one 400 GbE link; a QSFP-DD port is two tiles, 800 GbE. On a p150 four tiles' SerDes go to PCIe and two are harvested (telemetry tag 35, ENABLED_ETH), leaving 8 with ports; tt-umd's translated coordinates for them are x 24-31, y 25. A tile's own NIU says what it is (endpoint id `0x02xx`, its channel in the low byte).
- **What runs there.** E0 runs Tenstorrent's Ethernet firmware: link training, retraining after a drop, and its mailboxes. Its L1 is the top 64 KiB (0x70000 on): boot results at 0x7CC00 (postcode 0xC0DEA000 when the link trained, port status 1 when up), the remote chip's identity at 0x7CFE0 (its board id and channel), mailboxes at 0x7D000. E1 is free: `ethdump` holds it in reset (`SOFT_RESET_0` 0xFFB121B0, E1's bit 0x1000), writes its code to L1, sets its reset PC (0xFFB14008) and lets it go, never touching E0, and tt-metal's single-core Ethernet mode, which it forces on ttsim, does the same. Resetting E0 retrains the link: never.
- **Crossing the link.** A transmit queue is registers at 0xFFB90000 + 0x1000 n: source, size and destination (16-byte aligned), then `CMD` 2, a TT-link write into the peer tile's L1 at the destination address. The hardware numbers, acknowledges and resends the packets, so they arrive once and in order, but the sender only learns that the command was taken: completion is a 16-byte flag sent after the data on the same queue, which lands after it, and the receiver's acknowledgement back. E1 must use NoC1 (the firmware uses NoC0), and leave the queues and classifier as the firmware set them, sending on TXQ0 as tt-metal's single-core mode does.
- **Speed.** 50 GB/s each way per link, about 48 of payload (tt-metal's CCL report), 0.5 us a hop: about 100 GB/s each way per cable, 400 for a card's four ports. tt-metal's fabric moves packets of up to 15 KB, a few in flight, credits returned by remote increments.
- **The first step.** Find the link (port status 1 on x 24-31, with a timeout, and the peer's identity from 0x7CFE0); load a small program on E1 at both ends; the sender reads a chunk of DRAM over NoC1 into a slot, sends it and then its flag, and waits for a credit; the receiver polls the flag, writes the slot to DRAM, waits for the NoC's acknowledgements and sends the credit back; the host times it all out and puts both E1s back in reset (no kmd does it for us). ttsim's two-chip build (`bh_x2`, a P300's two chips, channels 2 and 3 wired to 9 and 8, a mock firmware on E0, both chips one process's two PCIe devices) can test it before a cable exists.
- **Risks.** tt-umd calls Blackhole's links flaky: poll their status during a transfer, never wait without a timeout. Which two tiles make up a port differs between sources; one cable needs only the one link that is up. Whether the firmware itself sends on TXQ0 at run time is not known.

## Bring-up on a p150

Everything so far ran on ttsim, which models the chip from Tenstorrent's own knowledge but runs each instruction at once, ignores most busy conditions, and completes NoC requests instantly (ttsim-chaos delays them and jitters the cores, and the suite passes under it). On a card, go in this order; each step only needs the ones before it. The tests open the card themselves when `TTSIM` is not set (`pci.open_device`), so the commands are the simulator's without it, as root.

Before: the card has its 300 W on one 12V-2x6 cable and `lspci -d 1e52:b140` shows it, its link at PCIe 5.0 x16 (`lspci -vv` says `LnkSta: Speed 32GT/s, Width x16`; a narrower one slows uploads and the probe's PCIe rows, not decode); the IOMMU is off or in passthrough (`iommu=pt`), since `pci.Card` hands the device physical addresses; a few 2 MiB hugepages are free (`echo 4 > /proc/sys/vm/nr_hugepages`; each `Runtime` holds one). `pci.Card` unbinds tt-kmd itself, and stops with what to do when it is not root, when the IOMMU translates the card's DMA (its group's type is not `identity`), or when no hugepage is free. Tenstorrent's own tools (tt-smi, tt-flash, and TT-NN for step 12) want tt-kmd built for the running kernel: read the card's firmware version with `tt-smi` first, and if it is older than the latest bundle (tenstorrent/tt-firmware), flash that with `tt-flash`, so both stacks run on the firmware the benchmark records.

## Still unknown or untested

- **gpt-oss-20b's two blocks, twice wrong in bf16.** Two of six runs of the same check gave the chip's logits far from numpy's (18% of the span at one decode step; 34% over the prompt), each with other heavy work on the host beside it (a numpy script; the whole suite); every run alone agreed within 0.73%. Not the replay (bit for bit op by op's), not stale DRAM (every new block filled with NaN first: none read), not launches overlapping (one at a time). What the host's load can change in a simulator that runs only when ticked is the open question: the chip's timing against the host's at boot (the AI clock's wait is the host's 0.2 s), and with it which freed DRAM each block reuses. Run it under load until it fails, then compare that run's kernels and addresses against a good one's.

- The real-card backend (`pci.Card`) and the reset (`pci.reset`) have not run on a card yet. It assumes root, the IOMMU off or in passthrough, and free 2 MiB hugepages (Bring-up, above).
- Whether ASIC_STATE0, the all-on power message and AICLK go busy wake Tensix on silicon after kmd clock-gated it and take the AI clock to 1,350 MHz (`python3 -m ferrite.chip` prints the clock it reached), and whether the PCIe tile's window 0 reaches host memory without kmd's iATU ("Host memory, from the device" has the fallback).
- Whether the host-to-PCIe-tile loopback in `test_dma` (BAR read that turns into a device read of host memory) behaves on silicon as it does on ttsim. Device-initiated writes from a core's NIU into host memory, the path that matters (every readback, the dispatcher's status), run on ttsim but are untested on silicon.
- ISA does not document BAR2 (iATU, DMA engine), the DRAM tile's internal address map, ARC's message protocol, or the power-on value of soft reset. ttsim models them; real silicon may differ.
- ttsim does not model `mhartid`, `fence.i`, the PC snapshot registers, NoC request splitting, or most of BAR2. Plain ttsim completes every NoC request instantly, so a unicast's outstanding count is back to 0 before anyone reads it, and a posted write's bytes have left before the next instruction; ttsim-chaos delays requests ("ttsim-chaos"), but neither stalls on the busy conditions `STALLWAIT` waits for.
- That posted writes to host memory on one static VC arrive in order is the ISA's Wormhole NoC ordering, and its PCIe section; Blackhole's says nothing yet. Were a status to pass its times on the card, `profile` would read that launch's entry before it is written: an older launch's times, or zeros. Instruction cache invalidation is a no-op in ttsim, so `test_relaunch_without_reset` cannot catch a stale-instruction bug.
- One run of `test_train` under ttsim-chaos (NoC 0-200, Tensix and RISC-V 0.3, seed 6) disagreed with PyTorch at one of its middle steps, while its last step's loss and gradients came out bit for bit as in every other run: the training was right, and a value read back for the comparison (the weights PyTorch was given, a gradient, or the loss) was not. It has not come back in 112 runs since: 80 of the whole suite (in 60 of them each of training's 285 readbacks compared by hash, all identical) and 32 of training alone at up to NoC 0-2000 and 0.5. If it does, a hash of every `tobytes` in order against a good run's names the first wrong one.
